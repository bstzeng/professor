模組 B｜文字怎麼變成數字 · 第 7 課

為什麼中文比英文吃 token

這一課的目標

  • 知道中英文 token 效率的實際差距
  • 理解這個差距從哪裡來
  • 算出它對成本與 context 的影響

1. 實測差距

同一段話，用同一個 tokenizer 切，中文需要的 token 數通常明顯多於英文。 大致的經驗值是：

語言每 token 平均涵蓋1000 字需要
英文約 4 個字元（約 0.75 個單詞）約 1,300 tokens
中文（新式 tokenizer）約 1–1.5 個漢字約 700–1,000 tokens
中文（舊式小詞表）約 0.5 個漢字（一字拆多 token）約 2,000+ tokens

關鍵變數是詞表裡有沒有收中文。 Llama 2 的 32K 詞表幾乎沒收漢字，一個字常被拆成兩三個位元組 token； Llama 3 的 128K 詞表與 Qwen 的 151K 詞表收了大量中文詞，效率好很多。

2. 為什麼會這樣

原因在 BPE 的訓練語料。合併規則是統計出來的， 語料裡中文佔比低，中文字串就不會被合併成獨立 token， 於是退回位元組層級——而一個漢字在 UTF-8 裡是 3 個位元組。

漢字「模」的 UTF-8 編碼 = E6 A8 A1（3 bytes） 詞表沒收「模」 → 3 個 token 詞表收了「模」 → 1 個 token 詞表收了「模型」→ 1 個 token（兩個字一起）

3. 這件事花你多少錢

以 API 計價為例，假設每百萬 token 收 1 美元， 同一份 10 萬字的中文文件：

Tokenizertoken 數成本倍數
中文友善（1.2 字/token）約 83,000$0.0831.0×
中文不友善（0.5 字/token）約 200,000$0.202.4×

更嚴重的是 context 上限。 同樣宣稱 32K context 的兩個模型， 中文友善的那個能吃進兩倍以上的中文內容。 「context 長度」這個數字要換算成字數才有意義。

4. 對生成速度的影響

推理速度通常以 tokens/秒 計。同樣 30 tokens/秒：

  • 英文：約 22 個單詞／秒，讀起來很快
  • 中文（1.2 字/token）：約 36 個字／秒，也還行
  • 中文（0.5 字/token）：約 15 個字／秒，明顯卡

所以比較模型速度時，如果你的用途是中文， 單看 tokens/秒 會誤導——要看字/秒。

5. 怎麼自己測

python - <<'PY' from transformers import AutoTokenizer text = "這是一段用來測試中文斷詞效率的範例文字，總共大約三十個字。" for name in ["meta-llama/Llama-3.1-8B", "Qwen/Qwen2.5-7B"]: tok = AutoTokenizer.from_pretrained(name) n = len(tok.encode(text)) print(f"{name}: {n} tokens, {len(text)/n:.2f} 字/token") PY

挑模型時，如果主要處理中文，這個數字值得先測一下—— 它同時影響成本、context 與速度三件事。

重點回顧

  • 中文 token 效率取決於詞表有沒有收中文
  • 沒收的話退回位元組，一個漢字吃 3 個 token
  • 影響三件事：成本、可用 context、實際閱讀速度
  • 比較模型速度時，中文用途要看字/秒而非 token/秒
