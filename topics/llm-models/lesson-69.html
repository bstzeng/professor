Context length、RoPE scaling 與 YaRN

這一課的目標

  • 區分宣稱 context 與可用 context
  • 理解 RoPE scaling 與 YaRN
  • 學會判斷長 context 的真假

1. 問題

一個模型用 8K context 訓練，能不能處理 32K 的輸入？ 技術上可以（RoPE 沒有長度上限）， 但模型沒看過那麼遠的位置關係， 表現會急遽劣化——通常是開始語無倫次或忽略遠處的內容。

2. RoPE scaling

解法的基本想法是：把位置壓縮到模型熟悉的範圍。

方法做法問題
位置內插（PI）把位置 m 除以 s，32K 壓成 8K 的尺度近距離的解析度被犧牲
NTK-aware改 rope_theta 而非直接壓位置不需微調，但效果有限
YaRN不同頻率的維度用不同策略：高頻不動、低頻內插需要少量微調，但效果最好

YaRN 的洞見是：RoPE 的不同維度負責不同尺度的距離（第 8 課）。 管短距離的高頻維度不該被壓縮（否則相鄰字的關係會糊掉）， 只有管長距離的低頻維度需要調整。

3. 怎麼看出模型用了 scaling

// config.json "max_position_embeddings": 131072, "rope_scaling": { "type": "yarn", "factor": 4.0, "original_max_position_embeddings": 32768 }

這段話的意思是：

  • 原本訓練到 32K
  • 用 YaRN 外推 4 倍到 128K
  • 32K 以內是「原生」的，之後是外推的

如果 rope_scaling 是 null 而 max_position_embeddings 很大，那才是真正原生訓練的長度。

4. 宣稱 vs 可用

宣稱通常的實際可用範圍
原生訓練長度100% 可用
YaRN 外推 2 倍大致可用，長文件檢索略降
YaRN 外推 4 倍以上能讀進去，但深處的資訊容易被忽略
無微調的純內插品質下降明顯

一個實用的檢驗是「大海撈針」測試： 在很長的文本中間藏一句特定資訊， 然後問模型那句話是什麼。 很多宣稱 128K 的模型，在 64K 位置就開始撈不到了。

5. 自己啟用 scaling

# llama.cpp：直接指定更長的 context，引擎會自動處理 ./llama-server -m model.gguf -c 32768 --rope-scaling yarn --rope-scale 4 # transformers：改 config config.rope_scaling = {"type": "yarn", "factor": 4.0}

但要記得：硬開 scaling 而模型沒有對應微調，品質會掉。 而且 KV cache 會按照你設定的長度線性增加（第 68 課）， 開 128K 卻只用 4K 是純粹的浪費。

6. 實務建議

  1. 設定實際需要的長度，不要一律開最大
  2. 優先選原生長 context的模型，而非靠外推的
  3. 真的需要處理超長文件時，考慮 RAG 而非硬塞 context—— 檢索出相關片段，比讓模型讀一百萬字便宜也準確得多
  4. 用大海撈針測試驗證你實際需要的長度是否可靠

檢查你的理解

  1. 說明 YaRN 相對於單純內插的改進
  2. 從 config 判斷一個模型的原生 context 長度
  3. 解釋為何開最大 context 是浪費
