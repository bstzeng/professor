模組 N｜評測與選型 · 第 76 課

自己建 eval set

這一課的目標

  • 建立自己的評測集
  • 選擇合適的評分方式
  • 知道要多少題才夠

1. 為什麼要自己做

公開 benchmark 測的是「一般能力」，你在乎的是 「在我的任務上好不好用」。這兩者的相關性沒有想像中高。

而且你自己的評測集沒有污染問題—— 沒有模型看過它。這是它最大的價值。

2. 三十題就夠開始

題數能分辨的差距適合
10很大的差距（30% 以上）快速篩掉明顯不行的
30中等差距（15–20%）候選模型的初步比較
100較小差距（8–10%）正式選型
300+細微差距持續迭代、回歸測試

不要因為「只有三十題不夠科學」就不做。 三十題的自製評測，比任何公開榜單都更能預測你的實際體驗。

3. 題目從哪來

  1. 真實記錄：從你實際用過的 prompt 裡挑，這是最好的來源
  2. 涵蓋邊緣情況：刻意放幾題你知道很難的
  3. 包含失敗案例：之前哪個模型答錯過，就放進去
  4. 分類平衡：如果你有五種任務類型，每種各六題

一個常見錯誤是只放簡單題—— 結果所有模型都滿分，評測沒有區分力。 好的評測集應該讓最好的模型也只拿到七八成。

4. 評分方式

方式適合成本可靠度
精確比對有標準答案（分類、抽取）零高
程式驗證格式、JSON schema、可執行的程式碼低高
關鍵字檢查回答必須提到某些要點低中
模型評分開放式回答中中
人工評分最終確認高最高

優先用可程式化的評分。 能用精確比對就不要用模型評分—— 前者可以每次改動都重跑，後者要花錢且有雜訊。

5. 模型評分的注意事項

  • 用比你要評測的模型更強的模型當評審
  • 給明確的評分準則（rubric），不要只說「打 1 到 10 分」
  • 注意位置偏誤：兩兩比較時，把順序對調再跑一次
  • 注意自我偏好：模型傾向給自己家族的輸出較高分

6. 一個最小可行的做法

# eval.jsonl {"id": 1, "prompt": "...", "expect_contains": ["關鍵字A", "關鍵字B"]} {"id": 2, "prompt": "...", "expect_json_keys": ["name", "date"]} {"id": 3, "prompt": "...", "expect_exact": "分類C"} # 跑法（虛擬碼） for model in candidates: score = 0 for case in load("eval.jsonl"): out = generate(model, case["prompt"]) score += check(out, case) print(model, score / total)

把它存成腳本，每次要換模型、換量化等級、改 prompt， 就重跑一次。這比任何榜單都有用。

7. 別忘了測這些

  • 速度：記錄每題的 tokens/秒 與總時間
  • 輸出長度：推理模型的成本差異在這裡
  • 穩定性：同一題跑三次，答案會不會飄
  • 格式遵循率：要求 JSON 時，有幾成真的給出合法 JSON
