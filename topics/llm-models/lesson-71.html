模組 M｜跑起來：硬體與記憶體帳 · 第 71 課

塞不下時的手段：offload、mmap、量化 KV cache

這一課的目標

  • 掌握記憶體不足時的所有手段
  • 知道各自的速度代價
  • 建立處理順序

1. 手段清單（依代價由小到大）

手段省多少速度代價
縮短 contextKV cache 線性下降無
量化 KV cache 到 q8_0KV 減半幾乎無
降一級量化（Q5→Q4）權重約 15%略快（檔案更小）
關閉其他佔用顯存的程式0.5–2 GB無
用 mmap 而非全部載入視系統而定首次較慢
部分層 offload 到 CPU任意大
換更小的模型任意能力下降

2. Offload 的代價有多大

這是最需要理解的一點。假設一個 32B Q4 模型有 64 層， 顯存只夠放 48 層：

GPU 頻寬約 1000 GB/s CPU 記憶體頻寬約 50 GB/s（DDR5 雙通道） 兩者相差 20 倍 48/64 層在 GPU：這部分很快 16/64 層在 CPU：這部分慢 20 倍 整體速度會被慢的那部分拖垮， 即使只有 25% 的層在 CPU，速度可能掉到原本的 30%。

經驗法則：只要有任何一層在 CPU，速度就會顯著下降。 offload 是「能跑」與「不能跑」的差別， 不是「快」與「稍慢」的差別。

3. 調整 offload

# llama.cpp：-ngl 指定放 GPU 的層數 ./llama-server -m model.gguf -ngl 48 # 48 層在 GPU ./llama-server -m model.gguf -ngl 99 # 全部（層數不夠就是全部） ./llama-server -m model.gguf -ngl 0 # 純 CPU # 找出最大可用值的方法：從 99 開始往下試，直到不再 OOM

另一個技巧是優先把 KV cache 留在 GPU： 某些引擎允許把部分權重 offload 但 KV 全留 GPU， 因為 KV 的存取比權重更頻繁。

4. MoE 的特殊技巧

MoE 模型有一個 dense 模型沒有的選項： 把專家層放 CPU，其餘放 GPU。

因為每個 token 只會用到少數幾個專家， 從 CPU 讀取的資料量遠小於 dense 模型。 llama.cpp 有針對這個情境的選項， 讓大型 MoE 在小顯存上跑出可接受的速度。

5. mmap

llama.cpp 預設用 mmap 載入 GGUF： 檔案不會一次讀進記憶體，而是讓作業系統按需分頁載入。

  • 好處：啟動快、多個程序可共用同一份、系統會自動快取
  • 壞處：首次執行時會有磁碟讀取的延遲
  • 注意：如果模型比實體記憶體大，會一直在讀磁碟，慢到不可用

6. 處理順序

  1. 先把 context 設成實際需要的長度（最常見的浪費）
  2. 量化 KV cache 到 q8_0
  3. 關掉瀏覽器等佔顯存的程式
  4. 降一級量化等級
  5. 還不夠 → 換小一號的模型，不要 offload
  6. 真的非要跑這個模型不可 → offload，接受速度損失

第 5 步值得強調：14B 全在 GPU，通常比 32B offload 好用得多。 速度差 5 倍換來的一點能力提升，多數情況下不划算。

  2. 解釋 MoE 為何比 dense 適合部分 offload
