模組 N｜評測與選型 · 第 77 課

選型決策樹：從需求走到模型與量化等級

這一課的目標

  • 建立完整的選型流程
  • 把前面所有模組的結論串起來
  • 產出一個可執行的決定

1. 決策樹

步驟 1：硬體限制 顯存／記憶體有多少？扣掉 2 GB 系統與 KV cache │ 步驟 2：任務類型 ├── 需要推理（數學、程式、複雜分析）→ 考慮推理模型，但算好 token 成本 ├── 需要長 context → 檢查 rope_scaling 是不是原生 ├── 中文為主 → 檢查 tokenizer 與中文評測 └── 一般對話／改寫／分類 → 一般 Instruct 模型即可 │ 步驟 3：尺寸與量化 在記憶體預算內，選「參數量最大 × Q4_K_M」的組合 記憶體很充裕才往 Q5/Q6 走 │ 步驟 4：格式 本機自用 → GGUF ／ Mac → GGUF 或 MLX ／ 服務端 → AWQ 或 FP8 │ 步驟 5：候選清單 挑 3–5 個模型，不要只挑一個 │ 步驟 6：實測 用你自己的三十題評測集跑一遍（第 76 課） │ 步驟 7：決定 同分時選：檔案小的、社群活躍的、授權寬鬆的

3. 三個典型情境的完整答案

情境一：8 GB 顯卡的筆電，想做中文摘要與改寫

  • 記憶體預算：約 6 GB 給模型
  • 尺寸：7–8B
  • 量化：Q4_K_M（約 4.9 GB）
  • 模型：挑中文能力好的 7–8B Instruct（看 tokenizer 的中文效率，第 7 課）
  • 格式：GGUF，引擎用 Ollama 或 LM Studio
  • 不要：推理模型（輸出太長）、MoE（記憶體不夠）

情境二：24 GB 顯卡，想用來寫程式

  • 記憶體預算：約 22 GB
  • 選項 A：32B dense @ Q4_K_M（約 19 GB）——品質高，速度約 30 tok/s
  • 選項 B：30B-A3B MoE @ Q4_K_M（約 18 GB）——速度快很多，品質略低
  • 建議：兩個都下載，用你自己的程式任務實測（第 76 課）
  • 格式：GGUF 或 EXL2（後者可精確填滿顯存）

情境三：要服務公司內部一百人

  • 這是批次服務場景，與單人完全不同（第 70 課）
  • 引擎：vLLM 或 SGLang
  • 格式：AWQ 或 FP8
  • 關鍵瓶頸是 KV cache 不是權重——一百人同時用，KV 可能要幾十 GB（第 68 課）
  • MoE 在這裡很划算：活躍參數少，吞吐量高
  • 要先算清楚併發數與 context 長度

4. 同分時的加分項

加分項為什麼
Apache 2.0 或 MIT 授權商用無虞（第 65 課）
官方有發 GGUF 或 QAT 版品質有保障（第 66 課）
社群活躍有問題找得到解法
有多個尺寸的同系列之後可以無痛換大或換小
原生長 context不靠外推（第 69 課）
tokenizer 中文效率好省成本與 context（第 7 課）

5. 模組 N 總結

  • 公開 benchmark 用來縮小候選，不用來做決定
  • 污染與過擬合讓分數普遍高估
  • 競技場較難作弊，但有長度與格式偏誤
  • 自製三十題評測集是最可信的依據
  • 選型流程：硬體 → 任務 → 尺寸量化 → 格式 → 候選 → 實測
