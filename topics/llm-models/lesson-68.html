KV cache 怎麼算，為什麼長 context 這麼貴

這一課的目標

  • 掌握 KV cache 的精確公式
  • 理解它為何隨 context 線性成長
  • 知道壓縮 KV cache 的手段

1. 它為什麼存在

生成第 N 個 token 時，需要對前面 N−1 個 token 做注意力。 而那些 token 的 K 與 V永遠不會改變（因果遮罩，第 10 課）。 所以算過就存起來，下次直接用。

沒有 KV cache有 KV cache
每個新 token 的計算重算全部 N 個位置只算 1 個位置
生成 N 個 token 的總計算O(N²)O(N)
記憶體不需要額外需要存 2×N×… 的張量

這是典型的空間換時間，而且換得非常划算——沒有它，長對話會慢到不能用。

2. 公式

KV cache bytes = 2 × layers × n_kv_heads × head_dim × seq_len × batch × bytes_per_element 2 : K 與 V 各一份 layers : 每層都要存 n_kv_heads : 注意是 KV 頭數，不是 Q 頭數（第 19 課） bytes_per_element: FP16 = 2, FP8 = 1, INT4 = 0.5

3. 每 token 的成本

把 seq_len 設為 1，得到「每個 token 要多少記憶體」：

模型層n_kv每 token（FP16）32K context
8B 級328128 KiB4.0 GiB
14B 級488192 KiB6.0 GiB
32B 級648256 KiB8.0 GiB
70B 級808320 KiB10.0 GiB
8B 若用 MHA3232512 KiB16.0 GiB
驗算（8B）: 2 × 32 × 8 × 128 × 2 bytes = 131,072 bytes = 128 KiB ✓

最後一列說明了 GQA 的價值：同樣的模型， 沒有 GQA 的話 KV cache 是四倍。

4. 批次服務的爆炸

單人使用時 KV cache 還好，但服務多人時它乘上 batch：

8B 模型，每人 8K context，同時服務 32 人： 128 KiB × 8192 × 32 = 32 GiB 權重只要 4.85 GB，KV cache 卻要 32 GB。

這就是為什麼 vLLM 這類服務引擎的核心技術是 PagedAttention——像作業系統管理記憶體分頁一樣管理 KV cache， 避免為每個請求預留最大長度造成的浪費。

5. 壓縮手段

手段節省代價
GQA／MQA4–32 倍模型架構決定，你改不了
量化 KV cache 到 FP82 倍品質輕微下降
量化到 INT44 倍長對話品質明顯下降
縮短 context線性能處理的內容變少
滑動視窗注意力固定上限看不到太久以前的內容
PagedAttention減少浪費需要支援的引擎
# llama.cpp 量化 KV cache ./llama-server -m model.gguf -c 32768 \ --cache-type-k q8_0 --cache-type-v q8_0 # vLLM vllm serve model --kv-cache-dtype fp8

實務建議：K 用 q8_0、V 也用 q8_0 是安全的組合， 能省一半而幾乎無感。再往下壓（q4）就要實測了。

重點回顧

  • KV cache 把生成的計算從 O(N²) 降到 O(N)
  • 大小 = 2 × 層 × n_kv × head_dim × seq × batch × bytes
  • 與 KV 頭數相關，與 Q 頭數無關
  • 批次服務時 KV cache 常常超過權重本身
  • 量化 KV 到 FP8/q8_0 能省一半且幾乎無感
