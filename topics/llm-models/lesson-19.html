GQA 與 MQA：KV head 怎麼省記憶體

這一課的目標

  • 理解 MHA、GQA、MQA 的差別
  • 算出 GQA 對 KV cache 的節省
  • 知道為何幾乎所有新模型都用 GQA

1. 三種配置

MHA（多頭） : 32 個 Q 頭，32 組 K/V ← 每個 Q 頭有自己的 K/V GQA（分組） : 32 個 Q 頭， 8 組 K/V ← 每 4 個 Q 頭共用一組 MQA（多查詢）: 32 個 Q 頭， 1 組 K/V ← 全部共用一組

config.json 裡就是 num_attention_heads 與 num_key_value_heads 這兩個欄位的比值。 相等就是 MHA，後者為 1 就是 MQA，介於中間就是 GQA。

2. 真正的動機：KV cache

參數上的節省只是附帶效果（第 11 課算過，約省 37%）。 真正的動機是推論時的記憶體。

KV cache 大小 = 2 × layers × n_kv × head_dim × seq_len × bytes 2 : K 和 V 各一份 layers : 每層都要存 n_kv : 只跟 KV 頭數有關，跟 Q 頭數無關

關鍵在最後一行：KV cache 與 n_kv 成正比。 把 32 降到 8，cache 直接變成四分之一。

3. 實際數字

以 8B 模型、32 層、head_dim=128、8K context、FP16 為例：

配置n_kvKV cache（8K token）
MHA324.0 GiB
GQA81.0 GiB
MQA10.125 GiB
驗算（GQA）: 2 × 32 × 8 × 128 × 8192 × 2 bytes = 2 × 32 × 8 × 128 = 65,536 × 8192 = 536,870,912 × 2 bytes = 1,073,741,824 bytes = 1 GiB

把 context 拉到 128K，MHA 需要 64 GiB 的 KV cache， GQA 只要 16 GiB。這已經是「能不能跑」的差別，不是「快不快」。

4. 品質代價

共用 K/V 當然會損失一些表達能力。實測結論大致是：

  • MQA：品質下降明顯，且訓練容易不穩
  • GQA（4 或 8 組）：品質幾乎與 MHA 持平
  • 分組數是可調的旋鈕，大模型常用 8，小模型用 2 或 4

這就是 GQA 成為標準的原因：它幾乎白拿—— 省下四分之三的 KV cache，品質卻沒明顯損失。

5. 怎麼看出一個模型用了什麼

curl -s https://huggingface.co/meta-llama/Llama-3.1-8B/raw/main/config.json \ | python3 -c "import sys,json; c=json.load(sys.stdin); \ print('heads', c['num_attention_heads'], 'kv', c['num_key_value_heads'])" # heads 32 kv 8 → GQA，分 4 組

評估一個模型能不能跑長 context 時， 這兩個數字比宣稱的 context 長度更有參考價值。

重點回顧

  • GQA 讓多個 Q 頭共用一組 K/V
  • KV cache 與 n_kv 成正比，32→8 直接省四分之三
  • 參數節省是附帶的，記憶體節省才是重點
  • GQA 品質幾乎無損，MQA 則有明顯代價
