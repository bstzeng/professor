VRAM 公式：權重、KV cache、啟動值、開銷

這一課的目標

  • 掌握完整的 VRAM 計算公式
  • 算出四個組成部分
  • 建立可靠的估算習慣

1. 四個部分

總需求 = 權重 + KV cache + 啟動值 + 框架開銷
部分大小與什麼相關
權重參數量 × bpw ÷ 8模型大小與量化等級
KV cache見第 68 課context 長度、batch、架構
啟動值單人推論時很小（幾百 MB）batch 大小與序列長度
框架開銷0.5–1.5 GBCUDA context、引擎本身

2. 權重

權重 (GB) = 參數量(B) × bpw / 8 例： 8B @ Q4_K_M (4.85 bpw) = 8 × 4.85 / 8 = 4.85 GB 32B @ Q4_K_M = 32 × 4.85 / 8 = 19.4 GB 70B @ Q4_K_M = 70 × 4.85 / 8 = 42.4 GB 8B @ BF16 (16 bpw) = 8 × 16 / 8 = 16 GB

更簡單的做法：直接看檔案大小。 GGUF 檔案多大，權重就佔多少記憶體（因為是直接 mmap 進去的）。

3. 完整範例

題目：8B 模型（32 層、8 KV 頭、head_dim 128），Q4_K_M，8K context，單人使用。

權重 = 8 × 4.85 / 8 = 4.85 GB KV cache = 2 × 32 × 8 × 128 × 8192 × 2 bytes = 1.07 GB 啟動值 ≈ 0.3 GB 框架開銷 ≈ 0.8 GB ──────────────────────────────────────────────────────────── 合計 ≈ 7.0 GB

所以 8 GB 顯卡剛好能跑，但幾乎沒有餘裕—— context 拉到 16K 就會爆。這就是為什麼很多人 「照理說放得下卻 OOM」。

4. 快速估算口訣

短 context（≤4K）： 檔案大小 × 1.2 中 context（8–16K）： 檔案大小 × 1.4 長 context（32K+）： 要認真算 KV cache，可能超過權重本身

對 70B 模型跑 128K context，KV cache 會到 40 GB—— 跟權重一樣大。長 context 的成本常常被嚴重低估。

5. 多卡與 offload

情況怎麼算
多張同款顯卡總量可加，但每張要留自己的框架開銷
部分 offload 到 CPU留在 GPU 的層數 × 每層大小
Apple 統一記憶體與系統共用，通常可用約 70% 的總記憶體

llama.cpp 的 -ngl（n-gpu-layers）參數就是控制 「幾層放 GPU」。放不下時從這裡調。

6. 一段可用的估算程式

def vram_gb(params_b, bpw, layers, n_kv, head_dim, ctx, batch=1, kv_bytes=2): weights = params_b * 1e9 * bpw / 8 kv = 2 * layers * n_kv * head_dim * ctx * batch * kv_bytes overhead = 1.0e9 activation = 0.3e9 * batch return (weights + kv + overhead + activation) / 1e9 # 8B Q4_K_M, 8K context print(vram_gb(8, 4.85, 32, 8, 128, 8192)) # 約 7.0 # 32B Q4_K_M, 32K context（64 層） print(vram_gb(32, 4.85, 64, 8, 128, 32768)) # 約 29
