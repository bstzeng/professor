GGUF：它是容器格式，不是演算法

這一課的目標

  • 理解 GGUF 是格式不是演算法
  • 知道檔案裡有什麼
  • 掌握它的生態定位

1. 最重要的一件事

GGUF 是一種檔案格式（容器），不是量化演算法。

是什麼類比
GGUF容器格式像 .zip 或 .mkv
Q4_K_M裝在裡面的量化方式像 zip 裡的壓縮演算法
GPTQ／AWQ量化演算法另一套演算法，存在 safetensors 裡

所以 GGUF 檔案也可以裝沒有量化的 F16 或 F32 權重。 你在 HF 上看到的 model-F16.gguf 就是這種—— 它是量化的中間產物，也是自己做量化時的來源檔。

2. 單檔設計

GGUF 把一個模型需要的所有東西打包成一個檔案：

model-Q4_K_M.gguf ├── 標頭（magic number、版本） ├── Metadata（鍵值對） │ ├── general.architecture = "llama" │ ├── llama.block_count = 32 │ ├── llama.embedding_length = 4096 │ ├── llama.attention.head_count = 32 │ ├── tokenizer.ggml.tokens = [...] ← 整個詞表 │ ├── tokenizer.chat_template = "..." ← chat template │ └── ... └── 張量資料（量化後的權重）

這帶來幾個實際好處：

  • 下載一個檔案就能跑，不用管 config、tokenizer 有沒有配齊
  • 不會有版本錯配的問題
  • 支援 mmap——不必全部讀進記憶體就能開始推論
  • metadata 可讀，用工具就能查模型規格

3. 歷史

格式時期問題
GGML早期沒有版本管理，改一次格式就全部失效
GGJT 等中間版本過渡同上
GGUF現行可擴充的 metadata，向前相容

所以看到 .ggml 或 .bin 結尾的舊量化檔， 新版 llama.cpp 已經不支援了，要找 GGUF 版。

4. 生態

工具與 GGUF 的關係
llama.cppGGUF 的發源地與參考實作
Ollama底層用 llama.cpp，模型庫都是 GGUF
LM Studio圖形介面，直接讀 GGUF
text-generation-webui支援 GGUF 與其他格式
llama-cpp-pythonPython 綁定

GGUF 最大的優勢是硬體覆蓋範圍： 它是唯一有成熟 CPU 推論與 Apple Silicon 支援的格式。 GPTQ、AWQ、EXL2 基本上都要 NVIDIA CUDA。

5. 自己做一個

git clone https://github.com/ggml-org/llama.cpp cd llama.cpp && cmake -B build && cmake --build build -j # 1. HF 格式 → GGUF（F16） python convert_hf_to_gguf.py /path/to/hf-model --outfile model-F16.gguf # 2. F16 → 量化 ./build/bin/llama-quantize model-F16.gguf model-Q4_K_M.gguf Q4_K_M # 3. 跑起來 ./build/bin/llama-cli -m model-Q4_K_M.gguf -p "你好"

轉換時要注意架構支援：新架構的模型要等 llama.cpp 更新才轉得動。 MoE 模型與多模態模型的支援通常比較晚。

6. 查看 metadata

./build/bin/llama-cli --model model-Q4_K_M.gguf --verbose 2>&1 | head -40 # 或用 Python pip install gguf python -c " from gguf import GGUFReader r = GGUFReader('model-Q4_K_M.gguf') for f in r.fields.values(): print(f.name) "

遇到「模型講不停」「輸出格式怪怪的」， 第一件事就是查 metadata 裡的 tokenizer.chat_template 與 EOS token 有沒有正確帶過來。
