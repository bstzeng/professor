模組 H｜微調：你自己做得到的部分 · 第 43 課

該微調、該 RAG、還是該改 prompt

這一課的目標

  • 建立三種手段的判斷準則
  • 認識最常見的誤用
  • 知道正確的嘗試順序

1. 三者各自解決什麼

手段解決不解決
Prompt 工程指令不清、格式不對、缺少範例模型不會的能力
RAG模型不知道的事實（你的文件、最新資訊）模型不會的行為
微調模型不擅長的行為（風格、格式、任務模式）灌入大量新事實（效率極差）

一句話記住這個區分： RAG 給知識，微調給技能，prompt 給指示。

2. 判斷表

你的需求該用
回答要根據我公司的內部文件RAG
回答要引用最新的資料RAG
輸出永遠要是特定 JSON 結構Prompt（＋結構化輸出約束）；量大時微調
語氣要符合公司品牌微調（LoRA 就夠）
要處理一種模型沒學過的內部標記語言微調
要在特定領域做分類，準確率要很高微調（小模型即可）
回答不夠詳細Prompt
模型不知道我們產品的規格RAG（不是微調）

3. 最常見的誤用

「我要讓模型學會我們公司的知識，所以我要微調。」

這幾乎總是錯的，理由有四：

  1. 效率極差：讓模型可靠記住一份文件，需要把它重複很多次， 而且還是會記錯細節
  2. 無法更新：文件改了就要重新訓練
  3. 無法追溯：模型說出來的東西無法附上出處
  4. 會產生幻覺：模型學會「這類問題該用這種語氣回答」， 然後自信地編造細節

RAG 在這四點上全部勝出：即時更新、可附出處、 不會因為沒學過就亂編（檢索不到可以說不知道）。

4. 正確的嘗試順序

  1. 先調 prompt：最便宜，常常就夠了。加 few-shot 範例、 明確的輸出格式、拆步驟
  2. 換模型：換大一號或換一個更適合該任務的模型， 比微調便宜得多
  3. 加 RAG：如果問題是知識不足
  4. 最後才微調：而且先從 LoRA 開始

很多人跳過前三步直接去微調， 結果花了幾天訓練，效果還不如把 prompt 寫清楚。

5. 微調真正划算的三種情況

情況為什麼划算
用小模型取代大模型把 70B 的某個特定能力蒸餾到 7B，推論成本降十倍
穩定的輸出格式微調後不需要在 prompt 裡塞大量範例，省 token 也更可靠
prompt 已經塞不下當 few-shot 範例超過幾十個，把它們變成訓練資料更有效

6. 模組 H 總結

  • 全參數微調需要參數量 16 倍的記憶體，LoRA 省 87%，QLoRA 再省更多
  • LoRA 的 rank 依資料量選，掛全部線性層
  • 要轉 GGUF 就必須合併，且要合併回 16-bit 基座
  • RAG 給知識、微調給技能、prompt 給指示
  • 嘗試順序：prompt → 換模型 → RAG → 微調

  2. 說出「用微調灌知識」的四個問題
