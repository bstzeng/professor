團隊的 Skill 庫

這一課的目標

  • 設計團隊 Skill 庫的結構
  • 建立 Skill 的審查與淘汰流程
  • 控制 Skill 數量與上下文成本

建議的結構

team-skills/ ← 獨立的 repo，或放在主專案 ├── README.md ← 索引：名稱、用途、負責人、風險等級 ├── multi/ │ └── parallel-research/SKILL.md ├── auto/ │ ├── plan-execute-verify/SKILL.md │ └── pr-babysitter/SKILL.md ├── tool/ │ └── commit-message/SKILL.md └── meta/ └── skill-audit/SKILL.md

實際安裝時，Claude Code 需要放在 .claude/skills/<name>/、Codex 需要 .agents/skills/<name>/（只看一層資料夾），所以分類資料夾通常用在「原始碼庫」，再用腳本或外掛打包到正確位置。

團隊規則

  • 命名：動詞或任務名、小寫連字號，避免和工具內建名稱衝突。
  • 負責人：每個 Skill 有一個人負責維護。
  • 審查：新增或修改要經過 PR 審查，風險等級高的要額外審核。
  • 淘汰：定期檢查使用頻率，半年沒用、或有更好的替代品就移除。
  • 上下文預算：限制每個專案啟用的 Skill 數量；Claude Code 可用 skillOverrides 把少用的 Skill 設為只顯示名稱或只能手動呼叫。

🧭 這一課的重點

團隊 Skill 庫建議用獨立 repo 或主專案目錄，以 README 索引名稱、用途、負責人與風險，原始碼可按分類存放再打包到工具要求的一層目錄。團隊規則包括命名一致、每個 Skill 有負責人、以 PR 審查變更、定期淘汰，並控制啟用數量（Claude Code 可用 skillOverrides 降低少用 Skill 的上下文成本）。

🧩 本課程介紹的工具與格式變化很快，內容依撰寫時（2026 年）的官方文件與原始碼庫整理，實際行為以各工具最新文件為準。收藏庫中的自製 Skill 為教學範本，使用前請依自己的專案調整；安裝任何第三方 Skill 前，請先完整閱讀其內容（第 40 課）。
