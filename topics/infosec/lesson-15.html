CSRF 跨站請求偽造

這一課的目標

  • 理解 CSRF 的原理
  • 理解 CSRF 與 XSS 的差別
  • 掌握 SameSite 與 CSRF Token 的防禦

原理

瀏覽器有一個方便的行為：對某個網站發出請求時，會自動帶上那個網站的 Cookie。所以：

  1. 你登入了網路銀行，瀏覽器裡有銀行的 Session Cookie。
  2. 你在另一個分頁打開了攻擊者的網頁。
  3. 那個網頁偷偷送出一個表單到銀行的「轉帳」網址。
  4. 瀏覽器自動帶上了你的銀行 Cookie——銀行以為是你本人要轉帳。

攻擊者看不到你的 Cookie，也看不到回應，但他不需要看到：只要讓你的瀏覽器「替他」送出請求就夠了。

CSRF 與 XSS

XSSCSRF
攻擊者的程式在哪裡執行受害網站上攻擊者自己的網站上
利用的是網站對使用者輸入的信任網站對使用者瀏覽器的信任
能否讀到資料可以通常不行，只能「發出動作」

防禦

  • SameSite Cookie：設為 Lax 或 Strict 時，從其他網站發出的跨站請求（尤其是 POST）不會帶上 Cookie。現代瀏覽器多半預設為 Lax，大幅降低了 CSRF 的風險。
  • CSRF Token：網站在表單中放一個隨機的祕密值，送出時檢查。攻擊者的網頁拿不到這個值。
  • 重要動作（轉帳、改密碼、改信箱）要求重新輸入密碼或 MFA。
  • 不要用 GET 請求做有副作用的動作——一張圖片的網址就能觸發 GET。

XSS 會讓 CSRF 防禦失效

如果網站有 XSS，攻擊者的程式就在網站自己的網域上執行，可以讀到 CSRF Token，SameSite 也擋不住。所以各種防禦要一起做，而不是只靠一種。

🧭 這一課的重點

瀏覽器對網站發出請求時會自動帶上該網站的 Cookie，所以你登入銀行後開啟攻擊者網頁，該網頁偷偷送出轉帳表單，銀行會以為是你本人。攻擊者看不到 Cookie 與回應但不需要。XSS 的程式在受害網站上執行、利用網站對輸入的信任、可讀資料；CSRF 在攻擊者網站上、利用網站對瀏覽器的信任、通常只能發出動作。防禦有 SameSite Cookie（現代瀏覽器多預設 Lax）、表單中的隨機 CSRF Token、重要動作要求重新驗證，以及不用 GET 做有副作用的動作。有 XSS 時 CSRF 防禦會失效。

🛡️ 本課程只介紹攻擊的原理與防禦方法，所有示範都是在瀏覽器內的模擬，不會連線到任何系統。未經授權入侵他人系統是違法行為（刑法第 358～363 條妨害電腦使用罪）；想練習請使用合法的靶場與 CTF。
