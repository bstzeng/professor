Docker Compose：多容器服務編排

這一課的目標

  • 理解為什麼真實應用程式常常需要多個容器協同運作，以及手動逐一啟動容器的痛點
  • 能讀懂一份docker-compose.yml，說出每個區塊的作用
  • 理解Compose預設的網路行為：同一份設定檔裡的容器，如何用「服務名稱」互相找到對方

第54課學會了用docker run啟動單一容器，但 回顧模組J的三層式架構：一個真實運作的網站，通常需要 網頁伺服器、應用程式伺服器、資料庫至少三個角色協同 運作，各自可能就是一個獨立的容器。如果每次都要手動 打好幾行docker run，還得自己確保連接埠、 網路設定彼此對得起來，非常繁瑣又容易出錯——這正是 Docker Compose要解決的問題。

1. 問題：多容器應用程式的手動管理很痛苦

假設一個應用程式需要網頁伺服器、應用程式伺服器、 資料庫三個容器，每次啟動都要記得三個容器各自的映像檔 名稱、連接埠對應、環境變數設定，還要確保啟動順序 （資料庫最好先準備好，應用程式伺服器才連得上），並且 手動設定好讓這幾個容器能互相通訊的網路——只要有一個 環節記錯或打錯指令，整個應用程式就啟動不起來。

2. Docker Compose：用一份YAML宣告整組服務

Docker Compose讓你把一個多容器應用程式 需要的所有服務，寫進一份宣告式的YAML設定檔——習慣上 命名為docker-compose.yml。每個服務 （service，通常對應一個容器）分別描述要用哪個映像檔 （或是從哪個Dockerfile建置）、開放哪些連接埠、需要哪些 環境變數，以及跟其他服務之間的依賴關係，接著用一個 指令就能把整組服務一次啟動起來。

3. 完整範例：拆解docker-compose.yml

以下是一份對應模組J三層式架構的簡化範例：網頁伺服器 （web）、應用程式伺服器（app，從本地Dockerfile建置）、 資料庫（db，直接使用官方PostgreSQL映像檔）：

services: web: image: nginx:alpine ports: - "8080:80" volumes: - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro depends_on: - app app: build: ./app environment: - DB_HOST=db - DB_PORT=5432 depends_on: - db db: image: postgres:16 environment: - POSTGRES_PASSWORD=examplepassword - POSTGRES_DB=myappdb volumes: - db-data:/var/lib/postgresql/data volumes: db-data:

逐段拆解：services底下的web、 app、db各自是一個服務（容器）； web直接使用官方nginx:alpine 映像檔，把主機8080埠對應到容器80埠，並掛載一份本地的 nginx設定檔進容器裡；app則用build: ./app指定從./app目錄底下的 Dockerfile現場建置映像檔，並透過environment 設定連往資料庫需要的連線資訊；db使用官方 postgres:16映像檔，用環境變數設定資料庫 密碼與預設建立的資料庫名稱，並透過volumes 把資料庫實際的資料檔案，掛載到最下方宣告的具名資料卷 （volume）db-data裡，讓資料庫的資料不會 因為容器被刪除而跟著消失；depends_on則 描述服務之間的啟動依賴順序（例如app依賴 db）。

小提醒：現代Compose不再需要version欄位

早期的docker-compose.yml檔案，通常會在最上方寫一行 version: "3.9"指定格式版本——現行的 Docker Compose規格已經不再需要這個欄位，直接從 services開始寫即可，這也是上面範例省略 它的原因。

4. 啟動與關閉整組服務

docker compose up docker compose up -d docker compose down

在docker-compose.yml所在的目錄下執行docker compose up，會依序建置（如果需要）並啟動設定檔 裡定義的所有服務；加上-d則跟 docker run -d一樣，讓所有容器在背景執行。 要停止並移除這組服務時，執行docker compose down 即可一次清乾淨——不需要再一個個手動 stop、rm。

5. 服務發現：容器之間怎麼靠「名字」互相找到對方

Compose有一個很方便的內建行為：預設會替同一份 docker-compose.yml裡的所有服務，建立一個共用的虛擬 網路，並提供類似DNS的服務發現機制（呼應模組G第30課 DNS解析的概念，只是這裡的「域名」就是服務名稱，範圍 僅限於這個Compose網路內部）——容器可以直接用其他服務 的服務名稱當作主機名稱來連線，不需要 知道對方實際的IP位址。像上面範例裡，app 服務只要連到db:5432，Compose內建的DNS就會 自動把db解析成資料庫容器目前的IP——即使 容器重啟後IP位址改變，服務名稱仍然有效。

檢查你的理解

  1. 能說出Docker Compose相較於手動下多個docker run指令，解決了哪些具體問題
  2. 能解釋同一份docker-compose.yml裡的容器，如何用服務名稱互相連線
  3. 能說出docker compose up -d與docker compose down各自的作用
