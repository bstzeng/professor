解析LLM回傳的JSON

這一課的目標

  • 理解為什麼「要求LLM輸出JSON」不保證拿到的一定是乾淨的JSON
  • 能辨識常見的輸出污染樣式，尤其是markdown程式碼框
  • 能寫出一段n8n Code節點的JavaScript，清理污染並安全地解析成JSON

第35課讓System Prompt明確規定LLM只能輸出JSON，理論上 問題就解決了。但實際跑起來會發現，地端模型（尤其是 參數量較小、經過量化的模型，回顧第7課的取捨）並不會 百分之百乖乖照規則做。這一課要處理的，是這個「理論 跟實務有落差」的縫隙。

1. 為什麼「叫模型輸出JSON」不保證拿到乾淨的JSON

LLM的訓練資料裡有大量技術文件、程式教學，這些內容習慣 把程式碼片段包在markdown的三個反引號程式碼框裡。就算 System Prompt明確禁止額外文字，模型有時還是會「習慣性」 把JSON包進```json ... ```裡，或是在JSON 前後加一句「以下是分類結果：」之類的說明。模型的參數量 越小，這種不遵守指令的情況通常越常見。

2. 常見的污染樣式

  • markdown程式碼框——回覆被包成 ```json\n{...}\n```或單純 ```\n{...}\n```
  • 前導或結尾的說明文字——例如「這封信 的分類結果如下：」加在JSON前面，或「希望這對你有幫助」 加在JSON後面
  • 多餘的換行或空白——單獨不影響 JSON.parse()，但常常跟前兩種問題一起出現

如果不處理這些污染，直接對整段回應做 JSON.parse()會直接丟出例外，整個工作流 執行到這一步就會中斷。

3. 解法：用Code節點清理並安全解析

在LLM節點後面接一個Code節點，寫一小段 JavaScript，先把可能的markdown框跟多餘文字清掉，再嘗試 解析，並用try/catch包起來避免解析失敗直接 炸掉整個流程：

// Code節點：清理並解析LLM回傳的文字 const raw = $input.first().json.response; // Ollama回傳的原始文字欄位 // 去掉```json、``` 這類markdown程式碼框標記 const cleaned = raw .replace(/```json/gi, '') .replace(/```/g, '') .trim(); let parsed; try { parsed = JSON.parse(cleaned); } catch (err) { // 解析失敗時，不要讓整個工作流中斷， // 改成回傳一個帶有錯誤標記的固定結構 parsed = { category: 'unknown', urgent: false, summary: '解析失敗，原始回應：' + raw.slice(0, 80) }; } return { json: parsed };

這裡的.replace()用正則表達式把 ```json跟```兩種標記都去掉， 不管模型是用哪一種包法；.trim()清掉頭尾 多餘的空白與換行。就算模型在JSON外面多加了幾句說明， 更嚴謹的做法還可以用正則表達式擷取第一個 {到最後一個}之間的內容， 再交給JSON.parse()。

4. 更輕量的做法：直接在表達式裡處理

如果污染樣式很固定（例如模型幾乎每次都只用同一種 markdown框），也可以不用整個Code節點，改在Set節點的 欄位裡直接寫n8n表達式，用JavaScript字串方法處理，例如 {{ $json.response.replace(/```json|```/g, '').trim() }}。 但這種寫法沒有try/catch，一旦格式跟預期 不一樣，表達式本身就會報錯。實務上只要輸出格式不是 百分之百穩定，用Code節點寫完整的防呆邏輯，會比塞在 單一表達式裡可靠得多。

小提醒：這裡先做「基本防呆」，完整的錯誤處理在模組K

這一課的try/catch只是先確保解析失敗時 流程不會直接中斷，先給一個安全的預設值。至於「解析 失敗之後該怎麼辦」——要不要重試、要不要通知人工介入—— 屬於更完整的錯誤處理策略，會在模組K詳細討論。

檢查你的理解

  1. 說明為什麼就算System Prompt明確要求輸出純JSON，實務上還是可能拿到不乾淨的回應
  2. 寫出用Code節點清理markdown程式碼框並安全解析JSON的基本邏輯
  3. 解釋為什麼用try/catch包住JSON.parse()，比讓它直接丟出例外更適合放進工作流
