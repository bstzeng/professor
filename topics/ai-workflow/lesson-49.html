模組 L｜RAG基礎 · 第 49 課

向量資料庫是什麼

這一課的目標

  • 理解向量資料庫解決的問題：儲存大量嵌入向量，並快速找出跟查詢最相似的幾筆
  • 理解為什麼一般的傳統資料庫不擅長做這件事
  • 認識兩個適合搭配地端優先架構的向量資料庫選項：Qdrant與Postgres＋pgvector

上一課把文件切成chunk、再把每個chunk轉換成嵌入向量。 這一課要問：這些向量最後存放在哪裡？當文件數量從幾份 變成幾千份，chunk的數量可能上看數萬筆，要在這麼多向量 裡即時找出「跟這次問題最相似的幾筆」，需要的是一種 專門為這件事設計的資料庫。

1. 為什麼傳統資料庫不擅長做這件事

傳統的關聯式資料庫（回顧模組J第42課串接資料庫），擅長 的是精確比對——某個欄位等不等於某個值、某個日期是否 落在某個區間。但向量相似度搜尋要問的問題完全不同： 「在這幾萬組向量裡，哪幾組跟這一組查詢向量的數學距離 最近」。這種「最近鄰搜尋」（nearest-neighbor search） 如果對每一筆資料都逐一計算距離再排序，資料量一大就會 非常慢，沒辦法做到即時查詢。

2. 向量資料庫：專門為相似度搜尋設計

向量資料庫（vector database）就是為了 解決這個效能問題而生的資料庫類型。它的核心工作是： 儲存大量的嵌入向量（通常還會附帶一些中繼資料，例如這 個向量對應到原始文件的哪一段內容），並且透過專門的 索引結構，讓「找出跟查詢向量最相似的N筆」這件事，即使 面對數萬、數十萬筆資料，也能在很短的時間內完成，而不 需要逐一比對。對RAG來說，向量資料庫扮演的角色，就是 第47課提到的「檢索」步驟實際發生的地方——查詢時，先把 問題轉成向量，再拿這組向量去向量資料庫裡搜尋最相似的 chunk。

// 概念示意：向量資料庫裡一筆記錄大致長這樣 { "id": "退換貨政策-chunk3", "vector": [0.0213, -0.1147, 0.0892, ...], "text": "退貨申請須於收到商品後七天內提出，商品需保持全新未拆封狀態。", "metadata": { "source": "退換貨政策.pdf", "chunk_index": 3 } }

除了向量本身，通常還會一併存下原始的chunk文字內容跟 一些中繼資料（來源文件、chunk編號），這樣查詢時找到 最相似的向量後，才能直接拿回對應的文字內容，交給LLM 參考——這也是第53課組Prompt時，實際會用到的資料。

3. 幾個適合地端優先架構的選項

向量資料庫的產品選項不少，這裡先介紹兩種在地端優先、 又能跟n8n這類工作流平台搭配的方向，模組M實作時會再回頭 挑一種具體動手：

  • Qdrant——一套開源、可以自行架設在 自己伺服器上的向量資料庫，專門為向量相似度搜尋設計， 是自架（self-hosted）向量資料庫裡相當熱門的選項，跟 這門課「資料留在自己環境裡」的方向一致
  • Postgres＋pgvector——如果團隊本來 就已經在用PostgreSQL（回顧第42課串接資料庫），可以 安裝pgvector這個擴充套件，讓既有的 Postgres資料庫額外具備儲存向量、執行相似度搜尋的 能力，不需要另外架設一套獨立的資料庫系統

這兩者只是眾多選項中的兩種方向性介紹；n8n目前對特定 向量資料庫的節點支援情況會持續演進，實際串接方式會在 模組M第52課具體討論，這裡先建立「向量資料庫是什麼、 大致有哪些類型的選項」這個概念即可。

檢查你的理解

  2. 用自己的話解釋向量資料庫在RAG流程裡扮演的角色
