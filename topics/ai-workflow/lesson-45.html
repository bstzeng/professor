模組 K｜錯誤處理與流程穩定性 · 第 45 課

n8n的錯誤處理節點與重試機制

這一課的目標

  • 認識n8n節點層級的「失敗後重試」設定，以及它適合解決哪一類問題
  • 認識Error Trigger工作流的概念，理解它怎麼做到集中式的失敗通知
  • 學會設計一個「JSON解析失敗就轉人工review」的備援分支，取代讓整個執行直接中斷

上一課列出了地端LLM工作流特別容易遇到的三種失敗情境： 回應變慢、JSON格式不穩定、Ollama服務暫時無回應。這一課 具體看n8n提供了哪些機制，來讓工作流在遇到這些情況時， 不會就這樣整個崩潰。

1. 節點層級的重試：Retry On Fail

n8n的每個節點，在設定畫面裡都有一組跟錯誤處理相關的 選項，其中最基本的是「失敗後自動重試」——啟用之後， 節點執行失敗時不會立刻判定整個執行失敗，而是依照設定 的次數（例如重試3次），每次間隔一段等待時間，重新嘗試 執行同一個節點，全部重試完仍然失敗，才真正視為失敗。

這個機制特別適合處理暫時性的問題——例如 Ollama伺服器當下正忙、一次網路請求剛好逾時。重試一兩次， 很可能第二次就順利拿到回應了。但要注意，重試機制解決 不了「每次都會發生」的問題——如果LLM是因為Prompt設計 不良，導致每次輸出格式都不對，重試再多次，結果通常還是 一樣，這種情況需要的是修正Prompt（回顧模組H），而不是 單純重試。

2. Error Trigger工作流：集中處理失敗通知

如果每個工作流都要各自寫一套「失敗了要怎麼通知」的 邏輯，會非常重複。n8n提供了另一個層級的機制：可以另外 建立一個獨立的工作流，以Error Trigger 節點作為觸發點，再到原本的工作流設定裡，指定這個獨立 工作流作為它的「錯誤處理工作流」。這樣一來，只要原本 的工作流執行失敗（包含重試次數用盡之後仍然失敗）， n8n就會自動觸發這個指定的錯誤處理工作流，並把是哪個 工作流、哪一次執行、失敗訊息是什麼，一併傳遞過去。

這種設計的好處是集中化——不管公司內部 有幾十個不同的自動化流程（信件分類、試算表同步、資料庫 寫入……），全部都可以指向同一個錯誤處理工作流，由它統一 負責發Slack通知、寄信給管理員，不需要在每個流程裡各自 重複實作一次通知邏輯。

3. Fallback邏輯：解析失敗就轉人工review

重試與集中通知，處理的是「讓相關的人知道流程失敗了」。 但有一種情況更適合用不同的方式處理：回顧第36課解析 LLM回傳的JSON，如果某一筆資料的LLM輸出剛好格式不對、 解析失敗，與其讓整個執行直接中斷、等人去後台翻執行 紀錄，不如把「解析失敗」本身當成一種正常會發生的分支， 自動把這筆資料寫進一個給人工複查用的地方，讓自動化流程 本身可以繼續往下處理其他正常的項目。

具體做法：在解析JSON的節點之後，用IF節點檢查解析是否 成功；成功的項目照原本的路徑繼續走（分流、寫入資料庫、 寄信……）；失敗的項目則走另一條分支，把原始的LLM輸出、 錯誤訊息、時間戳記，寫進第40課介紹過的Google試算表裡 另外開的一個「待人工複查」分頁，必要時再搭配第41課的 Slack通知，提醒有人要去看一下。

// Code節點：嘗試解析LLM輸出的JSON，失敗就標記起來 try { const parsed = JSON.parse($input.item.json.llmOutput); return { json: { ...parsed, parseOk: true } }; } catch (err) { return { json: { raw: $input.item.json.llmOutput, parseOk: false, errorMessage: err.message } }; }

後面接一個IF節點，條件設為parseOk是否等於 true：符合的項目走「繼續自動化」分支， 不符合的項目走「寫入待複查分頁」分支。這樣即使某幾筆 資料的LLM輸出有問題，也只是那幾筆被攔下來，不會拖垮 整批資料的處理。
