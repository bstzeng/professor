模組 K｜錯誤處理與流程穩定性 · 第 46 課

模組總結：讓工作流在失敗時不會整個中斷

這一課的目標

  • 整合模組K的三個機制，理解它們各自解決什麼問題、怎麼互相搭配
  • 回顧這些機制怎麼讓模組G到J做出來的旗艦流程更有韌性
  • 銜接模組L：RAG——一個跟錯誤處理不同、但同樣重要的新能力

模組K只有兩堂正課，但補上了一塊之前完全沒處理過的 缺口：模組G到J一路做出來的信件自動化旗艦流程，到目前 為止都假設LLM步驟會順利完成。這一課把第44、45課的內容 收斂成一套完整的觀點，看看「讓流程在失敗時不會整個 中斷」實際上是怎麼一回事。

為什麼地端LLM特別需要這一塊：第44課的核心

第44課的重點是一個對比：雲端LLM API的高可靠度，建立在 供應商大規模的基礎設施之上；把LLM換成地端的Ollama， 代表這份「穩定性工程」有一部分責任，轉移到工作流設計者 自己身上。具體要多考慮的，是回應變慢、JSON格式偶爾不 穩定、Ollama服務本身可能暫時無回應這三種情境。這不是 否定地端路線，而是認清這是選擇地端優先（回顧第2課）時 真實存在的取捨。

三層機制：從自動修復到人工介入

第45課具體介紹了n8n因應這些情境的三個機制，它們其實是 按照「處理成本」由低到高排列的三層防線：

  1. 節點層級重試（Retry On Fail）—— 第一線防線，自動處理暫時性的失敗，多數時候問題就在 這一層被悄悄解決，不需要驚動任何人
  2. Error Trigger工作流——重試也救不回來 時的集中通知機制，讓管理者知道「有事情需要人去看」， 而不用在每個工作流裡各自重複實作通知邏輯
  3. 人工複查備援分支——針對「解析失敗」 這種可預期會偶爾發生的情況，讓自動化流程本身可以繼續 往下跑，只把有問題的少數項目攔下來，交給人事後處理
// 第45課備援分支的核心邏輯，濃縮回顧 try { const parsed = JSON.parse(llmOutput); // 解析成功 → 交給IF節點判斷parseOk，繼續原本的自動化路徑 } catch (err) { // 解析失敗 → 寫入「待人工複查」分頁，流程本身繼續處理下一筆 }

目的：韌性，不是完美

模組K的三個機制，目標不是讓工作流永遠不出錯——那不 現實。目標是讓「出錯」這件事，不會演變成整個流程整批 停擺、需要有人手動去救。旗艦的信件自動化流程，經過 模組K補強之後，即使某一筆信件的LLM輸出剛好不理想， 其他信件依然能正常被處理完，出問題的那一筆也不會被 悄悄遺失，而是被明確地記錄下來、等人複查。

接下來：從「處理失敗」轉向「補齊能力」

模組K讓既有的流程更穩固，模組L要換一個方向——補上一項 現有流程完全沒有的能力：讓LLM能夠參考你自己的私有文件 來回答問題，而不是只能依賴訓練時學到的通用知識。這個 技術叫RAG（Retrieval-Augmented Generation，檢索增強 生成），模組L先從概念開始，模組M再回到n8n裡動手實作。

檢查你的理解

  1. 能說出模組K的三層機制分別是什麼，以及它們的先後順序邏輯
  2. 能解釋為什麼這三層機制合起來，是在追求「韌性」而不是「零錯誤」
  3. 能說明模組L要補上的能力，跟模組K處理的問題有什麼本質上的不同
