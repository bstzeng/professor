模組 H｜資料前處理與Prompt設計 · 第 34 課

模組總結：讓Prompt能重複套用在不同輸入上

這一課的目標

  • 完整回顧模組H做的三件事：拆解問題、整理輸入資料、分工設計Prompt
  • 確認現在的工作流已經能處理「任何一封信」，不再侷限於單一測試案例
  • 銜接模組I：LLM的回應還是一段文字，接下來要讓它輸出結構化JSON

模組H從第31課點出「Prompt寫死」這個問題開始，到第32、 33課動手解決它，這一課回頭把整個過程串起來看，確認 現在的工作流已經具備什麼能力，也老實面對還剩下什麼 問題。

模組H完成了什麼

第31課先講清楚了道理：Prompt應該拆成固定不變的指示 文字，加上用n8n表達式動態帶入的佔位符，才能讓同一份 設定套用在每次執行都不同的輸入資料上。第32課動手把 這個道理落實在資料層——用Set節點把觸發器原始輸出， 整理成subject、body、 sender這幾個乾淨一致的欄位，隔開了上游 資料格式的變動跟下游Prompt模板之間的依賴。第33課則 把Prompt本身依照職責拆成兩層：System Prompt定義固定 不變的角色、分類標準、輸出格式；User Prompt用表達式 帶入這一次要處理的信件內容。三課合起來，解決的是同一 個核心問題——讓Prompt從「只服務一筆測試資料」變成 「能重複套用在任何輸入上」。

// 模組H完成後，整套Prompt設計的骨架 System Prompt（固定不變）：角色設定＋分類標準＋輸出格式規定 User Prompt（模板）： 主旨：{{ $json.subject }} 內文：{{ $json.body }} 寄件人：{{ $json.sender }}

還剩下什麼問題：輸出仍然只是一段文字

即使現在Prompt已經能處理任何一封信，第29課看到的那種 輸出——「這封信件屬於「客訴」類型……」——本質上還是一 段給人類閱讀的自然語言文字。就算第33課的System Prompt 已經要求LLM用「類型：……／摘要：……」這種較固定的格式 回覆，這仍然只是一段文字，工作流裡的IF、Switch節點 沒辦法可靠地從一段自由格式的文字裡，抓出「類型到底是 客訴還是詢問」這個關鍵資訊來做條件判斷——文字格式稍微 有一點點不一致（多一個空格、多一句客套話），程式化的 字串比對就可能失敗。

下一步：讓LLM直接輸出結構化資料

模組I要解決的正是這個問題：要求LLM直接輸出成JSON這種 結構化格式，例如{"category": "客訴", "summary": "……"}，工作流才能用程式邏輯可靠地讀出 category欄位的值，並依照這個值做條件 分流——這也是這門課旗艦專案第26課藍圖裡，「結構化 JSON」跟「條件分流」這兩段要補上的部分。

檢查你的理解

  1. 依序說明模組H第31、32、33課，各自解決了「Prompt寫死」這個問題的哪一部分
  2. 解釋為什麼即使System Prompt已經規定了回覆格式，輸出仍然不算是結構化資料
  3. 說明為什麼工作流裡的條件判斷節點難以可靠地處理自由格式的文字輸出

下一課預告

模組I從下一課開始：先談為什麼要讓LLM輸出結構化的JSON 資料，而不是一段自然語言文字，這會是讓這個工作流真正 從「回答問題」進化到「做決策」的關鍵一步。
