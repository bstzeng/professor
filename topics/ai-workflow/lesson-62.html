n8n的執行紀錄與除錯畫面

這一課的目標

  • 認識n8n的Executions（執行紀錄）列表，以及每筆紀錄顯示的執行狀態
  • 能點進單次執行紀錄，逐一檢視每個節點實際收到、送出的資料
  • 理解執行紀錄為什麼是排查無人值守工作流問題的第一站

模組O把工作流變成能靠排程、Webhook自動觸發、不需要人 手動啟動的系統，但這也代表每一次執行，都可能沒有任何人 親眼看著它跑。這一課要介紹n8n介面裡的Executions （執行紀錄）列表——這是回頭檢視「這個工作流過去 每一次到底跑了什麼」最主要的工具，尤其對排程、Webhook 觸發的無人值守流程來說特別重要。

1. Executions列表：每一次執行的歷史紀錄

n8n主畫面提供一個Executions列表，會列出這個工作流（或 整個n8n實例）過去每一次被執行的紀錄，每一筆通常包含 觸發時間、耗費的時間、以及最關鍵的執行狀態 ——常見狀態包括Success（成功執行完畢）、 Error（執行過程中發生錯誤而中斷）、以及 執行中或等待中的狀態。只要工作流被排程或Webhook觸發過 至少一次，這裡就會累積出對應的紀錄，不需要額外設定 什麼記錄機制。

2. 點進單次執行：逐節點檢視實際資料

列表本身只能看到「成功還是失敗」這種概略資訊，真正有 除錯價值的是點進某一筆具體的執行紀錄 之後看到的畫面：n8n會用當初那次執行實際跑過的畫布狀態 重現一次，讓你可以逐一點擊每個節點，檢視這個節點在那次 執行裡，實際收到的輸入資料與實際產生的 輸出資料（回顧模組E談過的JSON資料結構， 這裡看到的正是實際流動的JSON內容）。如果某個節點在那次 執行中失敗了，這個節點通常會被明顯標示出來，點開後能看到 實際的錯誤訊息。

// 例如點開「Ollama聊天模型」節點，看到的輸入資料 { "prompt": "請判斷這封信件的分類與緊急程度……", "model": "llama3.1:8b" } // 這個節點失敗時，對應看到的輸出／錯誤訊息 { "error": "Request timed out after 30000ms", "node": "Ollama Chat Model" }

3. 為什麼這對無人值守流程特別重要

有人手動執行、盯著畫面跑的工作流，出問題時至少當下能 親眼看到是哪個節點卡住、回傳了什麼；但排程半夜自動跑、 或是Webhook在你不在電腦前時被觸發的流程，唯一能重建 「當時到底發生了什麼」的依據，就是這份執行紀錄。這也是 為什麼模組O完成排程與Webhook之後，緊接著要學會查看 執行紀錄——工作流開始無人值守運作的那一刻起，執行紀錄 就變成排查問題唯一可靠的第一手資料，而不只是開發階段 用來偵錯的輔助工具。

小提醒：留意執行紀錄的保留設定

n8n通常可以針對執行紀錄的保留期限、保留筆數做設定 （尤其是自架的n8n，這類設定會影響資料庫的儲存空間）。 排程頻繁執行的工作流，如果需要回頭追溯較久之前的執行 狀況，記得確認保留設定是否足夠，避免真正需要的那筆 紀錄已經被清掉。

檢查你的理解

  1. 說明Executions列表能看到哪些概略資訊，以及點進單筆執行紀錄後能看到什麼更詳細的內容
  2. 解釋失敗節點在執行紀錄畫面裡，通常會怎麼被標示出來
  3. 說明為什麼執行紀錄對排程、Webhook這類無人值守觸發的流程特別重要
