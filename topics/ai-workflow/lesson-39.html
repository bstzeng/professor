串接Email：讀取與寄送

這一課的目標

  • 理解為什麼要從測試用的手動觸發器，換成真正輪詢收件匣的Email Trigger（IMAP）節點
  • 能設定IMAP憑證與輪詢間隔，讓工作流對真實寄來的信件自動啟動
  • 認識選用的Send Email（SMTP）節點，知道它適合用在什麼情境

模組I把分類、解析、分流的邏輯都設計好了，但整條工作流 目前的起點，還是第27課為了方便測試而用的手動觸發器—— 每次都要自己按一下才會執行。這一課要把起點換成真正 會自動運作的觸發方式：讓n8n自己去收信匣裡看有沒有新信。

1. 從手動觸發，換成Email Trigger（IMAP）

第27課用手動觸發器（或Webhook配合手動呼叫）在開發階段 方便重複測試，不用等真的有信件寄來才能驗證邏輯對不對。 但正式上線後，工作流不可能靠人一直按觸發按鈕。這裡要 換上Email Trigger（IMAP）節點——它會 用IMAP協定連上指定的信箱，定期檢查有沒有新信件，一旦 發現新信，就自動啟動整個工作流，把那封信的內容當成 輸入資料往下傳。

2. 設定IMAP憑證

Email Trigger節點需要一組IMAP憑證才能連上信箱，通常 要填入以下幾項資訊：

Host：信箱服務商的IMAP伺服器位址（例如imap.gmail.com） Port：IMAP over SSL的常用埠號是993 User：完整的信箱帳號（例如support@example.com） Password：信箱密碼，或服務商要求的應用程式密碼 SSL/TLS：啟用（避免帳密與信件內容以明文傳輸）

許多信箱服務商（例如Gmail）在啟用兩步驟驗證後，不允許 直接用登入密碼透過IMAP連線，這時候需要另外產生一組 專用的應用程式密碼，用那組密碼設定這裡的憑證，而不是 帳號本身的登入密碼。

3. 輪詢間隔（Polling Interval）

Email Trigger節點是用「輪詢」的方式運作：每隔一段固定 時間，就連上信箱檢查一次有沒有新信件（而不是信箱主動 推播）。輪詢間隔設得越短，新信件被處理的延遲就越低， 但也代表對信箱伺服器發出的檢查請求越頻繁；設得太長， 則客訴信件可能要等好一段時間才會被工作流看到、進而 觸發第41課的緊急通知。實務上通常會設定在一到五分鐘之間， 依信件的緊急程度需求調整。

4. 觸發後拿到的資料欄位

Email Trigger節點觸發之後，會把這封信的內容整理成JSON 資料往下傳，其中最常用到的欄位包含寄件者、主旨、內文 等。這些欄位就是第32課用Set節點整理輸入資料時的原始 材料——換句話說，模組H處理的「輸入資料」，從這一課 開始，真正變成了從信箱裡讀出來的真實信件，而不是測試 用的假資料。

// Email Trigger節點輸出的欄位，在後續節點裡可以這樣取用 {{ $json.from }} // 寄件者信箱 {{ $json.subject }} // 信件主旨 {{ $json.text }} // 純文字內文

5. 選用：用Send Email（SMTP）節點自動回覆寄件者

除了讀信，n8n也有對應的Send Email（SMTP） 節點，可以在工作流裡寄出信件。這個專案可以選擇性地加上 一個自動回覆：不管信件分類結果是什麼，都先用SMTP節點 回一封「已收到您的來信，我們會盡快處理」給寄件者，讓 對方知道信件確實有被系統接收到。SMTP節點同樣需要一組 憑證：

Host：信箱服務商的SMTP伺服器位址（例如smtp.gmail.com） Port：常見為465（SSL）或587（TLS／STARTTLS） User／Password：與寄件信箱對應的帳密或應用程式密碼

要注意的是，如果信件被分類為spam，通常不會 希望對垃圾信也自動回覆——這一點的分支設計，會在後面 跟Switch節點的輸出一起考慮，不是所有分類都適合套用同一種 自動回覆邏輯。
