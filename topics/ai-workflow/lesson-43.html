模組 J｜串接外部系統 · 第 43 課

模組總結：完整的端到端自動化流程

這一課的目標

  • 完整回顧從Email Trigger到Slack通知，整條工作流每一段各自做了什麼
  • 看懂一張涵蓋整個工作流的完整端到端流程圖
  • 理解這套流程目前還缺少什麼，並知道下一模組要解決的問題

從第26課設定情境開始，經過模組G打通第一次觸發到AI回應 的迴路、模組H把Prompt模板化、模組I讓AI輸出變成結構化 決策，到這個模組把分支真正接上信件、試算表、Slack、 資料庫——現在，這套「自動分類並路由客服信件」的工作流， 已經是一個能真正端到端運作的系統了。這一課是一個 milestone：完整走一遍整條流程，畫出全貌，也誠實地看看 還缺了什麼。

完整走一遍：從一封新信到一則Slack通知

一封新的客戶來信，會依序經過以下幾個階段。第39課 的Email Trigger（IMAP）節點輪詢信箱，發現新信後 自動啟動工作流；模組H的Set節點把主旨、 內文、寄件者這些原始欄位整理成乾淨的輸入；模組F 接上的LLM節點依照第33、35課設計的 System Prompt，對這份輸入做分類，輸出固定 schema的JSON；第36課的Code節點清理可能 的markdown污染，安全解析成乾淨的物件；第37課 的Switch／IF節點依照category跟 urgent兩個欄位分流；不管走哪條分支， 第40課的Google Sheets節點都會先把這封 信記錄成稽核紀錄的一列（信件量夠大時，第42課的 資料庫節點可以並存或取代這一步）；只有被判定為 「客訴且緊急」的信件，才會繼續觸發第41課的Slack 節點，發出一則帶有寄件者與摘要的即時通知。

// 每一封信最終會產生的結構化判斷結果， // 是驅動這整條流程走向的唯一依據 {"category": "complaint", "urgent": true, "summary": "顧客反應包裹延遲送達"} // category + urgent 這兩個欄位，同時決定了： // 1. 是否走進「客訴」分支（category） // 2. 是否額外觸發Slack通知（urgent） // summary 欄位則被同時寫進試算表與Slack訊息內容

這套流程還缺了什麼：如果LLM掛掉、逾時、回傳亂七八糟的東西呢

這條流程在「一切順利」的情況下已經能完整運作，但目前 每一步都預設LLM會準時、正確地回應。實際部署地端LLM時， 至少有三種情況目前完全沒有被處理：LLM節點呼叫 逾時（模型正在處理別的請求、或這台機器 資源不夠，回應時間拖得太久）；LLM節點本身 失敗（Ollama服務沒開、模型沒載入、 連線被拒絕）；以及就算有第36課的清理與 try/catch防呆，仍然解析失敗 （模型輸出的內容連基本結構都不對，清理邏輯也救不回來）。 目前這三種情況發生時，工作流要嘛直接中斷、要嘛只是悄悄 寫進一筆category: "unknown"的紀錄，沒有人 會知道有信件其實沒有被正確處理。

銜接模組K：從「能動」到「動得穩」

模組G到J做的事，是讓這套系統在正常情況下能完整跑 完一輪；模組K要處理的，是「不正常情況」——當某個環節 失敗時，工作流該怎麼重試、該怎麼通知人工介入，而不是 讓整個流程默默壞掉、或是把錯誤的資料當成正常資料處理。 這是把一套「能動」的自動化，變成一套「動得穩」的自動化 必經的一步。
