監控地端LLM的資源使用狀況

這一課的目標

  • 會用ollama ps檢查目前有哪些模型被載入記憶體、各佔用多少空間
  • 認識作業系統層級可以用來監控CPU／GPU資源的工具，依平台各自對應
  • 能辨認地端LLM資源吃緊時，實際會出現的幾種徵兆

上一課的執行紀錄，能回答「n8n裡每個節點收到、送出了什麼 資料」，但如果問題出在AI這一步本身——回應異常慢、甚至 整個沒有反應——執行紀錄能看到的只是「這個節點花了很久」 或「逾時失敗」，真正的原因往往要回到Ollama、回到執行 模型的那台機器本身去查。這一課要介紹幾個檢查地端LLM 資源使用狀況的實際工具。

1. ollama ps：查看目前載入記憶體的模型

Ollama提供一個很直接的指令，列出目前有哪些模型被載入 記憶體、正在佔用資源：

$ ollama ps NAME ID SIZE PROCESSOR UNTIL llama3.1:8b a1b2c3d4e5f6 5.4 GB 100% GPU 4 minutes from now

輸出的每一欄各自透露不同的資訊：NAME是目前 載入的模型名稱；SIZE是這個模型實際佔用的 記憶體大小；PROCESSOR顯示這個模型主要是靠 GPU還是CPU在跑（呼應第7課提過的硬體門檻取捨——同一個 指令，就能直接確認模型有沒有吃到GPU加速，還是退回較慢的 CPU運算）；UNTIL則是這個模型還會在記憶體裡 停留多久——Ollama預設會在一段閒置時間後，自動把沒有在 使用的模型從記憶體釋放掉，避免長期佔用資源。如果這裡 完全沒有任何一行輸出，代表目前沒有任何模型被載入記憶體。

2. 作業系統層級的監控：CPU、記憶體、GPU用量

ollama ps能看到「哪個模型佔了多少」，但要 看整台機器當下的資源使用全貌（包括n8n本身、以及其他 同時在跑的程式），需要搭配作業系統提供的監控工具，依 平台各自不同：

  • macOS——內建的活動監視器 （Activity Monitor），可以看CPU、記憶體、 （部分機型）GPU的即時使用率
  • Windows——內建的工作管理員 （Task Manager），效能頁籤同樣能看到CPU、 記憶體、GPU的使用狀況
  • Linux——終端機工具 htop能看CPU與記憶體的即時使用率 （通常需要另外安裝）；如果是Nvidia GPU， nvidia-smi能查看GPU的 使用率與顯示記憶體（VRAM）佔用狀況，這對確認地端LLM 有沒有確實吃到GPU加速特別有用
# Linux：檢查CPU／記憶體整體使用狀況 $ htop # Linux：檢查Nvidia GPU使用率與顯示記憶體佔用 $ nvidia-smi

3. 資源吃緊的實際徵兆

在真正打開監控工具細查之前，有幾個實務上常見、值得留意 的徵兆，通常暗示地端LLM正承受資源壓力：

  • 回應明顯比平常慢——同樣長度的 prompt，平常幾秒鐘就有回應，突然變成要等上十幾秒甚至 更久，可能是CPU／GPU被其他程式搶用、或是模型被迫在CPU 與GPU之間切換
  • 請求逾時（timeout）——n8n呼叫Ollama API的HTTP Request節點（或AI節點）設定了逾時時間， 在資源吃緊、回應時間被拉長時，特別容易觸發逾時錯誤 （回顧模組K第44、45課的錯誤處理與重試機制，正是用來 應對這類狀況）
  • Ollama本身失去回應——在同時有多個 並發請求湧入、遠超機器負荷時，Ollama服務本身可能變得 遲緩甚至暫時無法回應新的請求，這種狀況常發生在排程與 Webhook剛好同時觸發多個工作流、都需要呼叫LLM的時候

小提醒：先確認徵兆，再決定要不要深查

不是每一次變慢都值得大動作排查——先用ollama ps跟作業系統監控工具快速確認一下當下的資源 狀況，如果CPU／GPU用量確實偏高、或是有多個工作流同時 在觸發，通常就能對應到剛才列出的徵兆，不需要懷疑是 n8n或prompt設計本身出了問題。
