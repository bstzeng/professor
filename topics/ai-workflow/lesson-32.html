模組 H｜資料前處理與Prompt設計 · 第 32 課

用n8n的Set節點整理輸入資料

這一課的目標

  • 理解為什麼要在送進LLM之前，先用Set節點整理成乾淨一致的欄位結構
  • 實際設定一個Set節點，把觸發器輸出的原始資料轉成subject、body、sender三個標準欄位
  • 理解這樣的中間層設計，能讓下游Prompt模板更簡單、也更能抵擋上游資料格式的變動

上一課講清楚了Prompt要模板化的道理，但模板要穩定運作， 有一個前提：每次填進佔位符的欄位值，本身要是乾淨、 名稱一致的資料。這一課要動手處理這件事——用第20課 介紹過的Set節點，在資料送進LLM節點之前，先做一層 整理。

1. 為什麼不直接把觸發器的原始輸出送進Prompt

目前開發階段用的是Manual Trigger，輸出的欄位是自己 手動定義的，看起來乾淨。但正式上線後，觸發器會換成 Email Trigger（IMAP，第27課提過），它輸出的原始資料 結構是IMAP協定本身定義的，欄位可能叫subject 、textPlain、from 這類名稱，還會夾雜其他跟分類任務無關的中繼資料（例如 郵件標頭、附件資訊）。如果Prompt模板裡的表達式直接 寫死引用這些原始欄位名稱，一旦之後觸發器設定調整、 或欄位命名跟預期不同，所有引用到這些欄位的地方都要 跟著改。更穩健的做法，是在觸發器跟LLM節點之間，加一層 專門負責「翻譯」的Set節點。

2. 設定Set節點：只留下需要的三個欄位

在畫布上，於觸發器後面加入一個Set節點，設定它輸出三個 統一命名的欄位，值分別用表達式引用觸發器輸出裡對應的 原始欄位：

// Set節點的欄位設定 subject = {{ $json.subject }} body = {{ $json.textPlain }} sender = {{ $json.from }}

這裡刻意把Set節點輸出的欄位名稱（subject、 body、sender）跟原始觸發器 欄位名稱（subject、textPlain、 from）分開來看待，即使剛好同名也一樣視為 獨立的一層——重點是下游所有節點，包括Prompt模板，從此 只需要認得這三個固定名稱，不用關心它們背後實際來自 哪一種觸發器、哪一種原始欄位命名方式。

提醒：記得只留需要的欄位

n8n的Set節點通常可以選擇是否保留其他未特別設定的 原始欄位。這個場景建議只保留整理過的這幾個乾淨欄位， 捨棄用不到的郵件標頭、附件等原始中繼資料——這樣傳給 下游的資料結構會更精簡，Prompt模板裡也不會不小心 引用到不該用的欄位。

3. 這一層帶來的好處：Prompt模板更簡單、也更穩

有了這個乾淨的中間層，第31課提到的Prompt模板佔位符， 就可以一律用同一套簡單的欄位名稱：

// Prompt模板裡的表達式，只需要認得這三個統一欄位 主旨：{{ $json.subject }} 內文：{{ $json.body }} 寄件人：{{ $json.sender }}

往後不管觸發器換成哪一種（Manual Trigger測試、Email Trigger正式上線），只要在Set節點這一層更新對應的原始 欄位引用，Prompt模板本身完全不用動。這是軟體設計裡常見 的「加一層間接層」的思路，在n8n工作流裡也同樣適用。

檢查你的理解

  1. 說明為什麼不建議讓Prompt模板直接引用觸發器的原始欄位名稱
  2. 寫出Set節點把觸發器輸出轉換成subject、body、sender三個欄位的設定方式
  3. 解釋這種「加一層Set節點」的做法，如何讓工作流更能抵擋上游資料格式的變動
