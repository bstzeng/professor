在n8n中串接向量資料庫節點

這一課的目標

  • 知道n8n的AI／LangChain功能裡，內建了可以直接使用的向量資料庫節點
  • 理解「插入」與「查詢」這兩種基本操作模式，各自對應RAG的哪個階段
  • 理解為什麼用內建節點，比自己手刻HTTP呼叫向量資料庫API更省事

上一課讓Ollama把一段文字變成了嵌入向量，這一課要把這個 向量實際存起來、之後也能查得到。第23課提過，n8n內建了 一整組跟LangChain整合的AI節點，其中就包含專門用來串接 向量資料庫的節點，讓這一步不需要自己手刻HTTP請求去呼叫 向量資料庫的API。

1. n8n的向量資料庫節點：AI功能的一部分

n8n把跟AI相關的節點（聊天模型、嵌入模型、向量資料庫、 後面模組N會談到的Agent與工具）整合在同一套以LangChain 為基礎的功能底下。向量資料庫節點就是這套功能裡的一員， 它抽象掉了「怎麼跟特定向量資料庫的API溝通」這一層細節 ——你在節點設定裡指定連線資訊（例如Qdrant的位址，或 Postgres＋pgvector的連線設定，回顧第49課提到的選項）， 節點本身負責處理實際的插入與查詢請求。

2. 兩種基本操作：插入與查詢

向量資料庫節點的用法，基本上圍繞著兩種操作模式，分別 對應第50課講的準備階段跟查詢階段：

  • 插入（Insert）——把文件chunk連同 它的嵌入向量，寫入向量資料庫。通常會在準備階段的 工作流裡使用：讀取文件 → 切塊 → 呼叫Ollama產生嵌入 （第51課）→ 用向量資料庫節點的插入模式，把chunk文字 與向量一起存進去
  • 查詢（Query）——輸入一個嵌入向量， 回傳資料庫裡最相似的幾筆chunk。用在查詢階段的工作流 裡：使用者問題 → 呼叫Ollama把問題轉成向量 → 用向量 資料庫節點的查詢模式，取回最相關的幾個chunk

具體節點的設定欄位（例如要回傳前幾筆最相似結果，這個 參數常見的名稱類似「Top K」）會依照連接的向量資料庫 種類略有差異，這裡先掌握「插入」與「查詢」這兩種模式 的用途，實際畫面在自己的n8n版本裡動手試一次會最清楚。

// 準備階段的工作流（概念示意，非n8n原生語法） 讀取文件節點 → 切塊（Code節點或文字分割相關節點） → 呼叫Ollama嵌入（第51課，/api/embeddings） → 向量資料庫節點：插入模式 輸入：chunk文字 + 對應的嵌入向量 // 查詢階段的工作流 接收使用者問題（例如Webhook觸發） → 呼叫Ollama嵌入（同一個模型：nomic-embed-text） → 向量資料庫節點：查詢模式 輸入：問題的嵌入向量 輸出：最相似的N筆chunk文字

3. 為什麼用內建節點，而不是自己刻HTTP呼叫

回顧模組F第22到24課，比較過用HTTP Request節點手動呼叫 Ollama API，跟直接用n8n內建AI節點這兩種做法的差異。 向量資料庫這裡也是類似的取捨：自己手刻HTTP呼叫，理論 上什麼向量資料庫都能接，但要自己處理每種資料庫API格式 的細節；用內建的向量資料庫節點，好處是插入、查詢這類 常見操作已經被包裝成統一的介面，設定連線資訊之後就能 直接在工作流裡使用，不需要重新研究一次每種資料庫各自 的HTTP API規格。對這門課的實作範例來說，內建節點是 更快上手的路徑。
