串接資料庫：寫入結構化紀錄

這一課的目標

  • 理解什麼情境下資料庫會比試算表更適合當作紀錄的目的地
  • 認識n8n連接關聯式資料庫的節點，以Postgres為例，了解其基本操作
  • 知道把分類資料寫進資料庫時，資料表欄位設計要考量哪些基本原則

第40課用試算表建立了稽核紀錄，第41課讓緊急客訴多了一層 即時通知。這一課簡單補上第三種紀錄方式：資料庫。它不是 這個專案的必要條件，但當信件量成長、或有其他系統需要 查詢這份紀錄時，會是比試算表更合適的選項。

1. 試算表撐不住的時候：資料量與查詢需求

試算表在信件量不大、主要靠人回頭瀏覽的情境下很好用， 但有兩種情況會讓它開始不太夠用：一是資料量持續累積， 單一工作表存放太多列之後，開啟、篩選、計算都會變慢； 二是除了人以外，還有其他系統（例如一個內部儀表板、 另一套報表工具）需要用程式化的方式查詢這份紀錄——這種 「結構化查詢」的需求，正是關聯式資料庫的強項，而不是 試算表原本設計要處理的場景。

2. n8n的資料庫節點：以Postgres為例

n8n內建多種資料庫節點，包括Postgres、MySQL等常見的 關聯式資料庫，這裡以Postgres節點為例。 跟Google Sheets節點類似，Postgres節點也提供多種操作， 其中最常用在這個場景的是Insert （新增一列資料）——概念上跟Append Row很像，差別在於 資料寫進的是資料庫裡的一張資料表，而不是試算表的一個 工作表分頁。

3. 設定資料庫憑證與資料表欄位對應

使用前，需要先在n8n建立Postgres的連線憑證（主機位址、 埠號、資料庫名稱、帳號密碼），並在資料庫裡先建好對應的 資料表。延續第40課的欄位設計，一張最基本的紀錄表結構 大致像這樣：

CREATE TABLE email_log ( id SERIAL PRIMARY KEY, received_at TIMESTAMP, sender TEXT, category TEXT, urgent BOOLEAN, summary TEXT );

Postgres節點的Insert操作，會把前面節點傳來的欄位，逐一 對應到資料表的每一個欄位——邏輯上跟第40課Google Sheets 欄位對應的做法一致，只是這裡的received_at、 sender、category、 urgent、summary對應的是資料庫 資料表的欄位名稱，而不是試算表表頭。多出來的 urgent欄位設成布林型別，之後如果想統計 「緊急客訴佔整體信件的比例」，可以直接下SQL查詢，不需要 額外整理。

4. 試算表與資料庫可以並存，不是互斥選擇

不一定要「拿掉試算表、換成資料庫」，兩者其實可以同時 存在：試算表保留給人快速瀏覽、篩選最近的紀錄；資料庫 則作為長期、大量資料的結構化儲存，供其他系統查詢或做 進一步分析。實務上，可以在Code解析節點之後，同時接出 兩條連線——一條去Google Sheets的Append Row，一條去 Postgres的Insert，兩邊各自累積各自用途的紀錄。

檢查你的理解

  1. 說明什麼情況下，資料庫會比試算表更適合作為紀錄的目的地
  2. 寫出這個專案的紀錄資料表大致需要哪幾個欄位，以及各自的型別
  3. 解釋為什麼試算表與資料庫可以並存，而不是只能二選一
