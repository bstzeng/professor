模組 L｜RAG基礎 · 第 50 課

模組總結：RAG的完整運作流程

這一課的目標

  • 把模組L三課的概念，整合成準備階段與查詢階段兩段完整的RAG流程
  • 理解這兩個階段各自在「什麼時候」執行、執行的頻率有什麼不同
  • 銜接模組M：把這套概念，在n8n裡實際動手做出來

模組L的三課，分別看了「為什麼需要RAG」（第47課）、 「文件怎麼被切塊與轉成嵌入向量」（第48課）、「向量存 在哪裡、怎麼被搜尋」（第49課）。這一課把它們串成一條 完整的流程，並且點出一個關鍵結構：RAG其實可以拆成 時間點完全不同的兩個階段。

兩個階段：準備一次，查詢很多次

RAG看起來是一整套流程，但拆開來看，其實是兩件發生在 不同時間點的事：準備階段（ingestion） 只需要在文件加入或更新時執行一次（或定期執行），把 文件轉換成向量資料庫裡可以被搜尋的形式；查詢 階段（query）則是每一次有人提出問題時都會 執行一次，直接使用準備階段已經存好的向量資料庫，不需要 重新處理一次所有文件。這個「準備一次、查詢很多次」的 結構，是RAG之所以能做到即時回答的關鍵。

準備階段：文件 → 切塊 → 嵌入 → 存入向量資料庫

對應第48、49課的內容：先把原始文件（產品手冊、內部 SOP、合約……）切成一塊一塊的chunk，每個chunk透過嵌入 模型轉換成向量，再連同原始文字內容，一起存進向量資料庫 （例如第49課提到的Qdrant，或Postgres＋pgvector）。這個 階段通常在文件庫有新增或更新時執行，不需要每次使用者 提問都重做一次。

查詢階段：問題 → 嵌入 → 相似度搜尋 → 注入Prompt → LLM作答

對應第47課建立的RAG基本邏輯：使用者提出問題後，先把 這個問題本身也轉換成嵌入向量（用跟準備階段相同的嵌入 模型），拿這組向量去向量資料庫裡做相似度搜尋，找出 最相關的幾個chunk，把這些chunk的原始文字內容組合進 送給LLM的Prompt裡，最後由LLM根據問題本身，加上這些 剛檢索到的參考內容，生成最終的回答。

// 兩個階段合起來，濃縮回顧 準備階段（不常執行）： 文件 → 切塊（第48課） → 嵌入（第48課） → 存入向量資料庫（第49課） 查詢階段（每次提問都執行）： 問題 → 嵌入 → 向量資料庫相似度搜尋 → 取回相關chunk → 注入Prompt → LLM根據Prompt作答

同一個嵌入模型，貫穿兩個階段

有一個容易被忽略、但很重要的細節：準備階段用來把文件 chunk轉成向量的嵌入模型，跟查詢階段用來把使用者問題 轉成向量的嵌入模型，必須是同一個模型。 不同的嵌入模型，即使輸入同一段文字，產生出來的向量 空間也未必相容，拿模型A產生的問題向量，去跟模型B 產生的文件向量比對距離，比較出來的相似度沒有意義。 模組M實作時會看到，這一點在實務上要特別留意。

檢查你的理解

  1. 說明RAG為什麼可以拆成準備階段跟查詢階段，這兩者在執行時機上有什麼不同
  2. 依序列出準備階段的四個步驟，以及查詢階段的五個步驟
  3. 解釋為什麼準備階段跟查詢階段，必須使用同一個嵌入模型
