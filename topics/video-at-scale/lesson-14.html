TCP、QUIC 與影片：為什麼影片走 HTTP

這一課的目標

  • 理解「用 HTTP 傳影片」的理由
  • 比較 TCP 與 UDP 在影片上的表現
  • 知道 QUIC 帶來什麼改變

1. 直覺上應該用 UDP

影片是即時媒體，掉幾個封包無所謂， 重傳反而造成延遲。教科書會告訴你這種情境該用 UDP。 早期的串流協定（RTP／RTSP、RTMP）也確實是這樣設計的。

但今天絕大多數的影片是用 HTTP over TCP 傳的。為什麼？

2. 五個壓倒性的理由

理由說明
快取HTTP 檔案可以被任何一層快取，這是 CDN 能運作的前提
防火牆80／443 埠到處都通，自訂 UDP 協定常被企業網路擋掉
現成生態伺服器、負載平衡、監控、CDN 全部現成
成本用通用 HTTP 基礎設施，比維護專用串流伺服器便宜得多
畫質彈性ABR 天然建立在「一段一個檔案」之上

第一個理由最關鍵。回到第 5 課的算式： 快取把源頭需求從 100 Tbps 降到 1 Tbps。 任何無法被快取的協定，都要付出一百倍的基礎設施成本。 這個差距大到讓「TCP 重傳造成的延遲」相形之下微不足道。

3. 緩衝區化解了 TCP 的缺點

TCP 的問題是「隊頭阻塞」：一個封包掉了， 後面的資料都要等它重傳。對即時通訊這是災難。

但影片播放有緩衝區（第 13 課）。 手上已經有 10 秒的影片，重傳多花的 200 毫秒完全被吸收掉。 緩衝區把「即時傳輸問題」變成了「批次下載問題」， 而批次下載正是 HTTP 最擅長的。

4. QUIC 與 HTTP/3

QUIC 建在 UDP 之上，但保留了 HTTP 的語意。它改善了幾件事：

改善對影片的意義
0-RTT／1-RTT 連線建立開播更快，TTFF 下降
串流層級的獨立重傳一個段掉封包不會卡住其他段
連線遷移手機從 Wi-Fi 切到 4G 時連線不中斷
更好的擁塞控制行動網路下的吞吐量較穩

最後兩項對行動裝置特別有感。 而且因為它仍然是 HTTP 語意， 整個 CDN 與快取架構完全不用改—— 這是它能被大規模採用的原因。

5. 什麼時候還是要用 UDP 專用協定

情境為什麼
視訊通話延遲要低於 200 ms，沒有緩衝區可用
雲端遊戲延遲要求更嚴苛
超低延遲直播（< 1 秒）緩衝區被壓到極小，TCP 重傳會直接卡
直播訊號回傳從攝影現場傳回機房，用專用可靠 UDP 協定

判斷原則很清楚：能容忍幾秒緩衝的，用 HTTP； 不能的，用 UDP 專用協定，並接受無法快取的成本。

重點回顧

  • 影片用 HTTP 的首要理由是可被快取，這決定了一百倍的成本差距
  • 緩衝區吸收了 TCP 重傳的延遲
  • QUIC 保留 HTTP 語意，因此 CDN 架構不用改
  • 只有無法容忍緩衝的即時場景才用 UDP 專用協定
