導流：使用者怎麼被指到正確那台機器

這一課的目標

  • 比較三種導流機制
  • 理解各自的精度與反應速度
  • 知道影音平台為何用應用層導流

1. 問題

有幾千個節點，使用者發出請求時， 要怎麼讓他連到正確的那一個？ 「正確」的定義包含：夠近、有那個內容、還有餘裕、沒故障。

2. 三種機制

DNS 導流Anycast應用層導流
做法依查詢來源回不同 IP多個節點宣告同一個 IP，靠 BGP 選路先連一個入口，由它回傳實際的節點網址
精度中（看到的是 DNS 伺服器位置）低（BGP 選的是網路距離不是真實延遲）高（知道使用者身分與內容）
反應速度慢（受 TTL 限制）快（BGP 收斂）即時
能否依內容導流不能不能能
額外延遲無無多一次往返

3. 為什麼 DNS 導流不夠精準

DNS 伺服器看到的是解析者的 IP，不是使用者的 IP。 如果使用者用的是公共 DNS，解析請求可能來自幾百公里外， 導流就會導錯。

EDNS Client Subnet 這個擴充可以讓解析者附帶使用者的網段資訊， 改善了這個問題，但不是所有解析者都支援。

4. Anycast 的問題

Anycast 讓 BGP 自動選擇「最近」的節點，聽起來很理想。 但 BGP 的「近」是AS 跳數，不是實際延遲。 常見狀況是流量被導到跳數少但地理上很遠的節點。

另一個問題是連線穩定性： BGP 路由變動時，同一個連線可能被導到不同節點， 造成 TCP 連線中斷。這對長時間的影片下載特別麻煩。 （QUIC 的連線遷移可以緩解這件事。）

5. 應用層導流：影音平台的選擇

1. 播放器向「導流服務」要播放資訊 POST /get_playback_url { video_id, client_info } 2. 導流服務綜合判斷： · 使用者的 IP 對應到哪個 ISP、哪個地區 · 哪些節點有這支影片 · 各節點目前的負載與健康狀態 · 使用者的裝置與網路類型 · 內容的地理授權限制 3. 回傳實際的節點網址 { "url": "https://edge-tw-03.example.net/..." } 4. 播放器直接向該節點要影片段

代價是多一次往返（影響 TTFF）， 但換來的控制力太有價值：

  • 可以依內容導流（這個節點有沒有這支影片）
  • 可以即時反應節點故障或過載
  • 可以做灰度發布與 A/B 測試
  • 可以處理地理授權限制
  • 可以在播放中途切換節點

而且那次往返通常可以與其他必要的 API 呼叫合併 （取得影片 metadata、廣告、字幕清單），實際成本不高。

7. 模組 F 總結

  • CDN 解決延遲、頻寬成本、來源負載、可用度四件事
  • 影音快取節點是「儲存與網路強、CPU 弱」的特殊機器
  • 自建與商用的分水嶺約在平均 1–5 Tbps
  • 四層架構中，ISP 內嵌節點承載最大宗流量
  • 預先填充在免費的離峰時段搬貨，大幅提升命中率
  • 影音平台用應用層導流，因為只有它能依內容與即時狀態決策
