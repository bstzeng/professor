模組 H｜儲存（二）：怎麼存才不會壞 · 第 43 課

分散式檔案系統：從 GFS 到現代

這一課的目標

  • 理解分散式檔案系統的基本設計
  • 知道 metadata 與資料分離的理由
  • 認識規模帶來的設計演進

1. 要解決什麼

幾萬台機器、幾百萬顆硬碟， 要讓上層程式看起來像一個檔案系統： 給一個路徑就能讀寫，不用管資料實際在哪台機器。

2. 經典設計（GFS 那一代）

┌──────────────┐ │ Master 節點 │ 只存 metadata： │ │ · 檔案 → 區塊清單 │ │ · 區塊 → 存在哪幾台機器 └──────┬───────┘ │ 只問「在哪裡」 ┌──────┴────────────────────────────────┐ │ Chunk Server × 數千台 │ │ 每台管自己的本機硬碟，存 64 MB 的區塊 │ └───────────────────────────────────────┘ 讀取流程： 1. 客戶端問 Master：檔案 X 的第 3 個區塊在哪？ 2. Master 回：在機器 A、B、C 3. 客戶端直接向 A 讀，不再經過 Master

關鍵設計是資料不經過 Master。 Master 只處理「在哪裡」的查詢， 實際的位元組直接在客戶端與儲存節點之間流動。 這讓單一 Master 能管理極大的叢集。

3. 幾個關鍵決定

決定理由
區塊很大（64 MB 起）減少 metadata 數量；影音檔案本來就大
只支援追加寫入影片寫一次就不改，不需要支援隨機修改
放寬一致性換取可用度與效能
故障是常態偵測、複製、重建全部自動化
metadata 放記憶體查詢要快；用大區塊讓 metadata 放得下

第二項值得注意：放棄通用性換取簡單。 這個檔案系統不能當一般檔案系統用， 但它完美符合「寫一次、讀很多次、不修改」的影音場景。

4. 單一 Master 的極限

隨著規模成長，單一 Master 撐不住：

  • metadata 超過單機記憶體
  • 查詢速率超過單機處理能力
  • Master 故障時整個叢集暫停
  • 小檔案太多時 metadata 爆炸（第 36 課）

所以下一代系統把 metadata 層本身也分散化： 用分散式資料庫存 metadata，多個無狀態的前端處理查詢。 這讓系統能擴展到 EB 級。

5. 現代設計的幾個特徵

特徵說明
metadata 分散化存在可水平擴展的資料庫，不再是單點
糾刪碼原生支援不只是複本（第 41 課）
分層感知系統自己管理資料在熱／冷層之間搬移
多租戶隔離不同服務共用同一套儲存，但互不影響
跨區域複製內建的跨機房資料放置策略
物件介面不一定是檔案系統語意，常是 PUT／GET 的物件儲存

最後一項是重要的簡化： 影音平台其實不需要「檔案系統」， 它需要的是「給我一個 ID，還我一坨位元組」。 物件儲存的語意更簡單，也更容易擴展。

6. 對上層的意義

轉碼服務、CDN 回源、備份系統， 全部透過同一個介面存取資料，不必知道：

  • 資料在哪台機器、哪顆硬碟
  • 用的是複本還是糾刪碼
  • 資料在熱層還是冷層
  • 剛剛有沒有硬碟壞掉正在重建

這層抽象是整個系統能運作的關鍵。 沒有它，每個應用都要自己處理幾百萬顆硬碟的故障。
