不是下載也不是串流：HLS 與 DASH 的分段機制

這一課的目標

  • 理解分段串流的機制
  • 看懂 manifest 檔案
  • 知道分段長度的取捨

1. 不是下載整個檔案

早期的網路影片是「下載完才能播」或「漸進式下載」。 現代串流不是這樣——影片被切成幾秒一段的小檔案， 播放器一段一段地要。

傳統：GET /video.mp4 （一個 500 MB 的請求） 現代：GET /1080p/seg-001.m4s （一個 2 MB 的請求） GET /1080p/seg-002.m4s GET /720p/seg-003.m4s ← 網路變差，換低畫質 GET /720p/seg-004.m4s

這個設計帶來四個好處：

  • 可以逐段切換畫質（ABR）
  • 每段都是普通的 HTTP 檔案，可以被任何 HTTP 快取加速
  • 跳轉時只要抓對應的段，不必下載整個檔案
  • 直播只要持續產生新的段就好

第二點是規模化的關鍵：因為是普通 HTTP 檔案， 整個 CDN 生態才能直接拿來用。第 14 課會展開。

2. Manifest

播放器怎麼知道有哪些畫質、每段的網址是什麼？ 靠一個描述檔（manifest／playlist）。

# HLS 的主播放清單（master.m3u8） #EXTM3U #EXT-X-STREAM-INF:BANDWIDTH=700000,RESOLUTION=640x360 360p/index.m3u8 #EXT-X-STREAM-INF:BANDWIDTH=2500000,RESOLUTION=1280x720 720p/index.m3u8 #EXT-X-STREAM-INF:BANDWIDTH=5000000,RESOLUTION=1920x1080 1080p/index.m3u8 # 單一畫質的播放清單（1080p/index.m3u8） #EXTM3U #EXT-X-TARGETDURATION:4 #EXTINF:4.0, seg-001.m4s #EXTINF:4.0, seg-002.m4s ...

3. HLS 與 DASH

HLSDASH
提出者AppleMPEG（國際標準）
描述檔.m3u8（文字清單）.mpd（XML）
裝置支援iOS 原生，幾乎全平台Android、瀏覽器、智慧電視
片段格式早期 .ts，現在多用 fMP4fMP4
實務平台通常兩種都提供，片段檔案可共用（CMAF）

CMAF 是重要的一步：它讓 HLS 與 DASH 共用同一批片段檔案， 只需要兩份不同的 manifest。這直接省下一半的儲存與快取空間。

4. 分段長度的取捨

段長延遲切換反應請求數壓縮效率
1 秒低快多（開銷大）差（I 幀太密）
2–4 秒中好適中好
6–10 秒高慢少最好

點播通常用 4–6 秒（優先壓縮效率）， 直播用 2 秒或更短（優先低延遲）， 超低延遲直播會用「分塊傳輸」把一段再切成更小的塊邊產邊送。

5. 對基礎設施的意義

分段機制看起來是播放器的事，實際上決定了整個後端架構：

  • 每段是獨立檔案 → 可以用標準 HTTP 快取 → CDN 直接可用
  • 段的數量很大 → 一支一小時影片有近千個檔案 × 多個畫質 → 物件數量爆炸
  • 熱門段（影片開頭）與冷段（影片後半）的存取頻率差很多 → 快取策略要分開

最後一點很實際：大部分人只看影片的前面幾分鐘。 所以前幾段的快取價值遠高於後面的段。
