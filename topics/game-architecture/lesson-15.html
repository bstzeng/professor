  • 理解觀察者模式
  • 寫出簡單的事件系統
  • 知道事件的缺點
// 訂閱 events.Subscribe<PlayerDamaged>([](const PlayerDamaged& e) { hud.SetHp(e.newHp); }); // 發送：玩家不需要知道誰在聽 events.Publish(PlayerDamaged{ player, 10, newHp });

立即派送還是排入佇列

立即派送簡單，但接收者如果又發出事件，可能形成難以追蹤的連鎖。許多引擎改成把事件放進佇列，在畫格的固定時間點統一處理。

缺點

  • 流程分散，除錯時很難知道「是誰改了這個值」。
  • 忘記取消訂閱會造成記憶體洩漏或存取已刪除的物件。

🧭 這一課的重點

事件讓系統之間低耦合；代價是流程較難追蹤，要注意訂閱的生命週期。

🎮 本課以通用的遊戲引擎架構說明概念，程式碼為教學用的簡化片段（類 C++／C# 虛擬碼），不是特定引擎的實際原始碼；各引擎的實作細節以官方文件為準。
