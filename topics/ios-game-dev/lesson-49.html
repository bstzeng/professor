Xcode除錯器與中斷點

這一課的目標

  • 學會在Xcode程式碼編輯器的行號區域點擊設定中斷點，讓程式執行到該行時暫停
  • 能使用除錯區域的變數檢視器，以及主控台的po指令，檢查中斷當下的物件狀態
  • 認識print()語句這個更輕量、免設定的除錯手段，知道什麼情況適合用哪一種

模組K完成了分數與設定的儲存，遊戲的核心玩法與資料層都已經 到位。從這一課開始的模組L，要補上開發過程中不可或缺的 兩件事——除錯與效能檢查，讓你在遇到「東西壞了但不知道 為什麼」或「玩起來卡卡的」時，有系統化的方法排查，而不是 憑感覺亂改程式碼、改到能動就算了。這一課先從最基本、 也最常用的除錯工具開始：中斷點。

1. 中斷點：讓程式暫停在指定的一行

在Xcode的程式碼編輯器裡，每一行程式碼左邊都有一條窄窄的 「行號區域」（gutter）。直接用滑鼠點擊某一行左邊的空白處， 就會出現一個藍色箭頭形狀的標記——這就是一個 中斷點（breakpoint）。接下來用Cmd+R在模擬器或 真機上執行App時，只要程式的執行流程走到設了中斷點的那 一行，就會自動暫停下來，畫面卡在那個當下，等你檢查。

中斷點可以設很多個，也可以隨時點一下藍色箭頭把它切換成 灰色（暫時停用、不刪除），或是直接把它拖出行號區域來 刪除。這讓你可以在懷疑出問題的程式碼附近，先埋幾個 中斷點，用「執行到這裡確實有沒有發生」來一步步縮小 問題範圍。

2. 除錯區域：變數檢視器

程式在中斷點暫停時，Xcode視窗下方會自動打開 除錯區域，左邊是變數檢視器， 會列出當下這個作用域（scope）裡所有區域變數、參數， 以及它們目前的值。點擊某個物件型別的變數旁邊的展開 箭頭，還能進一步看它內部各個屬性的值——例如中斷在 一個處理碰撞的函式裡，就能直接看到傳進來的節點的 position、physicsBody的velocity等目前的實際數值， 不需要另外寫程式碼把它們印出來。

3. 主控台的po指令

除錯區域右邊是主控台（console），這裡 除了會顯示程式執行過程中print()印出的內容，暫停時還能 直接在提示字元（lldb）後面輸入指令，即時查詢當下的狀態。 最常用的就是po（print object）指令， 後面接一個運算式，就能把它的內容印出來：

(lldb) po paddle.position (lldb) po ball.physicsBody?.velocity (lldb) po lives

po的好處是不受限於變數檢視器目前顯示的內容——只要是在 目前作用域裡看得到的東西，甚至是稍微組合過的運算式 （例如po touch.location(in: self)），都能 當場算出來、印出結果，不需要為了看一個值就修改程式碼、 重新編譯。

4. print()語句：更陽春但即時可用的除錯法

中斷點跟po指令威力強大，但有時候你只是想確認「這段 程式碼到底有沒有被執行到」「這個值在遊戲跑起來的過程中 怎麼變化」，這種情境下，直接在程式碼裡插入 print()語句往往更快、更直覺，不需要另外設定 中斷點、也不會讓遊戲每次都真的暫停下來：

override func touchesMoved(_ touches: Set<UITouch>, with event: UIEvent?) { guard let touch = touches.first else { return } let location = touch.location(in: self) print("touchesMoved被呼叫，觸控x座標：\(location.x)") paddle.position.x = location.x }

跑起來之後盯著主控台看，如果手指在畫面上滑動時完全沒有 印出任何訊息，就代表touchesMoved這個函式 根本沒被呼叫到——問題出在「事件有沒有送進來」這一層， 而不是球拍移動的計算邏輯本身。這種「先確認程式碼有沒有 跑到」的排查方式，正是print()最擅長的場景。

5. 實戰演練：球拍不回應觸控的假設性bug

假設你回顧模組E、F做出來的打磚塊遊戲時，發現手指在畫面上 滑動，球拍卻完全沒有反應。可以按照以下順序排查：

  1. 先用print()確認事件有沒有進來——在 touchesMoved第一行加上print()，跑起來 滑動畫面。如果主控台完全沒反應，問題通常出在球拍節點 的isUserInteractionEnabled被設成 false、或是這個處理觸控的節點根本沒有被加進場景的 節點樹裡（回顧模組D的SKNode節點樹概念）。
  2. 如果事件有進來，改用中斷點深入看 ——在計算球拍新位置的那一行設中斷點，程式暫停時用 變數檢視器或po指令看location.x、 paddle.position目前的實際值，確認座標 轉換（回顧模組D第18課的座標系統）有沒有算錯。
  3. 逐步縮小範圍——如果座標本身是對的， 但球拍畫面上就是沒動，再往下檢查球拍節點是不是被 其他邏輯（例如物理引擎的物理體設定）鎖住了X軸的 移動。

這個流程的重點，不是「一定要用哪個工具」，而是先用最 便宜的手段（print()）快速確認問題出現的大致範圍，真的 需要深入檢查物件內部狀態時，再動用中斷點跟po指令。
