模組總結：update與遊戲迴圈

這一課的目標

  • 理解SpriteKit的遊戲迴圈，以及update(_:)方法在其中扮演的角色
  • 知道update(_:)大約多久被呼叫一次，適合放哪一類遊戲邏輯
  • 認識currentTime可以用來計算影格間的時間差，並知道這是可以先擱置的進階細節

模組D從SKScene、SKNode、SKSpriteNode，一路講到座標 系統，把「畫面上有什麼」講清楚了，但還沒回答一個關鍵 問題：這些東西是怎麼「動起來」的？模組D的最後一課， 就從這個問題出發，介紹SpriteKit的遊戲迴圈。

什麼是遊戲迴圈

SpriteKit在背後，每一個畫面更新的瞬間（稱為一個 「影格」，frame），都會依序執行一輪固定的處理流程： 更新遊戲邏輯、套用動作（SKAction，模組I會介紹）、 模擬物理效果（模組G會介紹）、計算碰撞，最後才把結果 畫到螢幕上——這一整輪處理，會不斷重複，這就是所謂的 「遊戲迴圈（game loop）」。update(_:)正是 SpriteKit在這個迴圈裡，開放給開發者插入自己遊戲邏輯的 關鍵位置之一。

override func update(_ currentTime: TimeInterval)

把update(_:)加到你的SKScene 子類別裡，SpriteKit就會在每一影格自動呼叫它一次——在 大部分裝置上，大約是每秒60次。這是放「需要持續、每 影格都檢查一次」的邏輯最適合的地方，例如檢查勝負條件、 或是移動一些沒有交給物理引擎或SKAction處理的物件。

class GameScene: SKScene { var score = 0 let winningScore = 10 override func update(_ currentTime: TimeInterval) { // 每一影格都會執行一次，適合放「持續檢查」的邏輯 if score >= winningScore { endGame(win: true) } } func endGame(win: Bool) { // 之後模組H會實作完整的勝負判定與畫面切換邏輯 } }

這個例子裡，update(_:)每一影格都會檢查 一次score是否達到winningScore， 一旦符合條件就呼叫endGame(win:)——這種 「每影格持續檢查」的模式，跟只在特定事件發生時才執行 一次的程式碼（例如觸控事件、碰撞事件）是不同的思維， 模組E、G會分別介紹這些事件驅動的寫法。

currentTime與影格間的時間差：可以先擱置的進階細節

update(_:)收到的currentTime 參數，是目前這一影格對應的系統時間戳記。把這次收到的 currentTime，跟上一次呼叫時記錄下來的 時間相減，就能算出兩次影格之間實際經過了多久——這個 差值一般稱為「delta time」，常常用來讓物件的移動速度 跟裝置實際的更新頻率脫鉤（frame-rate independent movement），確保在更新頻率較低或較高的裝置上，物件 移動的速度看起來是一致的。

這是稍微進階的技巧，牽涉到額外的狀態記錄與計算，對 剛學完模組D核心概念的階段來說，不需要急著搞懂或套用—— 等到後面模組L談效能優化、或是實際遇到「同一個動作在 不同裝置上速度感覺不一致」的具體問題時，再回頭處理 delta time的計算也完全來得及。

到這裡，模組D完整走完了SpriteKit最核心的四個概念： SKScene是容器、SKNode是組織方式、SKSpriteNode是最常見 的可視節點、加上座標系統與遊戲迴圈這兩個貫穿一切的 基礎規則。接下來的模組E，要開始處理玩家怎麼「操作」 這些節點——也就是觸控輸入。
