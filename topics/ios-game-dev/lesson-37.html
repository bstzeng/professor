模組 H｜實作專案③：遊戲邏輯與狀態管理 · 第 37 課

模組總結：完整的遊戲狀態機

這一課的目標

  • 認識用enum GameState把「遊戲目前在哪個階段」變成一組清楚、有限的狀態集合
  • 學會用switch對狀態分支，決定update(_:)該跑哪些邏輯、畫面該顯示什麼、要不要接受觸控輸入
  • 看懂模組F到H做出來的每一塊——球拍、球、磚塊、分數、生命、勝負、暫停與重新開始——怎麼被整合進同一套狀態機裡

模組H一路加了分數、生命值、勝負判定、暫停與重新開始， 每個功能各自都能動，但彼此的關係目前散落在好幾個獨立 的布林值跟條件式裡——isPaused管暫停、 lives <= 0管失敗、球是不是已經發射又 沒有變數記錄。這一課不新增遊戲功能，而是引入一個更 清楚的組織方式：用一個enum把「遊戲現在 處在哪個階段」明確定義出來，讓其餘所有邏輯，都圍繞著 這一個狀態值來決定該做什麼。

為什麼需要一個明確的狀態機

回想一下這整個專案：遊戲一開始，球應該還沒發射、 等待玩家點擊開始（呼應第27課的開始畫面）；玩家點擊後 進入正常遊玩；途中玩家可能按下暫停；最後可能磚塊清空 獲勝，也可能生命值歸零落敗。這五種情境，正是遊戲會 經歷的所有「階段」——如果沒有一個變數明確記錄目前在 哪個階段，很容易寫出互相矛盾的程式碼，例如遊戲明明已經 結束了，觸控事件卻還在移動球拍。狀態機的核心思路，就是 先把所有可能的階段窮舉出來，再讓其餘程式碼只根據「目前 是哪個階段」做決定。

定義GameState

用一個enum列出遊戲會經歷的五種狀態：

enum GameState { case ready // 等待玩家開始，球尚未發射 case playing // 正常遊玩中 case paused // 暫停中 case gameOver // 已落敗 case win // 已獲勝 }

接著在GameScene裡加入一個目前狀態的屬性， 並用didSet屬性觀察器，讓每次狀態改變時， 自動觸發對應的畫面更新：

var gameState: GameState = .ready { didSet { updateForState() } }

用switch控制每個狀態該做什麼

updateForState()用switch對 gameState分支，把每個狀態該有的畫面反應 集中寫在一個地方：

func updateForState() { switch gameState { case .ready: isPaused = false messageLabel.text = "點擊畫面開始遊戲" messageLabel.isHidden = false case .playing: isPaused = false messageLabel.isHidden = true case .paused: isPaused = true messageLabel.text = "已暫停" messageLabel.isHidden = false case .gameOver: isPaused = true messageLabel.text = "遊戲結束" messageLabel.isHidden = false case .win: isPaused = true messageLabel.text = "遊戲勝利！" messageLabel.isHidden = false } }

update(_:)裡原本第34課寫的球掉出底部偵測， 也應該只在.playing狀態才執行——遊戲還沒 開始，或已經結束時，不應該繼續判斷漏接：

override func update(_ currentTime: TimeInterval) { switch gameState { case .playing: if ball.position.y < 0 { ballLost() } default: break } }

把之前的邏輯接進狀態機

有了gameState，模組G、H做的其餘邏輯只要 在對的時機切換狀態即可，不用再各自維護獨立的旗標：

override func touchesBegan(_ touches: Set, with event: UIEvent?) { guard let touch = touches.first else { return } let location = touch.location(in: self) switch gameState { case .ready: gameState = .playing ball.physicsBody?.velocity = CGVector(dx: 140, dy: -220) case .playing: if pauseButton.contains(location) { gameState = .paused } // 其餘觸控交給移動球拍的邏輯 case .paused: if pauseButton.contains(location) { gameState = .playing } case .gameOver, .win: if restartButton.contains(location) { restartGame() } } } func gameWin() { gameState = .win } func gameOver() { gameState = .gameOver }

第35課寫的gameWin()、gameOver() 現在只需要一行：把gameState改成對應的 狀態，didSet就會自動呼叫 updateForState()處理畫面反應，不用在每個 觸發勝負的地方，重複寫顯示文字、暫停場景這些細節。

模組F到H，串成了什麼

回頭看看整個實作專案走到這裡累積了什麼：模組F建立了 場景、球拍、球、磚塊排版；模組G讓它們透過physics body 與bitmask真正產生碰撞、反彈、消滅；模組H加上分數、 生命、勝負判定、暫停與重新開始。這一課的 GameState，是把前面所有分散的邏輯，收攏 進同一套清楚的規則裡——這正是「能動的程式碼」跟 「結構清楚、之後好維護、好擴充的程式碼」之間的差異。
