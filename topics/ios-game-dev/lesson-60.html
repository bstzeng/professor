模組 M｜App內廣告整合 · 第 60 課

模組總結：使用者追蹤透明度（ATT）合規要求與上架前的廣告檢查清單

這一課的目標

  • 理解App Tracking Transparency（ATT）框架的基本要求：想跨App追蹤使用者做廣告個人化，必須先跳出系統權限彈窗徵求同意
  • 知道Info.plist要設定NSUserTrackingUsageDescription，並學會呼叫ATTrackingManager.requestTrackingAuthorization(completionHandler:)
  • 能列出一份上架前的廣告檢查清單，確保正式送審前該做的事都做了

橫幅、插頁、獎勵型三種廣告格式都實作完成了，模組M收尾 的這一課，要處理一個技術之外、但同樣不能忽略的主題—— 使用者追蹤透明度（App Tracking Transparency，簡稱ATT） 的合規要求。這不是選配功能，而是自iOS 14.5起，蘋果對 所有想做跨App廣告追蹤的App，明文規定的強制要求，沒做 對，輕則廣告效果打折，重則在App審查階段直接卡關。

什麼是App Tracking Transparency（ATT）

蘋果定義的「追蹤」，指的是把從你的App蒐集到的使用者或 裝置資料，跟其他公司的App、網站蒐集到的資料串連起來， 用於精準投放廣告或衡量廣告成效，或是把資料分享給資料 仲介商（data broker）。像AdMob這類廣告SDK，如果啟用了 跨App的廣告個人化功能，就落在這個定義範圍內。ATT框架的 規則很直接：任何App只要打算做這類追蹤，就必須先跳出 一個系統層級的權限彈窗，明確詢問使用者「是否允許這個 App追蹤你」，只有使用者點選允許，App才能繼續進行 追蹤相關的廣告個人化；使用者拒絕，App仍然可以正常運作、 照樣能顯示廣告，只是廣告聯播網會改用非個人化、不依賴 跨App追蹤資料的方式投放。

Info.plist：NSUserTrackingUsageDescription

系統彈窗裡除了固定的標題與允許／不允許兩個按鈕，還會 顯示一段由開發者自訂、說明「為什麼要追蹤」的文字，這段 文字就是在Info.plist裡設定的NSUserTrackingUsageDescription：

<key>NSUserTrackingUsageDescription</key> <string>我們想使用你的資料，提供更符合你興趣的廣告內容。</string>

這段文字應該誠實、具體地說明追蹤的用途（例如「提供更 符合你興趣的廣告」），而不是含糊帶過或跟實際用途不符—— 審查團隊跟使用者都看得到這段文字，內容不實際、或跟App 實際行為對不上，同樣可能成為退件的理由。

呼叫時機：ATTrackingManager.requestTrackingAuthorization

彈出這個系統權限請求，要在程式碼裡主動呼叫 AppTrackingTransparency框架提供的方法：

import AppTrackingTransparency func requestTrackingPermission() { ATTrackingManager.requestTrackingAuthorization { status in switch status { case .authorized: print("使用者同意追蹤") case .denied, .restricted, .notDetermined: print("使用者拒絕或尚未決定追蹤") @unknown default: break } } }

這個系統彈窗對每個App只會有效地跳出一次——使用者做出 選擇之後，之後同一個App再呼叫這個方法，系統不會重複 彈窗，而是直接回傳使用者先前的選擇（除非使用者自己到 系統設定裡手動更改）。因此常見的做法是在App 剛啟動、盡早的時間點就呼叫一次，理想上要在 第一次發出廣告請求之前完成，這樣不管使用者選擇同意或 拒絕，後續載入的每一支廣告，都能以最終確定的授權狀態 來請求，不會出現「廣告已經開始請求，使用者才做出選擇」 這種時序上的落差。無論使用者選擇同意或拒絕，App都必須 能正常繼續運作、正常顯示廣告——不能把功能鎖住、逼迫 使用者一定要同意追蹤才能使用App。

SKAdNetwork：不需要追蹤同意也能運作的歸因機制

即使使用者拒絕追蹤，廣告聯播網仍然需要知道「這支廣告 帶來了多少次App安裝」，才能計算成效、決定要不要繼續 投放——這正是蘋果另外提供的SKAdNetwork 框架要解決的問題：它用一種不需要識別個別使用者身份的 方式，統計廣告帶來的安裝歸因，因此完全不受ATT使用者 選擇的影響。要讓AdMob能透過SKAdNetwork回報歸因結果， 需要在Info.plist裡加入AdMob文件要求的一整組 SKAdNetworkIdentifier：

<key>SKAdNetworkItems</key> <array> <dict> <key>SKAdNetworkIdentifier</key> <string>cstr6suwn9.skadnetwork</string> </dict> <dict> <key>SKAdNetworkIdentifier</key> <string>4fzdc2evr5.skadnetwork</string> </dict> <!-- 其餘識別碼請以Google官方文件公布的完整清單為準 --> </array>

這份清單會隨著AdMob合作的廣告聯播網增減而更新，實際 要加入哪些識別碼，請以Google官方文件當下公布的完整 清單為準，而不是憑印象手動列幾組就當作完成。

上架前的廣告檢查清單

模組M到這裡，技術實作已經全部到位，正式送審前，值得 照著這份清單再確認一次：

  1. 把所有測試廣告單元ID都換成正式Ad Unit ID ——第57課提醒過，開發階段用的官方測試ID，必須在送審 前全部換成第55課在AdMob後台為這款遊戲建立的正式Ad Unit ID，橫幅、插頁、獎勵型三種格式都要逐一確認。
  2. ATT權限彈窗已經實作且確實會正常跳出 ——實機測試時確認Info.plist的 NSUserTrackingUsageDescription文字正確 顯示、requestTrackingAuthorization在 預期的時機被呼叫，同意與拒絕兩種結果都不會讓App 出現異常行為。
  3. App Store Connect的隱私權「營養標籤」如實 反映AdMob SDK實際蒐集的資料——這份標籤要 填寫的內容，必須跟AdMob SDK實際蒐集、使用的資料類型 一致，不能少報也不能亂填，詳細怎麼填寫，模組P會 有完整說明。
