碰撞分類（Collision Category）

這一課的目標

  • 理解categoryBitMask、collisionBitMask、contactTestBitMask這三個位元遮罩，各自在物理引擎裡扮演什麼角色
  • 學會用一個PhysicsCategory結構整理每一種物件的分類旗標，避免在程式碼裡直接寫死數字
  • 能分辨「兩個物體會不會真的物理彈開」跟「兩個物體會不會觸發didBegin(_:)通知」是兩件不同的事

上一課讓場景能在碰撞發生時呼叫didBegin(_:)， 但目前所有physics body之間，只要距離夠近都會觸發——球 撞到球拍、球撞到磚塊、甚至磚塊互相貼在一起，全部都是 「碰撞」，程式碼卻沒有任何方法分辨誰是誰。這一課要學的 位元遮罩（bitmask），是新手最容易搞混的SpriteKit概念 之一，但只要抓到「三個遮罩各自回答一個不同問題」這個 原則，其實並不難。

1. 為什麼需要分類：不是所有碰撞都該一視同仁

以這款打磚塊遊戲為例，球需要跟球拍、螢幕邊界真正 「physically」彈開，才會有正確的反彈角度；但球撞到磚塊 時，我們真正想要的動作是「磚塊消失」，而不一定需要 兩者先物理彈開才能判定。如果所有物體之間的碰撞規則都 一樣，就沒辦法做出這種區分——這正是SpriteKit設計三種 獨立位元遮罩的原因：讓「物理上會不會彈開」跟「會不會 觸發程式碼裡的通知」，可以分開設定。

2. 三個關鍵屬性，各自回答一個問題

SKPhysicsBody上有三個型別都是UInt32的屬性， 每一個bit（位元）都可以代表一種分類，透過位元運算來 判斷兩個body之間該不該產生碰撞或通知：

  • categoryBitMask——回答「我是誰」。這個 physics body屬於哪一個分類（球、球拍、磚塊、牆…）， 預設值是0xFFFFFFFF（所有分類）
  • collisionBitMask——回答「我會被誰物理 彈開」。物理引擎會拿這個body的collisionBitMask 跟對方的categoryBitMask做AND運算，結果不為0 才會產生碰撞反應，預設值同樣是0xFFFFFFFF （代表預設跟所有東西都會物理碰撞）
  • contactTestBitMask——回答「誰的接觸要 通知我的didBegin(_:)」。預設值是 0（完全不通知），必須明確指定才會收到 通知——而且就算collisionBitMask設定成 兩者不會物理彈開、直接穿過彼此，只要 contactTestBitMask設定正確，didBegin(_:) 一樣會被呼叫

容易搞混的地方

初學者最常犯的錯誤，是以為「兩個物體會不會撞在一起」 只由一個設定決定。實際上「彈不彈得開」跟「通不通知 你的程式碼」是完全獨立的兩件事：collisionBitMask 管的是物理引擎自己的反彈行為，contactTestBitMask 管的是要不要呼叫didBegin(_:)——兩者可以 任意組合，這正是這一課的重點。

3. 用PhysicsCategory整理分類旗標

與其在程式碼各處直接寫1、2、 4這種數字，慣例的做法是定義一個結構，用 <<位移運算子，讓每個分類各自佔一個 獨立的bit，這樣才能用|（OR）自由組合， 彼此又不會互相覆蓋：

struct PhysicsCategory { static let none: UInt32 = 0 static let ball: UInt32 = 0x1 << 0 // 0001 = 1 static let paddle: UInt32 = 0x1 << 1 // 0010 = 2 static let brick: UInt32 = 0x1 << 2 // 0100 = 4 static let wall: UInt32 = 0x1 << 3 // 1000 = 8 }

0x1 << 0就是1、0x1 << 1 就是2、0x1 << 2是4，每往左移一位數值 剛好翻倍，對應到二進位裡剛好只有一個bit是1——這樣不管 用|組合多少個分類，都不會有兩個分類疊在 同一個bit上，之後用&檢查時才不會誤判。

4. 實際套用到球拍、磚塊、球、邊界上

有了分類定義，接著幫每個physics body設定三個遮罩。球 要能撞到球拍、牆壁時真的彈開，同時撞到磚塊時要收到通知：

ball.physicsBody?.categoryBitMask = PhysicsCategory.ball ball.physicsBody?.collisionBitMask = PhysicsCategory.paddle | PhysicsCategory.wall ball.physicsBody?.contactTestBitMask = PhysicsCategory.brick | PhysicsCategory.paddle

球拍跟磚塊也要各自標明自己的分類，並且允許球把自己 物理彈開（球拍要讓球彈開；磚塊在這個設計裡，主要靠 contactTestBitMask被偵測到後就會消失， 不一定需要真的物理彈開）：

paddle.physicsBody?.categoryBitMask = PhysicsCategory.paddle paddle.physicsBody?.collisionBitMask = PhysicsCategory.ball for brick in bricks { brick.physicsBody?.categoryBitMask = PhysicsCategory.brick brick.physicsBody?.collisionBitMask = PhysicsCategory.none }

這裡把磚塊的collisionBitMask設成 PhysicsCategory.none，代表磚塊不會把球 物理彈開，球會直接「穿過」磚塊的位置，但因為 contactTestBitMask已經包含 brick，didBegin(_:)還是會被 正常呼叫，下一課會在裡面把磚塊移除。

另一種常見做法

有些打磚塊實作，會讓磚塊的collisionBitMask 也包含球，讓球撞到磚塊那一瞬間先物理彈開一次，緊接著 didBegin(_:)才把磚塊移除——視覺上會多一個 短暫的反彈手感。兩種做法都合理，這一課選擇比較單純的 「只靠contactTestBitMask偵測」版本，方便先把觀念釐清。

檢查你的理解

  1. 分別說明categoryBitMask、collisionBitMask、contactTestBitMask各自回答什麼問題
  2. 解釋為什麼PhysicsCategory裡每個分類要用0x1 << n而不是直接寫0、1、2、3
  3. 說明為什麼即使磚塊的collisionBitMask設成none，球撞到磚塊時didBegin(_:)還是會被呼叫
