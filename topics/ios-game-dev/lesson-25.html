模組 F｜實作專案①：打磚塊遊戲——基礎架構 · 第 25 課

建立球

這一課的目標

  • 用SKSpriteNode建立球，並定位在球拍正上方
  • 理解這一課刻意讓球維持靜止，真正的物理彈跳邏輯留給模組G
  • 認清目前架構下，球、球拍、磚塊雖然都在場景裡，但彼此還沒有互動能力

球拍準備好了，接著建立打磚塊遊戲裡另一個核心物件——球。 這一課有一個刻意的設計決定，先說在前面：球在這 一課只負責出現在正確的位置，暫時不會動。真正 讓球飛起來、撞到東西會反彈的邏輯，需要 SKPhysicsBody，那是模組G「物理引擎與碰撞」 的主題。先把靜態的球放進場景，可以確保這一課的重點—— 物件的建立與定位——不會被物理模擬的細節干擾。

1. 建立球的SKSpriteNode

延續第24課球拍的作法，球暫時也用純色方塊佔位，之後模組 J加入真正的美術素材時，只需要把這裡換成用圖片初始化的 SKSpriteNode，其他程式碼幾乎不用動：

class GameScene: SKScene { private let paddle = SKSpriteNode(color: .white, size: CGSize(width: 100, height: 20)) private let ball = SKSpriteNode(color: .yellow, size: CGSize(width: 20, height: 20)) override func didMove(to view: SKView) { paddle.name = "paddle" paddle.position = CGPoint(x: frame.midX, y: frame.minY + 80) addChild(paddle) ball.name = "ball" ball.position = CGPoint(x: paddle.position.x, y: paddle.position.y + 40) addChild(ball) } }

球的初始位置用paddle.position.x對齊球拍 的水平中心，y座標則是球拍的y座標再加上一段距離，讓球 看起來「放在球拍上方」，符合第23課規劃的場景佈局。 ball.name = "ball"同樣依照命名規範設定， 模組G判斷碰撞時會用到這個名稱。

2. 為什麼這一課選擇讓球保持靜止

沒有物理引擎的情況下，讓球「動起來」其實也做得到——例如 在update(_:)裡每一幀手動改變 ball.position，模擬一個固定方向的速度。但 這種手動位移的作法，沒辦法處理「撞到球拍或牆壁該怎麼 反彈」這類需要角度計算的行為，寫起來要嘛過度簡化、要嘛 提早重造physics engine的輪子。這門課的安排是： 這一課先讓球完全靜止，模組G才用SKPhysicsBody一次做對 重力、速度與反彈，避免在還沒學物理引擎之前， 寫一套之後要整個打掉重寫的手動位移邏輯。

3. 目前的架構總覽：三種節點，但還沒有互動

跑到這裡，GameScene裡已經有paddle （可以用手指移動）跟ball（暫時靜止）兩個 節點，下一課還會加入整排磚塊。但即使畫面上球跟球拍的 方塊重疊在一起，也不會發生任何碰撞反應 ——因為目前沒有任何節點被指定 physicsBody，SpriteKit根本不知道要偵測誰 跟誰接觸。這正是模組F要留給模組G解決的問題：先把場景 裡該有的物件都擺好，物理與碰撞留到下一個模組系統性地 處理。

檢查你的理解

  1. 寫出建立球的SKSpriteNode，並把它定位在球拍正上方的程式碼
  2. 說明這一課為什麼選擇讓球保持靜止，而不是先寫手動移動邏輯
  3. 解釋現在即使球和球拍在畫面上重疊，也不會發生任何碰撞反應的原因
