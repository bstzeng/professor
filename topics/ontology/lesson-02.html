模組 A｜什麼是 Ontology · 第 2 課

為什麼需要 Ontology

這一課的目標

  • 理解語意不一致造成的問題
  • 區分語法、結構與語意的互通
  • 理解 Ontology 解決的核心問題

一家公司的業務部說「客戶」，指的是曾經詢價的人；財務部說「客戶」，指的是付過錢的人；客服部說「客戶」，指的是有有效合約的人。三個系統的資料表都有一欄 customer_id，合併報表時，客戶數卻對不起來。

這不是程式錯誤，而是語意不一致。資料系統之間的互通有三個層次：

層次問題解法
語法檔案格式不同（CSV、JSON、XML）格式轉換
結構欄位名稱與資料表設計不同結構對應（mapping）
語意同一個詞意思不同；不同的詞意思相同Ontology：明確定義每個概念

真實世界的例子

  • 醫療：「心肌梗塞」「MI」「heart attack」「I21」（ICD-10 代碼）指的是同一件事；不同醫院的電子病歷要能互相理解，就需要像 SNOMED CT 這樣的醫學本體（第 40 課）。
  • 單位：1999 年 NASA 的火星氣候探測者號墜毀，原因之一是一個團隊用英制單位、另一個用公制，軟體介面沒有明確定義單位。
  • 國防與情報：「目標」「威脅」「事件」在各單位的定義不同，整合情報時必須先統一概念——這正是 Palantir 起家的問題（模組 J）。
  • 搜尋：使用者搜尋「蘋果」，是水果還是公司？

Ontology 提供什麼

  1. 共同詞彙：每個概念有唯一的識別碼與明確定義。
  2. 關係：概念之間怎麼連結（客戶「簽訂」合約、合約「屬於」產品線）。
  3. 約束與推理：哪些組合合法，以及可以自動推出哪些隱含的事實。
  4. 可重用：不同系統、不同組織共用同一套概念。
# 三個系統各自的「客戶」，用同一個本體概念對齊 crm = {"customer_id": 101, "status": "lead"} # 業務：詢價過 billing = {"customer_id": 101, "paid": True} # 財務：付過錢 support = {"customer_id": 101, "contract": "active"} # 客服：有合約 # 本體裡明確區分三個概念，而不是混用一個 "customer" ONTOLOGY = { "Prospect": "曾經表達購買意願的個人或組織", "PayingCustomer": "至少完成一筆付款的 Prospect", "ActiveAccount": "目前持有有效服務合約的 PayingCustomer", }

🧭 這一課的重點

系統互通有語法、結構、語意三層，最難的是語意：同詞異義、異詞同義。醫療術語、單位錯誤（火星氣候探測者號）、情報整合、搜尋歧義都源於此。Ontology 以共同詞彙、明確關係、約束與推理、可重用的概念，解決語意層的互通問題。

🕸️ 本課程的程式範例以 Python 為主（rdflib、owlready2 等），Turtle 與 SPARQL 以字串形式出現在 Python 中；Palantir 相關內容依公開資料整理，產品與財務資訊以撰寫時為準。

檢查你的理解

  1. 舉一個你工作或生活中「同一個詞，不同意思」的例子。
  2. 語法、結構、語意三種互通問題各舉一例。
  3. 為什麼光是統一欄位名稱，不能解決語意問題？
