常見的建模錯誤

這一課的目標

  • 辨認常見的建模錯誤
  • 理解剛性與 OntoClean 的檢查
  • 認識處理時間與變化的方法

錯誤一：把角色當成類別階層的一部分

「學生」「員工」「病人」「客戶」是角色：一個人可以開始或停止扮演它們。OntoClean（第 18 課）稱之為非剛性的。如果寫「學生 ⊑ 人」再寫「研究助理 ⊑ 學生 ⊓ 員工」還算合理；但寫「人 ⊑ 員工」或用「員工」當成某人唯一的類別，畢業或離職時就得改變他的類別，這是不對的。

較好的做法：角色可以是一個獨立的實體（某人在某段時間擔任某角色），或用「擔任」關係連結人與角色。

錯誤二：is-a 濫用

  • 部分當子類別：「引擎 ⊑ 汽車」。
  • 實例當子類別：「台北 ⊑ 城市」。
  • 「或」當子類別：「書或期刊」做成「書」的上層類別，再把期刊也放進去，結果階層亂成一團。
  • 用類別表示屬性值：「紅色的車」「藍色的車」「白色的車」……每種顏色一個子類別，不如用一個顏色屬性。

錯誤三：忽略時間與變化

「瑪麗 配偶 約翰」——什麼時候？離婚後這條三元組還成立嗎？RDF 的三元組本身沒有時間。常見的處理方法：

方法做法
具體化（第 8 課）把婚姻做成實體，加上開始與結束日期
命名圖（named graph）把一組三元組放進一個有名字的圖，再描述這個圖的有效時間
RDF-star讓三元組本身可以當作主詞，直接標註時間：<< :瑪麗 :配偶 :約翰 >> :自 2015 .
Wikidata 的限定詞每個陳述可以附加「開始時間」「結束時間」「來源」等限定詞（第 42 課）

錯誤四：混淆開放世界與封閉世界

期待 OWL 的 domain、基數限制幫你檢查資料（第 23、29 課）。結果資料有錯也不報錯，反而推出奇怪的結論。

錯誤五：沒有註解與定義

只有 IRI、沒有 rdfs:label 與 skos:definition，半年後連作者都不記得某個類別的意思。

from rdflib import Graph, Namespace, Literal from rdflib.namespace import XSD EX = Namespace("http://example.org/#") g = Graph() # RDF 1.2 / RDF-star 的寫法（rdflib 對 RDF-star 的支援依版本而定，這裡用具體化示範） m = EX.Marriage42 g.add((m, EX.partner, EX.Mary)); g.add((m, EX.partner, EX.John)) g.add((m, EX.validFrom, Literal("2015-06-20", datatype=XSD.date))) g.add((m, EX.validTo, Literal("2021-03-01", datatype=XSD.date)))

🧭 這一課的重點

常見建模錯誤：把非剛性的角色（學生、員工）放進類別階層，應改以角色實體或擔任關係表示；is-a 濫用，包括部分當子類別、實例當子類別、以子類別表示屬性值；忽略時間，可用具體化、命名圖、RDF-star 或 Wikidata 式限定詞處理；混淆開放與封閉世界；缺少註解與定義。

🕸️ 本課程的程式範例以 Python 為主（rdflib、owlready2 等），Turtle 與 SPARQL 以字串形式出現在 Python 中；Palantir 相關內容依公開資料整理，產品與財務資訊以撰寫時為準。
