Foundry 與前線部署工程師

這一課的目標

  • 認識 Foundry 平台的組成
  • 理解前線部署工程師（FDE）模式
  • 評估這種模式的優缺點

2010 年代，Palantir 把同樣的方法帶進企業：製造、能源、醫療、金融、航空。商業平台後來稱為 Foundry。

Foundry 的組成（簡化）

層功能
資料連接連到 ERP、MES、資料庫、檔案、串流、API 等數百種來源
資料整合Pipeline Builder（視覺化）、Code Repositories（Python／PySpark、SQL、Java）建立轉換管線；有版本與血緣追蹤
Ontology把整合後的資料對應成物件類型、屬性、連結；定義動作與函數
應用Workshop（低程式碼建應用）、Quiver（分析）、Contour（表格分析）、地圖等
AI模型整合與 AIP（第 62 課）
治理權限、標記、稽核、資料血緣
# Foundry 的資料轉換通常寫成 Python（PySpark）；以下是其轉換函式的寫法示意 from transforms.api import transform_df, Input, Output # Foundry 平台提供的套件 from pyspark.sql import functions as F @transform_df( Output("/Company/ontology/aircraft_status"), maintenance=Input("/Company/raw/mro_work_orders"), fleet=Input("/Company/raw/fleet_master"), ) def compute(maintenance, fleet): open_wo = (maintenance.filter(F.col("status") == "OPEN") .groupBy("tail_number").agg(F.count("*").alias("open_work_orders"))) return (fleet.join(open_wo, "tail_number", "left") .withColumn("available", F.coalesce(F.col("open_work_orders"), F.lit(0)) == 0)) # 這張輸出表接著被對應為 Ontology 中的「飛機」物件類型（每列一架、tail_number 為主鍵）

前線部署工程師（FDE）

Palantir 早期最有特色的做法，是派工程師直接進駐客戶現場，稱為前線部署工程師（Forward Deployed Engineer）。他們不只是安裝軟體，而是和客戶一起找出問題、整合資料、建立應用，再把在現場反覆出現的需求帶回產品。

優點缺點
真正解決客戶的問題，建立深厚關係成本高、毛利低，被批評「更像顧問公司」
產品從實戰中長出來（例如 Ontology 就是這樣成形的）擴張速度受限於人力
客戶黏著度高，一旦用上很難離開早期每個導入案都要很長時間才能看到成果

Palantir 後來的策略是把 FDE 的經驗不斷產品化，讓平台越來越能自助；2023 年的 AIP 訓練營（第 62 課）更把「幾個月的導入」壓縮成「幾天的實作」。FDE 這個職稱與模式，近年也被許多 AI 公司仿效。

🧭 這一課的重點

Foundry 把情報分析的方法帶進企業，由資料連接、整合管線（Pipeline Builder 與 Python／PySpark 程式碼庫）、Ontology、應用（Workshop、Quiver 等）、AI 與治理組成。前線部署工程師進駐客戶現場解決問題並把需求帶回產品，優點是深度與黏著度、產品從實戰成形，缺點是成本高、擴張慢。Palantir 持續將其產品化，並以 AIP 訓練營縮短導入時間。

🕸️ 本課程的程式範例以 Python 為主（rdflib、owlready2 等），Turtle 與 SPARQL 以字串形式出現在 Python 中；Palantir 相關內容依公開資料整理，產品與財務資訊以撰寫時為準。
