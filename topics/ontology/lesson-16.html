專家系統與知識獲取瓶頸

這一課的目標

  • 認識專家系統的架構與代表作
  • 理解知識獲取瓶頸
  • 從專家系統的失敗看 Ontology 的價值

1970～1980 年代，AI 從追求通用智慧，轉向解決特定領域的問題：把專家的知識寫成規則，讓電腦在狹窄的領域中做出專家級的判斷。這就是專家系統。

系統年代領域
DENDRAL1965 起從質譜資料推測有機分子結構
MYCIN1970 年代診斷血液感染並建議抗生素，約 600 條規則，表現接近專科醫師
XCON（R1）1980為迪吉多公司的 VAX 電腦配置訂單，據報每年省下數千萬美元

專家系統的架構

  • 知識庫：規則與事實。
  • 推理引擎：套用規則的程式（前向或後向推理）。
  • 解釋模組：說明「為什麼得到這個結論」——MYCIN 可以回答「為什麼你要問這個問題？」

知識獲取瓶頸

專家系統的最大問題不在推理，而在把知識放進去：

  • 專家很難把直覺說清楚，訪談耗時耗力。
  • 規則一多，彼此衝突、重複，維護變得非常困難（XCON 後期有上萬條規則）。
  • 每個系統都從頭建立自己的知識庫，無法共享與重用。
  • 系統很脆弱：遇到稍微超出範圍的情況就完全失效。

1980 年代後期，專家系統的商業市場崩潰，迎來 AI 的第二次寒冬。

教訓：知識需要能共享的結構

研究者反省：如果不同的系統能共用同一套對領域的概念化，就不必每次從頭開始。1991 年美國 DARPA 的知識共享計畫（Knowledge Sharing Effort）正是為此而生，它直接催生了格魯伯的本體定義與 Ontolingua 等早期本體工具（第 18 課）。

# 一個極簡的後向推理專家系統（MYCIN 風格） rules = [ ({"發燒", "頸部僵硬"}, "疑似腦膜炎"), ({"疑似腦膜炎", "革蘭氏陰性"}, "建議做腰椎穿刺並會診"), ] def prove(goal, facts, depth=0): if goal in facts: return True for conds, concl in rules: if concl == goal and all(prove(c, facts, depth + 1) for c in conds): print(" " * depth + f"由 {conds} 推得 {goal}") return True return False prove("建議做腰椎穿刺並會診", {"發燒", "頸部僵硬", "革蘭氏陰性"})

🧭 這一課的重點

專家系統把專家知識寫成規則，在狹窄領域表現出色，如 DENDRAL、MYCIN 與為迪吉多配置電腦的 XCON。架構包括知識庫、推理引擎與解釋模組。最大問題是知識獲取瓶頸：專家難以表述、規則衝突難維護、知識無法共享且系統脆弱，導致 1980 年代後期的 AI 寒冬。反省後的知識共享計畫，催生了可共享的本體概念。

🕸️ 本課程的程式範例以 Python 為主（rdflib、owlready2 等），Turtle 與 SPARQL 以字串形式出現在 Python 中；Palantir 相關內容依公開資料整理，產品與財務資訊以撰寫時為準。
