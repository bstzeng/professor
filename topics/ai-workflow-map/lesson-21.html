模組 D｜第三類：程式框架與 Agent SDK · 第 21 課

模組總結：什麼時候該從畫布走向程式碼

這一課的目標

  • 把四種框架類型的定位收成一張表
  • 掌握從平台轉向程式的四個訊號
  • 知道遷移時該先搬哪一部分

這個模組談了四類東西：通用框架與狀態圖、RAG導向框架、 官方 Agent SDK、多Agent框架。收尾時把它們放在同一張表上， 並回答遷移的問題。

1. 四類框架的定位

類型解決的核心問題代表
通用框架／狀態圖流程的分支、循環、狀態與中斷續跑LangChain／LangGraph
RAG導向框架資料接入、索引結構與查詢策略LlamaIndex、Haystack
官方 Agent SDK工具迴圈、脈絡管理、權限與可觀測性各模型供應商自家SDK
多Agent框架角色分工與協作編排CrewAI、AutoGen

2. 該轉向程式碼的四個訊號

  • 平台上的 Code 節點越來越多，畫布已經名存實亡
  • 需要自動化測試與版本控制，否則沒人敢改
  • 這個流程要成為對外產品的一部分
  • 成本或效能需要細緻控制（快取、批次、模型分級）

3. 遷移策略：不要一次全搬

最務實的做法是先搬處理層，後搬編排層：把最 複雜的AI步驟寫成一個有 API 的服務，讓平台去呼叫它。這時 你已經得到測試與版控的好處，而觸發與整合仍然享受平台的 便利。等到編排本身也變成瓶頸，再把流程搬進程式。這樣每 一步都可回退，不會停擺半年。

模組 D 重點回顧

  • 寫程式的四個理由：沒有天花板、可測試、可版控、可嵌入產品
  • 從鏈到圖：條件分支、循環、暫停等人，是Agent時代的必需品
  • 官方SDK貼合度高、第三方框架可移植性好；用薄介面折衷
  • 多Agent只在可平行、需對抗檢查、需脈絡隔離時才划算
  • 遷移先搬處理層，保留平台的觸發與整合優勢

檢查你的理解

  1. 說出四類框架各自解決的核心問題
  2. 背出該轉向程式碼的四個訊號
  3. 描述「先搬處理層」的遷移策略與它的好處
