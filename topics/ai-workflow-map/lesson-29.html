vLLM 與生產級推論服務

這一課的目標

  • 了解生產級推論服務解決的三個問題
  • 認識吞吐量與延遲之間的取捨
  • 知道什麼時候該從個人用工具升級到生產級方案

個人用的執行器假設一次一個人用。當你要讓 整個部門、或一個對外服務來用同一台機器，問題就完全不同了。

1. 生產級服務解決的三個問題

  • 併發：同時十個請求進來，不是排隊等，而是一起處理
  • 資源利用率：透過連續批次（continuous batching）與更聰明的記憶體管理，把昂貴的 GPU 榨乾
  • 穩定性：可監控、可水平擴充、可設定逾時與重試

vLLM 是這一類最常被提到的開源方案，其他還有 TGI、 SGLang、TensorRT-LLM 等，各有偏重。它們通常也提供 OpenAI 相容的 API 介面——這一點在模組 J 會說明為什麼重要。

2. 吞吐與延遲的取捨

批次處理能大幅提升每秒總產出（吞吐），但單一請求可能要 多等一點（延遲）。互動式聊天在意延遲，離線批次處理在意 吞吐。這是設定服務參數時最核心的取捨，也是你在寫需求 時應該先講清楚的一件事：這個流程是有人在等， 還是沒有人在等？

情境建議
一個人偶爾用個人執行器就好
小團隊共用、量不大個人執行器 + 簡單佇列，或直接用雲端 API
部門級、每天數萬次呼叫生產級推論服務
對外服務、有 SLA生產級推論服務 + 監控 + 備援

3. 別忘了算總帳

自架的成本不只是顯示卡：電力、機房或雲端 GPU 租用、 維運人力、模型更新的驗證工作，全部要算進去。實務上， 只有在量夠大、或資料真的不能外流時，自架的 總成本才會勝過雲端 API。這一點在模組 M 談成本 時會再展開。

檢查你的理解

  1. 說出生產級推論服務解決的三個問題
  2. 解釋吞吐與延遲的取捨，並判斷你的流程屬於哪一邊
  3. 列出自架方案總成本中，最容易被漏算的三項
