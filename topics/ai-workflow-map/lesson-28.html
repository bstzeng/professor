模組 F｜第五類：地端與自架方案 · 第 28 課

Ollama、LM Studio、llama.cpp：個人電腦上的模型執行器

這一課的目標

  • 認識三個常見的地端模型執行工具與各自的適用者
  • 了解量化、參數量與記憶體需求之間的關係
  • 知道地端執行在什麼任務上已經夠用

第五類是地端與自架方案。這一課從最基礎的一層開始： 怎麼在自己的機器上把模型跑起來。

1. 三個工具的定位

工具定位適合誰
llama.cpp底層推論引擎，效能與硬體支援的基礎要調到極致或嵌入自己程式的人
Ollama命令列＋本機 API，一行指令下載並執行模型要讓其他程式呼叫地端模型的人
LM Studio圖形介面，內建模型瀏覽與聊天想先用滑鼠試試看的人

對工作流來說，Ollama 這類提供本機 API 端點 的工具最關鍵——因為有了 API，模組 C 的自動化平台與模組 D 的程式框架才能呼叫它。這也是它常常成為地端工作流預設選擇 的原因。

2. 硬體門檻：三個數字的關係

能不能跑，主要看模型參數量、量化 程度與可用記憶體。粗略的心算方式： 4-bit 量化下，所需記憶體大約是參數量（以 B 為單位）的 0.6 到 0.8 倍 GB，再加上脈絡長度帶來的額外開銷。也就是說 8B 模型大概要 6GB 上下、70B 需要 40GB 以上——後者已經超出 多數個人電腦。

3. 量化：拿品質換可行性

量化是把模型權重的精度降低，換取更小的體積與更快的速度。 實務經驗是：4-bit 對多數任務影響可接受，再往下降（3-bit、 2-bit）品質衰退開始明顯，尤其在需要精確格式輸出或多步 推理的任務上。結論是：優先用「小一點但量化程度輕」 的模型，而不是「大很多但壓到極致」的模型。

4. 地端目前已經夠用的任務

  • 分類、標籤、情緒判斷這類短輸入短輸出的工作
  • 摘要與改寫（品質要求不極端的情況下）
  • 結構化擷取（從文字抓出欄位）——搭配好的提示與驗證
  • 作為RAG流程中的嵌入產生器

反過來，複雜推理、長篇創作、高難度程式撰寫，目前地端小 模型與雲端旗艦仍有明顯差距。混合使用是常態：敏感或高頻的 步驟走地端，困難的少數步驟走雲端。
