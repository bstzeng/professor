模組 C｜第二類：無碼／低碼自動化編排 · 第 12 課

Dify／Coze／Flowise／Langflow：以LLM為核心的應用建構器

這一課的目標

  • 分清楚「SaaS自動化平台」與「LLM應用建構器」的定位差異
  • 認識這類工具內建的四樣東西：知識庫、Agent、對話介面、API端點
  • 知道它們適合的產品形態與常見限制

同樣是拖拉節點，這一支的出發點完全不同。傳統自動化平台的 中心是「把A系統的資料送到B系統」；這一支的中心是 「做出一個以LLM為核心的應用」——例如一個 客服機器人、一個內部知識問答、一個文件處理助手。

1. 它們內建了什麼

  • 知識庫：上傳文件就自動完成切塊、嵌入與檢索，不用自己架向量資料庫（模組 G 會解釋這些名詞）
  • Agent 與工具：可以讓模型自己決定要呼叫哪個工具
  • 現成的對話介面：做完直接有一個可以分享的聊天網頁
  • API 端點：把整個應用包成 API 給別的系統呼叫

最後兩點是關鍵差異：傳統自動化平台的產出是「流程執行了」， 這類工具的產出是「一個可以給人用或給系統呼叫的 應用」。

2. 四個代表的側重

工具特色常見用途
Dify開源可自架，知識庫與應用發布完整企業內部知識問答、客服助手
Coze面向消費端的 bot 建構與平台分發社群機器人、個人助手
Flowise開源，貼近 LangChain 的節點化快速原型、把鏈式流程視覺化
Langflow開源，同樣是框架的視覺化外殼實驗不同的檢索與Agent結構

3. 常見限制

第一，簡單的事非常快，複雜的事很快撞牆—— 當你的需求超出平台的抽象，往往得整個搬到程式框架重做。 第二，版本控制與測試薄弱——流程存在平台 的資料庫裡，不容易做 code review 與自動化測試。第三， 抽象洩漏——出問題時你仍然需要理解底下的 切塊、檢索、prompt 到底發生什麼事，否則只能亂調參數。

選型提示

如果你的目標是「把AI塞進既有的公司流程」，選前一課的 自動化平台；如果目標是「做出一個獨立的AI應用給人用」， 選這一類。兩者也常常一起用：用 Dify 做知識問答應用， 再用 n8n 在特定事件時呼叫它的 API。
