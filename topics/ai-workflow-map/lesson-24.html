模組 E｜第四類：AI編碼工作流 · 第 24 課

終端／代理型：Claude Code、Codex、Aider、Cline

這一課的目標

  • 了解終端型工具的互動模型與它擅長的任務
  • 認識「可被腳本呼叫」為什麼是這一類的關鍵優勢
  • 知道使用代理型工具時必要的三道安全閘門

另一支路線不進編輯器，而是住在終端機裡：你在命令列描述 任務，它自己讀檔、改檔、跑測試、給出結果。Claude Code、 Codex 系列、Aider、Cline 都屬於這一族（有些同時提供 編輯器擴充）。

1. 互動模型的差異

IDE型的預設是「你在寫，AI 幫你」；終端型的預設是 「AI 在做，你在審」。你給的是任務層級的 描述，收到的是一組改動與執行結果。這讓它特別適合： 跨檔案的重構、依照錯誤訊息修 bug、把一個規格實作出來、 以及大量重複性的機械修改。

2. 關鍵優勢：可以被腳本呼叫

因為它是命令列工具，所以能被寫進 script、排程、CI，或是 被模組 C 的自動化平台觸發。這一步把「AI寫程式」從互動 行為變成工作流的一個節點——例如每天自動 檢查相依套件更新並開出修正、或是收到某類錯誤告警時 自動嘗試定位問題。這是本課程視角下最重要的一點。

3. 三道必要的安全閘門

閘門做法
版本控制永遠在乾淨的 git 狀態下開始，改動可一鍵回退
權限邊界限制可執行的指令範圍，破壞性操作要人工確認
審查不管它多有信心，合併前一定看 diff、跑測試

提示注入在這裡也成立

代理型工具會讀取程式碼、issue 內容、網頁文件、CI 日誌 ——這些都是外部輸入。一段藏在第三方套件 README 或 issue 留言裡的指令，理論上可以誘導代理做出非預期的事。 所以權限邊界不是為了防AI犯錯，也是為了防外部內容 借AI之手。模組 N 會完整展開。

檢查你的理解

  1. 說明IDE型與終端型在互動預設上的差異
  2. 解釋「可被腳本呼叫」為什麼讓編碼AI變成工作流的一環
  3. 列出三道安全閘門，並說明各自防的是什麼
