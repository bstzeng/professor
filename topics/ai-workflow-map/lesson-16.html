模組 D｜第三類：程式框架與 Agent SDK · 第 16 課

為什麼有了平台還是有人要寫程式

這一課的目標

  • 了解程式框架解決的是平台解不了的哪四件事
  • 認識「AI功能」與「AI產品」在工程要求上的差距
  • 知道框架本身其實是薄的，價值在哪裡

第三類工作流是用程式寫的。既然平台一小時就能做出可動的 流程，為什麼還有大量團隊選擇寫程式？答案不是「工程師比較 愛炫技」，而是四件平台做不到的事。

1. 四個不可取代之處

能力為什麼平台做不好
沒有天花板任何邏輯都能寫，不受平台抽象限制
可測試單元測試、回歸測試、評測集都能自動跑在 CI 上
可版控Git、code review、回滾、分支——工程協作的基礎設施
可嵌入產品流程要成為你賣的東西的一部分，就得住在你的程式碼庫裡

2. 「AI功能」與「AI產品」的差距

內部用的AI功能，出錯了大不了自己重跑一次；對外的AI產品， 每天有幾千個使用者、每個錯誤都是客訴。後者需要的東西 ——錯誤預算、灰度發布、A／B 測試、成本監控、審計紀錄 ——本質上就是軟體工程的一整套設施。這是選擇寫程式最 核心的理由。

3. 框架其實很薄，價值在哪

很多人第一次讀框架的原始碼會失望：所謂的「鏈」不過是 把幾次 API 呼叫串起來，自己寫也就幾十行。這個觀察是對的。 框架真正的價值在三個地方：統一的抽象 （換模型、換向量庫不用改流程）、現成的整合 （幾十種文件載入器、資料庫接口）、以及周邊工具 （追蹤、除錯、評測）。當你的專案很小，這些價值不明顯； 當它長大，重寫這些東西的成本會遠高於學一個框架。

務實的建議

不要為了「用框架」而用框架。最健康的路徑通常是：先用 官方 SDK 直接呼叫模型，把流程寫出來；當你發現自己開始 重複造輪子（重試邏輯、脈絡管理、工具註冊、追蹤）， 再引入框架。反過來——一開始就套上一層厚重抽象——常常 讓你連「模型到底收到什麼 prompt」都看不到。

檢查你的理解

  1. 說出程式框架相對平台的四個不可取代之處
  2. 解釋「AI功能」與「AI產品」在工程要求上的差距
  3. 說明框架的三個真正價值，以及什麼時候才需要它
