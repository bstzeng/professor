Search in Rotated Sorted Array II
搜尋旋轉排序陣列 II

Medium · 中等 陣列 二分搜尋

Problem

There is an integer array nums sorted in non-decreasing order (not necessarily with distinct values). Before being passed to your function, nums is rotated at an unknown pivot index.

Given the array nums after the rotation and an integer target, return true if target is in nums, or false if it is not.

Follow up: This problem is similar to Search in Rotated Sorted Array, but nums may contain duplicates. Would this affect the runtime complexity? How and why?

中文翻譯

有一個非遞減排序的整數陣列 nums（可能有重複的值），它在某個未知的位置被旋轉過。

給你旋轉之後的陣列和一個 target，判斷 target 在不在裡面。

進階：這題和第 33 題很像，但 nums 可能有重複值。這會影響複雜度嗎？為什麼？

重複值破壞了什麼？

第 33 題的核心判斷： nums[lo] <= nums[mid] -> 左半段 [lo, mid] 有序 在「所有值互不相同」的前提下，這個推論是對的。 但有重複值時它失效了： nums = [1, 1, 1, 0, 1] 斷點在 mid 右邊 nums = [1, 0, 1, 1, 1] 斷點在 mid 左邊 兩者的 lo=0, mid=2, hi=4 位置上的值【完全一樣】： nums[0] = 1, nums[2] = 1, nums[4] = 1 所以 nums[lo] <= nums[mid] 在兩種情況下都成立， 但「左半有序」只在第一種情況下為真 ✘ 唯一的補救： 當 nums[lo] == nums[mid] == nums[hi] 時， 我們無法判斷 —— 只好放棄這兩個端點： lo += 1 hi -= 1 這是安全的，因為 nums[lo] == nums[mid] != target （如果等於 target，上面的 nums[mid] == target 就回傳了）。 但它只縮小了 2 格而不是一半 —— 最壞情況（全部相同）退化成 O(n)。

而且 O(n) 是不可避免的。考慮 [1,1,1,...,1] 裡藏了一個 0 —— 任何演算法都必須在最壞情況下檢查幾乎每一格才能確定。「有重複值」這個條件，從根本上摧毀了 O(log n) 的可能性。

範例

範例 1 輸入：nums = [2,5,6,0,0,1,2], target = 0 輸出：true 範例 2 輸入：nums = [2,5,6,0,0,1,2], target = 3 輸出：false

限制條件

  • 1 ≤ nums.length ≤ 5000
  • −10⁴ ≤ nums[i] ≤ 10⁴
  • nums 是一個非遞減陣列旋轉後的結果（可能有重複值）
  • −10⁴ ≤ target ≤ 10⁴

LeetCode 原題

先看懂限制在說什麼

  • 可能有重複值 —— 這是和第 33 題唯一的差別，但它把複雜度從「保證 O(log n)」降成「平均 O(log n)、最壞 O(n)」。
  • 只要回傳 true/false（不用回傳索引）。這讓題目簡單一點 —— 因為有重複值時，「哪一個索引」本來就不唯一。
  • n ≤ 5000，所以就算退化成 O(n) 也完全跑得動。題目的重點是「你知不知道會退化，以及為什麼」。

解題思路

解法一

第 33 題 + 一個「無法判斷」的分支（標準解）

class Solution: def search(self, nums: List[int], target: int) -> bool: lo, hi = 0, len(nums) - 1 while lo <= hi: mid = (lo + hi) // 2 if nums[mid] == target: return True if nums[lo] == nums[mid] == nums[hi]: # 三個都一樣 -> 看不出哪一半有序，只好兩端各縮一格 lo += 1 hi -= 1 elif nums[lo] <= nums[mid]: # 左半段 [lo, mid] 有序 if nums[lo] <= target < nums[mid]: hi = mid - 1 else: lo = mid + 1 else: # 右半段 [mid, hi] 有序 if nums[mid] < target <= nums[hi]: lo = mid + 1 else: hi = mid - 1 return False

三個分支的優先順序

1. nums[lo] == nums[mid] == nums[hi] -> 無法判斷，兩端各縮一格 2. nums[lo] <= nums[mid] -> 左半段有序（此時已經排除了「三個都相同」，所以推論成立） 3. else -> 右半段有序 第 1 個分支【必須放在最前面】。 如果放在後面，分支 2 會先被觸發並做出錯誤的判斷。 為什麼「三個都相同」才需要放棄？ 只要 nums[lo] != nums[mid] 或 nums[mid] != nums[hi]， 至少有一邊能確定是有序的： nums[lo] < nums[mid] -> 左半一定有序（沒有斷點） nums[lo] > nums[mid] -> 左半一定有斷點 -> 右半有序 nums[lo] == nums[mid] 但 nums[mid] != nums[hi] -> 此時 nums[mid] != nums[hi]，右半的資訊是有效的 -> 走 else 分支判斷右半 嚴格說，只檢查 nums[lo] == nums[mid] == nums[hi] 是「最保守」的做法， 有些實作只檢查 nums[lo] == nums[mid]（也對，但剪得少一點）。

為什麼 lo += 1; hi -= 1 是安全的？

此時 nums[lo] == nums[mid] == nums[hi]， 而且我們已經確認 nums[mid] != target（不然上面就 return True 了）。 所以： nums[lo] == nums[mid] != target -> lo 這一格不可能是答案，可以丟 nums[hi] == nums[mid] != target -> hi 這一格也可以丟 丟掉兩格，區間縮小 2。 注意這裡不能寫成「lo = mid + 1」或「hi = mid - 1」—— 因為我們不知道 target 在哪一半，不能丟掉一整半。

解法二

先剝掉兩端的重複值，再二分

另一種組織方式：在每一輪二分之前，先把左右兩端「和鄰居相同」的值剝掉。

class Solution: def search(self, nums: List[int], target: int) -> bool: lo, hi = 0, len(nums) - 1 while lo <= hi: # 先把左右兩端「和端點相同」的重複值剝掉，再做二分 while lo < hi and nums[lo] == nums[lo + 1]: lo += 1 while lo < hi and nums[hi] == nums[hi - 1]: hi -= 1 mid = (lo + hi) // 2 if nums[mid] == target: return True if nums[lo] <= nums[mid]: if nums[lo] <= target < nums[mid]: hi = mid - 1 else: lo = mid + 1 else: if nums[mid] < target <= nums[hi]: lo = mid + 1 else: hi = mid - 1 return False

效果和解法一相同，但邏輯上「先清理、再判斷」比較分明。

複雜度也一樣（最壞 O(n)）—— 因為剝重複值本身就可能要剝 O(n) 次。

要小心內層 while 的條件是 lo < hi（不是 <=），否則 lo 可能衝過 hi，然後 nums[lo + 1] 越界。

兩種寫法挑一個記熟就好。解法一比較常見，而且只多一個分支（相對第 33 題的改動最小）。

複雜度說明
時間平均 O(log n)，最壞 O(n)同上
空間O(1)同上

邊界條件檢查清單

  • 全部相同且找得到：([1,1,1,1], 1) → true。第一次 mid 就命中。
  • 全部相同且找不到：([1,1,1,1], 2) → false。這是 O(n) 退化的極端情況。
  • 重複值藏住斷點：([1,0,1,1,1], 0) → true；([1,1,1,0,1], 0) → true。沒有「三端相同」分支的話，這兩筆會有一筆失敗。
  • 單一元素：([1], 1) → true；([1], 0) → false。
  • 兩個元素：([3,1], 1) → true。驗證 <= vs <（和第 33 題一樣）。
  • 沒有旋轉：([1,2,3], 2) → true。退化成普通二分。
  • 剝重複值時越界：內層 while 的條件寫成 lo <= hi 會 IndexError。

常見追問

追問一：為什麼 O(n) 是不可避免的？

對抗性論證（adversary argument）： 考慮 nums = [1, 1, 1, ..., 1]（n 個 1）中， 把其中一個換成 0，然後旋轉。 target = 0 任何演算法在檢查了 k 個位置之後， 如果那 k 個位置都是 1，它還是不知道 「剩下的 n - k 個位置裡有沒有 0」。 對手（adversary）可以一直宣稱「還沒檢查的某一格是 0」， 直到演算法檢查完所有位置為止。 所以最壞情況需要 Ω(n) 次比較。 這是一個很乾淨的下界證明 —— 它說明「有重複值時 O(log n) 不可能」， 而不只是「我們想不出更好的演算法」。

追問二：那為什麼還要寫二分而不是直接線性掃？

因為平均情況快很多。只有在「大量重複值」的病態輸入上才會退化 —— 而真實資料通常不是那樣。

這是一個很常見的工程取捨：

  • 快速排序：平均 O(n log n)，最壞 O(n²)，但實務上最快
  • 雜湊表：平均 O(1)，最壞 O(n)，但實務上無可取代
  • 本題：平均 O(log n)，最壞 O(n)

「最壞情況保證」和「平均效能」是兩個不同的目標 —— 在即時系統或對抗性環境（例如可能被攻擊的伺服器）裡選前者，在一般應用裡選後者。

追問三：如果要回傳「所有出現的索引」呢？

那本質上就是 O(出現次數)，而且要先找到「任一個」再往兩邊擴散。在全部相同的情況下就是 O(n) —— 無法避免。

追問四：第 154 題（找旋轉陣列的最小值 II）有同樣的問題嗎？

有，而且處理方式類似。第 153 題（無重複）可以穩定 O(log n)；第 154 題（有重複）在 nums[mid] == nums[hi] 時無法判斷，只能 hi -= 1，最壞退化成 O(n)。

四題放在一起看，會發現「重複值」對二分搜尋的影響是系統性的：

第 33 題 搜尋旋轉陣列（無重複） O(log n) 第 81 題 搜尋旋轉陣列（有重複） 最壞 O(n) 第 153 題 找最小值（無重複） O(log n) 第 154 題 找最小值（有重複） 最壞 O(n) 共同的原因： 二分搜尋依賴「能從 O(1) 的資訊判斷答案在哪一半」。 重複值讓那個判斷失效。
