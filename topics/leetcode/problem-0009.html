LeetCode 9

Palindrome Number
回文數

Easy · 簡單 數學

Problem

Given an integer x, return true if x is a palindrome, and false otherwise.

Follow up: Could you solve it without converting the integer to a string?

中文翻譯

給你一個整數 x，如果它是回文數就回傳 true，否則回傳 false。

回文數的意思是：正著讀和倒著讀都一樣。例如 121 是，−121 不是（倒過來是 121−）。

進階：能不能不把整數轉成字串就解出來？

三個一秒判定的特例

1. 負數 -> 永遠 False -121 倒過來是 "121-"，'-' 只能在左邊，不可能對稱。 2. 結尾是 0 且不是 0 本身 -> 永遠 False 10 倒過來是 01 = 1 ≠ 10 100 倒過來是 001 = 1 ≠ 100 因為正整數沒有前導零，結尾是 0 就表示開頭該是 0 —— 矛盾。 3. 0 本身 -> True 唯一結尾是 0 卻成立的數，所以第 2 條一定要寫 "and x != 0"。

這三條寫在最前面，剩下的邏輯會乾淨很多。特別是第 2 條，它是「只反轉一半」那個解法能夠終止得漂亮的關鍵。

範例

範例 1 輸入：x = 121 輸出：true 範例 2 輸入：x = -121 輸出：false 說明：從左讀是 -121，從右讀是 121-，不一樣。 範例 3 輸入：x = 10 輸出：false 說明：從右讀是 01，不等於 10。

限制條件

  • −2³¹ ≤ x ≤ 2³¹ − 1

LeetCode 原題

先看懂限制在說什麼

  • 範圍就是 32 位元有號整數，最多 10 位數 —— 所以任何 O(位數) 的解法都是 O(1) 等級，快得不得了。
  • 但「不轉字串」這個 follow-up 才是真正的考點。如果只寫 str(x) == str(x)[::-1]，面試通常到此為止，不會加分。
  • 注意：反轉整個數字可能溢位（第 7 題的問題）。所以「只反轉一半」不只是優化，在 32 位元環境裡是正確性的需求。

解題思路

解法想法轉字串？會溢位？
一、字串反轉s == s[::-1]會不會
二、整數全反轉反轉後和原值比不會在 C/Java 會
三、只反轉一半反轉到中點就停，兩半相比不會不會
解法一

轉成字串比對（最短，但答不到 follow-up）

class Solution: def isPalindrome(self, x: int) -> bool: s = str(x) return s == s[::-1]

str(-121) 是 "-121"，反轉後 "121-"，不相等 —— 所以連負數都不用特別擋，這個解法自動就對了。

兩行、絕對正確、LeetCode 上 0 ms。但題目白紙黑字寫了 follow-up，所以面試時這只能當開場，不能當結尾。

複雜度說明
時間O(log x)位數 = log₁₀x
空間O(log x)字串本身
解法二

反轉整個整數再比（會有溢位隱憂）

class Solution: def isPalindrome(self, x: int) -> bool: if x < 0: return False # 負數一定不是：'-' 只出現在左邊 original, rev = x, 0 while x: rev = rev * 10 + x % 10 x //= 10 return rev == original

邏輯很直白，Python 裡完全正確。

但在 C 或 Java 裡它是錯的

x = 1999999999 （不是回文） 反轉後 = 9999999991 > INT_MAX = 2147483647 在 32 位元環境裡，rev 會環繞成一個垃圾值。 碰巧的話它甚至可能等於某個 x，讓你得到錯誤的 true。 要修就得加上第 7 題那套溢位檢查 —— 但那樣就比解法三還長了。

這就是解法三存在的理由：只反轉一半，rev 的位數永遠不會超過 x 原本的一半，溢位問題從根本上消失。

複雜度說明
時間O(log x)位數次迴圈
空間O(1)幾個整數變數
解法三

只反轉後半段（進階解答）

回文的定義是「前半段 == 後半段反過來」。既然如此，根本不需要反轉整個數字 —— 把後半段反轉出來，跟剩下的前半段比就行了。

class Solution: def isPalindrome(self, x: int) -> bool: # 負數不是回文；結尾是 0 的也不是（除了 0 本身） # 因為那表示開頭必須是 0，而正整數不會有前導零 if x < 0 or (x % 10 == 0 and x != 0): return False rev = 0 while x > rev: # 只反轉一半就停 rev = rev * 10 + x % 10 x //= 10 # 偶數位：x 和 rev 剛好一樣長 -> x == rev # 奇數位：rev 多吃了正中間那一位 -> 砍掉它再比 return x == rev or x == rev // 10

終止條件 while x > rev 為什麼對？

每跑一輪，x 少一位、rev 多一位。所以 x 單調變小、rev 單調變大，一定會交會，迴圈保證終止。交會點就是中點：

位數為偶數（1221，4 位）： 跑 2 輪後 x = 12（前半）、rev = 12（後半反轉） 兩者位數相同 → 直接比 x == rev 位數為奇數（12321，5 位）： 跑 3 輪後 x = 12、rev = 123 rev 多吃了正中間的 '3' 但正中間那一位在回文裡「跟自己對稱」，怎樣都成立 → 砍掉它 比 x == rev // 10 → 12 == 12 ✔ 所以最後一行要寫成： return x == rev or x == rev // 10 兩種情況各對應一個條件，用 or 一次涵蓋。

為什麼一定要先擋「結尾是 0」？

假設不擋，看 x = 10： 輪 0： x = 10, rev = 0 10 > 0 → 跑 輪 1： x = 1, rev = 0 1 > 0 → 跑 （rev = 0*10 + 0 = 0，還是 0！） 輪 2： x = 0, rev = 1 0 > 1 不成立 → 停 檢查：x == rev ? 0 == 1 ✘ x == rev // 10 ? 0 == 0 ✔ → 回傳 True 錯了！10 不是回文。 根本原因：後半段的前導零在反轉時「消失」了， 導致 rev 的位數比預期少，中點判斷跟著失準。 先擋掉 x % 10 == 0（且 x != 0）就完全避開這個坑。

這個坑是這題最值得記的地方。它不是隨便的邊界檢查，而是「數字反轉會吃掉前導零」這個性質造成的必然結果。

複雜度說明
時間O(log x)只跑一半的位數
空間O(1)兩個整數變數

邊界條件檢查清單

  • 負數：-121、-1 → false。-0 在整數裡就是 0，不用擔心。
  • 0 → true。第 2 條特例的 and x != 0 就是為了它。
  • 結尾是 0：10、100、1000021 → false。解法三沒擋會錯。
  • 單一位數：0～9 → 全部 true。
  • 偶數位回文：1221、11 → true。走 x == rev 分支。
  • 奇數位回文：121、12321 → true。走 x == rev // 10 分支。
  • 接近上界：2147483647 → false；1410110141 → true。

常見追問

追問一：如果是十六進位或任意 base 的回文呢？

把所有的 10 換成 base 就好，邏輯完全不變。有趣的是：一個數可能在 base 10 是回文、在 base 2 不是（例如 121₁₀ = 1111001₂，不是回文），而 585 在兩種進位下都是回文（585₁₀ = 1001001001₂）。

追問二：要找「最接近 x 的回文數」呢？

第 564 題（Find the Closest Palindrome），難度陡增。核心想法是：拿前半段去鏡射出後半段，再考慮「前半段 ±1 後鏡射」以及 99...9 和 10...01 這兩個跨位數的候選，最後在這幾個候選裡挑最近的。

追問三：為什麼「只反轉一半」在系統程式裡是個有用的模式？

因為它體現了一個通則：不要算出你不需要的東西。反轉整個數字會製造一個可能溢位的中間值，而我們根本不需要那個值。同樣的想法出現在：檢查兩個大數是否相等時先比長度、比較浮點數時避免相減、判斷連結串列有沒有環時用快慢指標而不是全部存起來。
