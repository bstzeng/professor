LeetCode 1

Two Sum
兩數之和

Easy · 簡單 陣列 雜湊表

Problem

Given an array of integers nums and an integer target, return the indices of the two numbers that add up to target.

You may assume that each input has exactly one solution, and you may not use the same element twice. You can return the answer in any order.

中文翻譯

給你一個整數陣列 nums 和一個整數 target， 請回傳兩個數字的索引，使這兩個數字相加等於 target。

你可以假設每一組輸入恰好只有一組解， 而且同一個元素不能重複使用。 答案的順序不限。

範例

範例 1 輸入：nums = [2, 7, 11, 15], target = 9 輸出：[0, 1] 說明：nums[0] + nums[1] == 9，所以回傳 [0, 1]。 範例 2 輸入：nums = [3, 2, 4], target = 6 輸出：[1, 2] 範例 3 輸入：nums = [3, 3], target = 6 輸出：[0, 1] 說明：兩個 3 是不同的元素，允許使用。

限制條件

  • 2 ≤ nums.length ≤ 10⁴
  • −10⁹ ≤ nums[i] ≤ 10⁹
  • −10⁹ ≤ target ≤ 10⁹
  • 保證恰好存在一組解

LeetCode 原題

先看懂限制在說什麼

  • n ≤ 10⁴：O(n²) 是 10⁸ 次運算，在 LeetCode 上剛好會過但很慢。這題的重點不是「能不能過」，是「知不知道怎麼變成 O(n)」。
  • 數值可以是負數：不能用「只找比 target 小的數」這種假設。
  • 要回傳索引，不是數值：任何會打亂順序的做法（例如排序）都必須額外保留原本的索引。
  • 同一個元素不能用兩次：nums = [3, 3], target = 6 可以，但 nums = [3], target = 6 不行——這個區別會影響雜湊表解法的寫法。

解題思路

這題的核心轉換只有一句話： 與其問「哪兩個數加起來等於 target」，不如問「對每個數 x，另一個需要的 target − x 在不在？」

前者要兩兩配對，是 O(n²)； 後者是 n 次「查表」，而查表如果是 O(1)，整體就是 O(n)。 下面四種解法就是沿著這條路一步一步走過來的。

解法一

暴力雙迴圈

最直接的想法：枚舉所有的配對 (i, j)，檢查是否相加等於 target。

class Solution: def twoSum(self, nums: List[int], target: int) -> List[int]: n = len(nums) for i in range(n): for j in range(i + 1, n): # j 從 i+1 開始，避免重複使用同一個元素 if nums[i] + nums[j] == target: return [i, j] return []

j 從 i + 1 開始有兩個作用： 避免把同一個元素用兩次（i == j）， 也避免把 (0,1) 和 (1,0) 算成兩組。

複雜度說明
時間O(n²)共檢查 n(n−1)/2 組配對
空間O(1)只用了幾個變數

為什麼慢：對每一個 nums[i]，我們都重新掃描了一次陣列去找 target − nums[i]。 這個「找」的動作是 O(n)，而且前面掃過的資訊完全沒有被記下來—— 下一輪又要從頭再找一次。

接下來三種解法，都是在回答同一個問題： 怎麼把「找」這個動作變快？

解法二

排序 + 雙指標

如果陣列是排好序的，找「兩數之和等於 target」有一個經典技巧： 左右各放一個指標，看兩端的和。

  • 和太小 → 左指標往右移（換一個更大的數）
  • 和太大 → 右指標往左移（換一個更小的數）
  • 剛好 → 找到了

但這題要回傳的是索引，不是數值。 排序會打亂順序，所以必須把「數值 + 原本的索引」綁在一起排。

class Solution: def twoSum(self, nums: List[int], target: int) -> List[int]: # 把 (數值, 原索引) 綁在一起排序，排完才不會弄丟索引 pairs = sorted((v, i) for i, v in enumerate(nums)) lo, hi = 0, len(pairs) - 1 while lo < hi: s = pairs[lo][0] + pairs[hi][0] if s == target: return sorted([pairs[lo][1], pairs[hi][1]]) if s < target: lo += 1 else: hi -= 1 return []
複雜度說明
時間O(n log n)排序主導；雙指標本身只有 O(n)
空間O(n)存 (值, 索引) 的新陣列

比暴力法好，但還不是最好。 它比解法四多了一個 log n，而且空間也沒有省下來。

那為什麼還要學它？因為這個技巧在題目不要求回傳索引、 或陣列本來就有序時是最佳解，而且它能自然推廣到三數之和（15 題）、 四數之和（18 題）。這題只是它的一個「用不太上」的場合。

解法三

雜湊表：兩趟

回到那句核心轉換：我們想要的是「給一個數值，O(1) 查出它的索引」。 這正是 Python dict 的工作。

第一趟：把所有 數值 → 索引 存進字典。
第二趟：對每個 nums[i]，查 target − nums[i] 在不在。

class Solution: def twoSum(self, nums: List[int], target: int) -> List[int]: pos = {v: i for i, v in enumerate(nums)} # 第一趟：建表 for i, v in enumerate(nums): # 第二趟：查表 j = pos.get(target - v) if j is not None and j != i: # j != i：不能用到自己 return [i, j] return []

兩個容易踩的坑

  • j != i 不能省。如果 nums = [3, 2, 4], target = 6， 走到 i = 0（值 3）時，target − 3 = 3，查表查到的是它自己。 沒有這個檢查就會回傳 [0, 0]。
  • 重複數值會互相覆蓋。{v: i for ...} 遇到 nums = [3, 3] 時， 後面的 3 會蓋掉前面的，字典裡只剩 {3: 1}。 幸好這正好救了我們：i = 0 時查到 j = 1，j != i 成立，答案正確。 但這是碰巧——解法四不需要依賴這種巧合。
複雜度說明
時間O(n)兩趟線性掃描，字典操作平均 O(1)
空間O(n)字典最多存 n 筆
解法四 · 最佳解

雜湊表：一趟

解法三其實做了多餘的事。想一想：當我們走到位置 i 時， 要找的配對一定在 i 之前或之後。 如果它在之後，那等我們走到那個位置時，i 就變成「在之前」了。

所以只要往回找就夠了——而「往回」的資料，我們可以邊走邊記。

class Solution: def twoSum(self, nums: List[int], target: int) -> List[int]: seen = {} # 數值 -> 索引，只存「已經走過」的元素 for i, v in enumerate(nums): need = target - v if need in seen: # 先查：需要的數之前出現過嗎？ return [seen[need], i] seen[v] = i # 再記：把自己存進去 return []

「先查後記」的順序是關鍵

如果顛倒成「先 seen[v] = i 再查」，那麼當 target == 2 * v 時 （例如 nums = [3, 2, 4], target = 6）， 第一個 3 會先把自己存進去，然後立刻查到自己，回傳 [0, 0]。

維持「先查後記」，就結構上保證了查到的一定是不同的元素—— 不需要像解法三那樣額外寫 j != i。

四種解法對照

注意時間與空間的交換：從 O(n²)/O(1) 換到 O(n)/O(n)。 我們用一個最多 n 筆的字典，買到了 n 倍的速度。 這是演算法題裡最常見的一種交易，而且幾乎總是划算的—— 因為記憶體便宜，時間不便宜。

邊界條件檢查清單

情況輸入正確輸出哪個解法會出錯
重複數值[3, 3], 6[0, 1]字典建表若不處理重複會漏
需要的數等於自己[3, 2, 4], 6[1, 2]解法三漏寫 j != i；解法四順序寫反
含 0 與重複的 0[0, 4, 3, 0], 0[0, 3]用 if pos.get(x): 判斷會誤判（0 是 falsy）
全負數[-1,-2,-3,-4,-5], -8[2, 4]假設數值為正的解法
最小長度[1, 2], 3[0, 1]邊界索引處理

第三列特別容易錯

pos.get(x) 在查不到時回傳 None，查到索引 0 時回傳 0。 而 None 和 0 在 if 判斷裡都是假值。

j = pos.get(target - v) if j: # ✘ 索引剛好是 0 時會被當成「沒找到」 ... if j is not None: # ✔ 正確 ...

這是 Python 特有的陷阱，在 [0, 4, 3, 0], target = 0 這組測資會直接現形。

常見追問

如果有多組解，要全部回傳呢？

那就不能一找到就 return。而且字典要改成 值 → 索引清單，因為同一個值可能出現多次。

from collections import defaultdict def all_two_sums(nums, target): seen = defaultdict(list) result = [] for i, v in enumerate(nums): for j in seen[target - v]: # 所有之前出現過、值為 need 的位置 result.append([j, i]) seen[v].append(i) return result

如果陣列已經排好序呢？

那就用解法二的雙指標，O(n) 時間、O(1) 空間—— 比雜湊表還好，因為省下了字典的空間。 這正是 167. Two Sum II 那一題的設定。

雜湊表的 O(1) 是保證的嗎？

不是，是平均 O(1)。最壞情況（所有鍵雜湊到同一個桶）會退化成 O(n)， 整體變成 O(n²)。實務上 Python 的 dict 對整數鍵表現很好， 但在刻意構造的測資下（某些競賽平台會這麼做）確實可能被卡。 這題不會。
