模組 B｜工具使用 · 第 11 課

設計好工具

這一課的目標

  • 掌握工具命名與說明的原則
  • 決定工具的粒度
  • 讓工具回傳精簡、有用的結果

代理表現好不好，很大一部分取決於工具設計。Anthropic 的經驗是：花在工具上的心力，常常比花在提示上的更值得。幾個原則：

  • 命名清楚：動詞＋名詞，如 search_orders，不要叫 do 或 tool1。
  • 說明完整：做什麼、什麼時候該用（和什麼時候不該用）、回傳什麼、有什麼限制。
  • 參數有說明：特別是格式（日期、單位、大小寫）；可選值用 enum 列出。
  • 粒度適中：一個工具做一件事；但也別拆得太碎，讓模型要呼叫十次才能完成一件常見的事。
  • 回傳精簡：只回傳模型需要的欄位；過長的結果要截斷或分頁，別把五萬字的原始 JSON 全丟回去。
  • 數量節制：工具太多會讓模型選錯；把相關功能整合，或用工具搜尋按需載入。

🐍 Python 範例（離線版）　下載 b11_tool_design.py　需同資料夾的 mockllm.py

寫一個「工具定義檢查器」，對一個壞工具和一個好工具打分數。

# -*- coding: utf-8 -*- """第 11 課：好工具 vs 壞工具。用一個簡單的「檢查器」幫工具定義打分數。""" def lint_tool(t): issues = [] d = t.get("description", "") if len(d) < 20: issues.append("描述太短：要說明『做什麼、何時用、回傳什麼』") if not t["name"].replace("_", "").isalnum() or t["name"] in ("do", "run", "tool", "process"): issues.append("名稱太模糊：用動詞＋名詞，如 search_orders") props = t["input_schema"].get("properties", {}) for k, v in props.items(): if "description" not in v and "enum" not in v: issues.append("參數 %s 沒有說明" % k) if v.get("type") == "string" and any(w in k for w in ("date", "time")) and "format" not in v and "格式" not in v.get("description", ""): issues.append("參數 %s 沒說日期格式" % k) if len(props) > 6: issues.append("參數太多（%d 個）：考慮拆成多個工具" % len(props)) if "required" not in t["input_schema"]: issues.append("沒有標出必填參數") return issues bad = {"name": "do", "description": "查東西", "input_schema": {"type": "object", "properties": {"q": {"type": "string"}, "date": {"type": "string"}}}} good = {"name": "search_orders", "description": "依客戶 email 與日期區間搜尋訂單，回傳訂單編號、金額與狀態的清單（最多 20 筆）。客戶詢問訂單狀況時使用。", "input_schema": {"type": "object", "properties": { "email": {"type": "string", "description": "客戶 email"}, "start_date": {"type": "string", "description": "起始日期，格式 YYYY-MM-DD"}, "status": {"type": "string", "enum": ["pending", "shipped", "delivered"]}}, "required": ["email"]}} for t in (bad, good): issues = lint_tool(t) print("%-14s 分數 %d/10" % (t["name"], max(0, 10 - 2 * len(issues)))) for i in issues: print(" ✗", i) print("\n原則：把工具當成寫給『新進同事』的說明書——模型只能讀到這些字。") print("回傳也要精簡：只給模型需要的欄位，別把 5 萬字的原始 JSON 全丟回去。")

▶ 執行結果（這是實際執行的輸出）

do 分數 0/10 ✗ 描述太短：要說明『做什麼、何時用、回傳什麼』 ✗ 名稱太模糊：用動詞＋名詞，如 search_orders ✗ 參數 q 沒有說明 ✗ 參數 date 沒有說明 ✗ 參數 date 沒說日期格式 ✗ 沒有標出必填參數 search_orders 分數 10/10 原則：把工具當成寫給『新進同事』的說明書——模型只能讀到這些字。 回傳也要精簡：只給模型需要的欄位，別把 5 萬字的原始 JSON 全丟回去。

🧭 這一課的重點

好工具要命名清楚（動詞＋名詞）、說明做什麼何時用回傳什麼、參數有格式說明、粒度適中、回傳精簡，並控制工具數量。模型只能讀到說明，工具設計常比提示更影響代理表現。

🤖 本課的 Python 範例分兩版：離線版用一個模仿 Anthropic SDK 介面的「假 LLM」（mockllm.py），不需 API 金鑰即可執行，頁面上的輸出就是實際執行的結果；Claude API 版使用官方 anthropic 套件，需要 API 金鑰、會產生費用。API 細節（模型名稱、beta 功能）會隨時間更新，以官方文件為準。
