Prefill／Decode 分離

這一課的目標

  • 理解兩個階段互相干擾的問題
  • 理解分離部署的做法
  • 了解它的代價

Prefill 和 decode 擠在同一張 GPU 上，會互相干擾：一個長 prefill 會讓 decode 的使用者卡頓；為了穩定 TPOT 而限制 prefill，又會讓 TTFT 變長。更根本的是，兩者需要的硬體特性與平行策略完全不同。

分離部署（disaggregation）讓不同的 GPU 群各自專心做一件事：

  • Prefill 節點：處理新請求，產生 KV Cache 與第一個 token，然後把 KV Cache 傳給 decode 節點
  • Decode 節點：接收 KV Cache，以大批次持續生成
  • 兩邊可以依流量各自增減機器、各自選擇平行策略與 batch 大小

代表研究包括 DistServe（2024）、Splitwise（2024），以及月之暗面為 Kimi 服務設計的 Mooncake（2024），後者還加入了跨機器的 KV Cache 池。DeepSeek 也公開說明其 V3 服務採用了 prefill 與 decode 分離的部署。

代價是要在機器之間搬運 KV Cache：一個 8K token 的 Llama 3 70B 請求有約 2.5 GB 的 KV，需要高速網路（RDMA）才能讓傳輸時間不明顯增加 TTFT。所以它適合大規模的服務，小規模部署用 chunked prefill 通常就夠了。

🧭 這一課的重點

同機的 prefill 與 decode 互相干擾且需求不同；分離部署讓 prefill 與 decode 節點各自擴充與最佳化，代價是需以高速網路搬運 KV Cache。

⚡ 文中的硬體規格取自廠商公開資料（稠密運算、未計稀疏加速），速度與記憶體計算都是理論估算，實際數字會因軟體實作、批次與排程而不同。
