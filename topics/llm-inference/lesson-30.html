Prefix caching

這一課的目標

  • 理解 prefix caching 的原理
  • 認識它的應用場景
  • 了解它對成本的影響

因果遮罩保證：相同的前綴，KV Cache 一定相同。如果很多請求都以同一段系統提示開頭，或者同一段對話的下一輪要重送所有歷史，那麼前面那一段的 KV Cache 根本不必重算。

Prefix caching 把算過的 KV 區塊依內容（雜湊）保存下來。新的請求進來時，先找出最長的已快取前綴，只需要 prefill 剩下的部分。

  • 系統提示：數千 token 的系統提示只算一次，所有使用者共用
  • 多輪對話：每一輪只需 prefill 新增的使用者訊息
  • 長文件問答：對同一份文件問多個問題
  • agent：工具呼叫的迴圈中，前面的步驟每次都相同

SGLang 的 RadixAttention 用基數樹（radix tree）管理快取的前綴，能高效地找出最長共同前綴；vLLM 則以區塊雜湊實作自動前綴快取。許多 API 服務也提供「提示快取」功能，對命中快取的輸入 token 收取較低的費用。

實用建議

想讓快取命中，就把不變的內容放前面（系統提示、工具定義、文件），把會變的內容（使用者問題、時間戳記）放後面。任何前面的改動，都會讓後面的快取全部失效。

🧭 這一課的重點

相同前綴的 KV Cache 必然相同，prefix caching 依內容保存 KV 區塊，新請求只需 prefill 未命中的部分；適用於系統提示、多輪對話、文件問答與 agent。

⚡ 文中的硬體規格取自廠商公開資料（稠密運算、未計稀疏加速），速度與記憶體計算都是理論估算，實際數字會因軟體實作、批次與排程而不同。
