模組 D｜非同步與網路請求：現代網頁資料流動的核心 · 第 19 課

同步與非同步：為什麼JS常寫「等一下再做」

學習目標

  • 理解JS「單執行緒＋事件迴圈」的執行模型
  • 理解為什麼網路請求不能用「同步等待」的方式寫
  • 對照Python的requests，理解爬蟲工具跟瀏覽器JS的本質差異

模組D是整門課的核心目的地——資料真正從遠端 伺服器被抓下來的地方。但要看懂這部分JS程式碼， 得先建立一個Python裡不太需要特別去想的概念： 同步與非同步的差別。

1. Python的requests：同步、會等待

你已經很熟悉這樣寫Python：

import requests response = requests.get("https://example.com/api/data") print(response.json()) # 這一行，一定是在上一行執行完之後才會跑

這是同步（synchronous）執行： 程式碼由上而下依序執行，requests.get() 會讓程式停在原地等待，直到伺服器 回應為止，才會往下執行下一行。這很直覺， 但也代表：如果請求要花5秒鐘，你的整個程式 就會被卡住5秒鐘，什麼事都做不了。

2. 瀏覽器不能被卡住：JS是單執行緒

瀏覽器裡的JS有一個限制：它是單執行緒 （single-threaded）——同一時間只能做 一件事。如果JS發送網路請求時，也採用Python 那種「原地等待」的寫法，代表整個瀏覽器分頁 在等待回應的這幾秒鐘，會完全卡住不能動—— 使用者連捲動頁面、點擊按鈕都做不到， 體驗會非常糟糕。

3. 解法：非同步，先「登記」，等結果出來再處理

非同步的核心概念

JS採用非同步（asynchronous）的 做法解決這個問題：發送網路請求時，不會原地 等待，而是立刻把控制權交還給瀏覽器，讓使用者 可以繼續操作頁面；同時「登記」一段 「等結果真的回來以後，要執行的程式碼」—— 瀏覽器背景持續等待伺服器回應，一旦回應到達， 才回頭執行你登記的那段程式碼。這整套背景 運作機制稱為事件迴圈（event loop）。

        注意執行順序：印出來的是「1」「2」，
        然後（如果你在瀏覽器主控台實際執行，會等1秒）

        （印出「2」）跑完，之後才回頭處理登記好的
        那段程式碼。這個「程式碼撰寫順序」跟「實際
        執行順序」不一致的現象，正是非同步最違反直覺、
        也最需要花時間適應的地方。
      


      
4. 網路請求正是最典型的非同步操作

      

        「發送網路請求，等伺服器回應」跟
        setTimeout「等一段時間」，
        本質上是同一種模式：都是「現在做不完，
        要等外部的事情發生，才能繼續」。JS處理網路
        請求（下一課的Fetch API）用的正是跟
        setTimeout同一套非同步機制，
        只是等待的不是固定時間，而是「等伺服器
        回應」這件不確定要多久的事。
