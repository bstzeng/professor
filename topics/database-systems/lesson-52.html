總結：一個 App 從一台資料庫長大到全球規模

這一課的目標

  • 把各課的概念放進一個系統演進的脈絡
  • 理解每個階段的瓶頸與對策
  • 整理整門課的重點

一個 App 的成長

階段規模架構用到的課
1. 原型幾百位使用者一台 PostgreSQL，正規化的綱要、外鍵與約束第 4～14 課
2. 成長數萬位使用者，查詢變慢用 EXPLAIN 找慢查詢、建立適當的索引、修掉 N+1 查詢第 18～28 課
3. 讀取吃緊數十萬位使用者加上讀取副本、Redis 快取；注意複寫延遲與快取失效第 36、43 課
4. 正確性問題同時下單搶購理解隔離等級、用原子更新與 SELECT FOR UPDATE、處理死結與重試第 29～33 課
5. 可靠性不能停機、不能丟資料同步副本、自動容錯移轉、持續 WAL 封存與時間點復原、定期演練還原第 34～36 課
6. 分析需求老闆要各種報表用 CDC 把資料同步到資料倉儲，不再在主資料庫上跑報表第 17、49 課
7. 新功能全文搜尋、AI 助理倒排索引、向量搜尋、RAG第 22、48 課
8. 單機極限數億使用者、全球分布分片或分散式 SQL；仔細設計分片鍵，讓交易落在單一分片第 37～42 課

整門課的十個重點

  1. 關聯模型與 SQL 讓你說「要什麼」，資料庫決定「怎麼做」。
  2. 正規化讓每件事只記一次；反正規化是有意識的取捨。
  3. 一切設計都圍繞著減少磁碟 I/O；循序比隨機快得多。
  4. B+ 樹適合讀與範圍查詢，LSM 樹適合大量寫入。
  5. 最佳化器依統計資訊估計成本；估計錯誤是慢查詢最常見的原因。
  6. 交易的 ACID 由日誌、鎖與 MVCC 共同實現。
  7. 知道你的隔離等級，以及它防不了哪些異常。
  8. WAL：先寫日誌，資料頁可以慢慢寫；這也是複製與復原的基礎。
  9. 分散式系統必須在一致性、可用性與延遲之間取捨；共識演算法讓多台機器對同一件事達成一致。
  10. 沒有最好的資料庫，只有最適合需求與團隊的選擇——而 PostgreSQL 是很好的起點。

繼續學習

如果想更深入，可以閱讀卡納克（Martin Kleppmann）的《資料密集型應用系統設計》（Designing Data-Intensive Applications），以及卡內基美隆大學公開的資料庫系統課程。實際動手：安裝 PostgreSQL，對一個百萬筆的資料表練習 EXPLAIN、建索引、開兩個連線體驗隔離等級。

🧭 這一課的重點

一個 App 的成長依序經歷：原型用一台 PostgreSQL 與正規化綱要；成長時以 EXPLAIN、索引與修正 N+1 查詢解決變慢；讀取吃緊時加讀取副本與 Redis 快取；搶購時處理隔離等級、原子更新、死結與重試；可靠性需求下用同步副本、容錯移轉、WAL 封存與時間點復原；分析需求以 CDC 同步到資料倉儲；新功能加入倒排索引、向量搜尋與 RAG；單機極限時才分片或改用分散式 SQL。十個重點涵蓋關聯模型、正規化、I/O、B+ 樹與 LSM、最佳化器、ACID、隔離等級、WAL、分散式取捨與選型。

🗄️ 本課程以原理為主，程式範例用 SQL 與 Python（以 Python 實作簡化版的 B+ 樹、WAL、LSM 樹等核心結構）。各資料庫的實際行為依產品與版本而異，文中以 PostgreSQL、MySQL（InnoDB）與 SQLite 為主要參考。
