寬欄資料庫：Cassandra

這一課的目標

  • 理解寬欄資料模型
  • 理解以查詢為中心的建模
  • 理解可調一致性

Cassandra 最早由 Facebook 在 2008 年開發，結合了 Google Bigtable 的資料模型與亞馬遜 Dynamo 的分散式設計。它的設計目標是：海量寫入、沒有單點故障、跨資料中心。

資料模型

  • 分區鍵：決定資料在哪個節點（一致性雜湊，第 37 課）。
  • 叢集鍵：決定同一分區內資料的排序。
  • 同一個分區內可以有大量的資料列，依叢集鍵排序存放——所以叫「寬」欄。
-- CQL（Cassandra 查詢語言，看起來像 SQL） CREATE TABLE 感測器讀數 ( 感測器編號 text, 日期 date, 時間 timestamp, 溫度 double, PRIMARY KEY ((感測器編號, 日期), 時間) -- 分區鍵 (感測器, 日期)，叢集鍵 時間 ) WITH CLUSTERING ORDER BY (時間 DESC); SELECT * FROM 感測器讀數 WHERE 感測器編號 = 'S-17' AND 日期 = '2026-10-30' LIMIT 100;

以查詢為中心的建模

關聯式資料庫先設計正規化的表，再寫查詢；Cassandra 反過來：先列出所有查詢，再為每一個查詢設計一張表。同一份資料常常存好幾份（反正規化），因為 Cassandra 不支援 JOIN，查詢也必須指定分區鍵。

可調一致性

\[R + W > N \;\Rightarrow\; \text{read sees latest write}\]

每筆資料複製 N 份（例如 3），寫入時要求 W 份確認、讀取時要求 R 份回應。R + W > N 時，讀到的節點中一定有最新的寫入。可以每次查詢自己選：ONE（最快）、QUORUM（多數）、ALL（最一致）。

使用者

Netflix、Apple、Discord 等都曾大規模使用 Cassandra 或相容的 ScyllaDB，存放訊息、觀看紀錄、時序資料。它擅長「寫很多、依鍵讀」，不擅長即時的彈性查詢與分析。

🧭 這一課的重點

Cassandra 由 Facebook 在 2008 年開發，結合 Bigtable 的資料模型與 Dynamo 的分散式設計，目標是海量寫入、無單點故障與跨資料中心。分區鍵以一致性雜湊決定資料所在節點，叢集鍵決定分區內排序，同一分區可有大量依序存放的資料列。建模以查詢為中心：先列出查詢再為每個查詢設計一張表，常反正規化存多份，不支援 JOIN 且查詢須指定分區鍵。可調一致性中 R + W > N 時讀取可見最新寫入，可選 ONE、QUORUM、ALL。擅長寫多與依鍵讀，不擅長彈性查詢與分析。

🗄️ 本課程以原理為主，程式範例用 SQL 與 Python（以 Python 實作簡化版的 B+ 樹、WAL、LSM 樹等核心結構）。各資料庫的實際行為依產品與版本而異，文中以 PostgreSQL、MySQL（InnoDB）與 SQLite 為主要參考。
