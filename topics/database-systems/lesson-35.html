備份、還原與時間點復原

這一課的目標

  • 區分各種備份方式
  • 理解時間點復原
  • 建立 RPO 與 RTO 的概念

兩個關鍵指標

  • RPO（復原點目標）：最多能接受遺失多少時間的資料？（例如 5 分鐘）
  • RTO（復原時間目標）：最多能接受停機多久？（例如 1 小時）

這兩個數字決定了備份策略與成本：RPO 接近 0、RTO 只有幾秒，需要同步複製與自動切換；能接受一天的資料遺失，每天備份一次就夠了。

備份方式

方式做法優缺點
邏輯備份匯出成 SQL 或 CSV（pg_dump、mysqldump）可跨版本、可只備份部分資料；大資料庫很慢
實體備份複製資料檔（pg_basebackup、Percona XtraBackup）快；必須同版本
快照利用檔案系統或雲端磁碟的快照幾乎瞬間；要確保資料庫處於一致狀態
持續日誌封存不斷把 WAL 檔案複製到其他地方搭配實體備份，可以做時間點復原

時間點復原（PITR）

某天下午 3 點 07 分，有人誤下了 DELETE FROM 訂單（忘了 WHERE）。時間點復原的做法：

  1. 拿出前一晚的實體備份。
  2. 依序重播封存的 WAL，一直重播到下午 3 點 06 分 59 秒。
  3. 資料庫回到誤刪之前的那一刻。

備份的鐵則

  • 3-2-1 原則：3 份資料、2 種媒介、1 份在異地。
  • 沒有測試過還原的備份，不算備份：定期演練還原。
  • 副本不是備份：誤刪的指令會被立刻複製到副本上；勒索軟體也可能同時加密主機與副本。
  • 保留不可修改的備份（例如雲端物件儲存的鎖定功能），抵禦勒索軟體。

🧭 這一課的重點

RPO 是可接受遺失的資料時間，RTO 是可接受的停機時間，兩者決定備份策略與成本。備份方式包括可跨版本但大庫很慢的邏輯備份（pg_dump、mysqldump）、快但須同版本的實體備份（pg_basebackup、XtraBackup）、幾乎瞬間的快照與持續日誌封存。時間點復原以前一晚實體備份重播封存 WAL 至誤刪前一刻。鐵則包括 3-2-1 原則、未測試還原的備份不算備份、副本不是備份，以及保留不可修改的備份抵禦勒索軟體。

🗄️ 本課程以原理為主，程式範例用 SQL 與 Python（以 Python 實作簡化版的 B+ 樹、WAL、LSM 樹等核心結構）。各資料庫的實際行為依產品與版本而異，文中以 PostgreSQL、MySQL（InnoDB）與 SQLite 為主要參考。
