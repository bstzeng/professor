看懂 EXPLAIN：查詢計畫實戰

這一課的目標

  • 讀懂查詢計畫的樹狀結構
  • 比較估計值與實際值
  • 找出計畫中的效能問題
EXPLAIN ANALYZE SELECT c.姓名, SUM(o.金額) FROM 客戶 c JOIN 訂單 o ON o.客戶編號 = c.客戶編號 WHERE o.下單日期 >= '2026-10-01' GROUP BY c.姓名;

PostgreSQL 的輸出（簡化）：

HashAggregate (rows=1200) (actual rows=1187 time=85.2 ms) -> Hash Join (rows=48000) (actual rows=51320) Hash Cond: (o.客戶編號 = c.客戶編號) -> Index Scan using idx_下單日期 on 訂單 o (rows=48000) (actual rows=51320) Index Cond: (下單日期 >= '2026-10-01') -> Hash (rows=20000) -> Seq Scan on 客戶 c (rows=20000) (actual rows=20000)

怎麼讀

  • 由內往外、由下往上讀：最深層的運算子先執行。
  • 這個計畫：用索引找出十月以後的訂單 → 把客戶表整個讀進雜湊表 → 雜湊連接 → 雜湊聚合。
  • rows= 是估計值，actual rows= 是實際值（只有 EXPLAIN ANALYZE 才有，而且會真的執行查詢）。

常見的問題訊號

訊號可能的原因與對策
估計與實際差 10 倍以上統計資訊過時或欄位相關：執行 ANALYZE、建立延伸統計
大表上的 Seq Scan，但只回傳少量資料缺少索引，或索引因函數、型別轉換而失效
Nested Loop 的外層實際筆數很大基數低估：應該用 Hash Join
Sort 或 Hash 使用磁碟（external merge、Batches > 1）工作記憶體不足：調大 work_mem 或減少資料量
Index Scan 後大量「回表」考慮覆蓋索引

MySQL

MySQL 的 EXPLAIN 以表格呈現：注意 type 欄（ALL 代表全表掃描、ref／range 代表用到索引）、key（實際使用的索引）、rows（估計掃描筆數）與 Extra（Using filesort、Using temporary 常是效能警訊）。MySQL 8 也支援 EXPLAIN ANALYZE。

🧭 這一課的重點

EXPLAIN ANALYZE 顯示查詢計畫與實際執行結果，由內往外、由下往上閱讀，rows 為估計值、actual rows 為實際值（會真的執行查詢）。問題訊號包括估計與實際差 10 倍以上（執行 ANALYZE 或延伸統計）、大表 Seq Scan 只回傳少量資料（缺索引或索引失效）、外層筆數大的 Nested Loop（基數低估）、Sort 或 Hash 使用磁碟（調大 work_mem）與大量回表（考慮覆蓋索引）。MySQL 的 EXPLAIN 應注意 type、key、rows 與 Extra 欄位。

🗄️ 本課程以原理為主，程式範例用 SQL 與 Python（以 Python 實作簡化版的 B+ 樹、WAL、LSM 樹等核心結構）。各資料庫的實際行為依產品與版本而異，文中以 PostgreSQL、MySQL（InnoDB）與 SQLite 為主要參考。
