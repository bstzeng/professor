資料庫安全：SQL 注入、權限與加密

這一課的目標

  • 理解 SQL 注入的原理與防範
  • 理解最小權限原則
  • 認識加密與稽核

SQL 注入

把使用者輸入直接拼接進 SQL 字串，就給了攻擊者改寫查詢的機會：

import sqlite3 db = sqlite3.connect(":memory:") db.executescript("CREATE TABLE 使用者 (帳號 TEXT, 密碼雜湊 TEXT); INSERT INTO 使用者 VALUES ('admin', 'x');") user_input = "' OR '1'='1" # 錯誤：字串拼接 —— 查詢變成 WHERE 帳號 = '' OR '1'='1'，回傳所有使用者 bad = f"SELECT * FROM 使用者 WHERE 帳號 = '{user_input}'" print(db.execute(bad).fetchall()) # [('admin', 'x')] # 正確：參數化查詢 —— 輸入永遠只被當成「資料」，不會被當成 SQL good = "SELECT * FROM 使用者 WHERE 帳號 = ?" print(db.execute(good, (user_input,)).fetchall()) # []
  • 唯一可靠的解法：參數化查詢（預備陳述式）。資料庫先解析 SQL 的結構，再把參數當成純資料填入。
  • 不要自己寫「過濾危險字元」的函式——總有漏網之魚。
  • ORM 預設會參數化，但使用原生 SQL 或動態組合欄位名稱、排序方向時仍要小心（欄位名稱無法參數化，要用白名單）。

權限：最小權限原則

  • 應用程式用的帳號，只給它需要的權限（例如只能 SELECT、INSERT 特定的表），不要用超級使用者。
  • 報表帳號只能讀取副本。
  • PostgreSQL 的資料列層級安全（RLS）：讓每個租戶只能看到自己的資料列，即使應用程式有 bug 也不會外洩。

加密與稽核

層面做法
傳輸中強制 TLS 連線
靜態資料磁碟加密、透明資料加密（TDE）
特別敏感的欄位應用層加密（資料庫本身也看不到明文），密碼一律用 bcrypt、Argon2 等雜湊，而非加密
稽核記錄誰在什麼時間存取或修改了哪些敏感資料
備份備份檔同樣要加密與控管

🧭 這一課的重點

把使用者輸入直接拼接進 SQL 會造成 SQL 注入，例如輸入 ' OR '1'='1 使查詢回傳所有使用者。唯一可靠的解法是參數化查詢，資料庫先解析結構再把參數當純資料填入；不要自寫過濾函式，ORM 預設參數化，但動態欄位名稱與排序方向須用白名單。權限應遵守最小權限原則，報表帳號只讀副本，PostgreSQL 資料列層級安全 RLS 可隔離租戶資料。加密與稽核包括強制 TLS、磁碟加密與 TDE、敏感欄位應用層加密、密碼以 bcrypt 或 Argon2 雜湊、稽核紀錄與加密備份。

🗄️ 本課程以原理為主，程式範例用 SQL 與 Python（以 Python 實作簡化版的 B+ 樹、WAL、LSM 樹等核心結構）。各資料庫的實際行為依產品與版本而異，文中以 PostgreSQL、MySQL（InnoDB）與 SQLite 為主要參考。
