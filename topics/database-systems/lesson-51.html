選型指南：什麼情境用什麼資料庫

這一課的目標

  • 建立資料庫選型的思考框架
  • 認識常見情境的建議組合
  • 避免常見的選型錯誤

先問五個問題

  1. 資料的形狀：表格、文件、圖、時序、向量？
  2. 存取模式：讀多還是寫多？依鍵查詢還是彈性查詢？需要分析嗎？
  3. 一致性需求：錢與庫存需要強一致；按讚數可以最終一致。
  4. 規模：資料量與每秒請求數，現在與兩年後各是多少？
  5. 團隊：誰會維運？熟悉什麼？要自架還是用託管服務？

常見情境

情境建議（起點）
一般網站與商業應用PostgreSQL 或 MySQL（託管服務）＋讀取副本
行動 App 或桌面軟體的本機資料SQLite
快取、工作階段、排行榜Redis
日誌與監控Prometheus、ClickHouse、Elasticsearch
資料分析與報表雲端資料倉儲；小規模用 DuckDB
AI 語意搜尋與 RAGpgvector（資料量中等）或專用向量資料庫
超大量寫入、依鍵讀取（訊息、物聯網）Cassandra、ScyllaDB、DynamoDB
全球分布、需要強一致的交易Spanner、CockroachDB、TiDB
複雜關係與路徑（詐欺偵測）圖資料庫

常見的錯誤

  • 過早使用分散式資料庫：一台 PostgreSQL 在好的硬體上可以處理每秒數萬筆交易、數 TB 的資料，大多數公司永遠用不到更多。
  • 因為「無綱要」而選 NoSQL，結果在應用程式裡重新發明了綱要、交易與 JOIN。
  • 一次引入太多種資料庫：每多一種，就多一套維運、備份、監控、資安與資料同步的成本。
  • 忽略維運：備份、升級、監控、容錯移轉，往往比效能更決定系統的成敗。

多語言持久化

大型系統通常會組合多種資料庫，各司其職（交易用 PostgreSQL、快取用 Redis、搜尋用 Elasticsearch、分析用資料倉儲），再用 CDC（變更資料擷取）把資料從主資料庫同步到其他系統。關鍵是要有單一事實來源。

🧭 這一課的重點

資料庫選型先問五個問題：資料形狀、存取模式、一致性需求、現在與兩年後的規模，以及團隊與維運能力。常見情境建議：一般應用用 PostgreSQL 或 MySQL 加讀取副本，本機資料用 SQLite，快取用 Redis，日誌監控用 Prometheus、ClickHouse、Elasticsearch，分析用雲端資料倉儲或 DuckDB，語意搜尋用 pgvector 或專用向量資料庫，超大量寫入用 Cassandra、ScyllaDB、DynamoDB，全球強一致交易用 Spanner、CockroachDB、TiDB，複雜關係用圖資料庫。常見錯誤有過早分散式、為無綱要選 NoSQL、一次引入太多種與忽略維運；多語言持久化需以 CDC 同步並維持單一事實來源。

🗄️ 本課程以原理為主，程式範例用 SQL 與 Python（以 Python 實作簡化版的 B+ 樹、WAL、LSM 樹等核心結構）。各資料庫的實際行為依產品與版本而異，文中以 PostgreSQL、MySQL（InnoDB）與 SQLite 為主要參考。
