模組 B｜關聯模型與 SQL · 第 5 課

ER 模型：從需求畫出資料表

這一課的目標

  • 理解實體關係模型
  • 理解一對一、一對多、多對多
  • 把 ER 圖轉換成資料表

設計資料庫的第一步，不是直接寫 CREATE TABLE，而是釐清需求中有哪些「東西」以及它們的關係。1976 年陳品山（Peter Chen）提出的實體關係模型（ER 模型）是最常用的工具。

基本元素

  • 實體：需求中的名詞——客戶、商品、訂單。
  • 屬性：實體的特徵——客戶的姓名、電話。
  • 關係：實體之間的動詞——客戶「下」訂單、訂單「包含」商品。

基數

類型例子轉成資料表
一對一員工 — 員工證在其中一個表加外鍵（並設 UNIQUE），或合併成一個表
一對多客戶 — 訂單（一位客戶有很多訂單）在「多」的那一邊加外鍵：訂單.客戶編號
多對多訂單 — 商品（一張訂單多種商品，一種商品出現在多張訂單）建立中介表：訂單明細（訂單編號、商品編號、數量、單價）
CREATE TABLE 客戶 (客戶編號 INTEGER PRIMARY KEY, 姓名 TEXT, 電話 TEXT); CREATE TABLE 商品 (商品編號 INTEGER PRIMARY KEY, 品名 TEXT, 定價 NUMERIC); CREATE TABLE 訂單 ( 訂單編號 INTEGER PRIMARY KEY, 客戶編號 INTEGER REFERENCES 客戶, -- 一對多 下單時間 TIMESTAMP ); CREATE TABLE 訂單明細 ( -- 多對多的中介表 訂單編號 INTEGER REFERENCES 訂單, 商品編號 INTEGER REFERENCES 商品, 數量 INTEGER, 成交單價 NUMERIC, -- 下單當時的價格，和商品現在的定價不同 PRIMARY KEY (訂單編號, 商品編號) );

一個常見的設計細節

訂單明細裡要存「成交單價」，不能只參照商品表的定價：商品明天漲價，昨天的訂單金額不應該跟著變。區分「現在的狀態」與「當時的事實」，是資料模型設計中最常被忽略的問題之一。

🧭 這一課的重點

1976 年陳品山提出的實體關係模型以實體（名詞，如客戶、商品、訂單）、屬性與關係（動詞）描述需求。基數分為一對一（加唯一外鍵或合併）、一對多（在多的一方加外鍵，如訂單.客戶編號）與多對多（建立中介表，如訂單明細）。訂單明細應存成交單價而非只參照商品現價，區分現在的狀態與當時的事實是常被忽略的設計問題。

🗄️ 本課程以原理為主，程式範例用 SQL 與 Python（以 Python 實作簡化版的 B+ 樹、WAL、LSM 樹等核心結構）。各資料庫的實際行為依產品與版本而異，文中以 PostgreSQL、MySQL（InnoDB）與 SQLite 為主要參考。

  2. 為什麼訂單明細要存「成交單價」？
