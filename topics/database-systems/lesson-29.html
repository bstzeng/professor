模組 E｜交易與並行控制 · 第 29 課

ACID：交易的四個保證

這一課的目標

  • 理解交易的概念
  • 理解 ACID 各自的意義
  • 知道每個性質由哪些機制實現

轉帳：從 A 帳戶扣 1,000 元、在 B 帳戶加 1,000 元。如果扣款成功、入帳之前當機了呢？如果兩筆轉帳同時操作 A 帳戶呢？交易把一組操作包成一個不可分割的單位。

BEGIN; UPDATE 帳戶 SET 餘額 = 餘額 - 1000 WHERE 帳號 = 'A'; UPDATE 帳戶 SET 餘額 = 餘額 + 1000 WHERE 帳號 = 'B'; COMMIT; -- 或 ROLLBACK：全部取消
性質保證實現機制
原子性（Atomicity）全部成功或全部不做，沒有「做一半」日誌的復原（undo）
一致性（Consistency）交易前後，資料都滿足所有規則（約束、餘額不為負）約束＋應用程式邏輯
隔離性（Isolation）同時執行的交易，彼此看起來像依序執行鎖、MVCC（第 31、32 課）
持久性（Durability）一旦提交，就算立刻斷電也不會遺失WAL 與強制寫入磁碟（第 34 課）

一致性有點特別

A、I、D 是資料庫提供的機制；C 有一部分是應用程式的責任——資料庫不知道「轉帳前後總金額要相等」這種業務規則，除非你把它寫成約束。

持久性的代價

每次提交都要等日誌真正寫進磁碟（fsync），一次約 0.1～數毫秒。高寫入量的系統會用群組提交（把多個交易的日誌一起寫入）來分攤成本；也有些場景選擇非同步提交，用「可能遺失最後幾毫秒資料」換取速度。

BASE

許多 NoSQL 系統採用相對的 BASE 哲學：基本可用（Basically Available）、軟狀態（Soft state）、最終一致（Eventually consistent）——放寬一致性以換取可用性與擴展性（第 38 課）。

🧭 這一課的重點

交易把一組操作包成不可分割的單位，以 BEGIN、COMMIT 或 ROLLBACK 界定。ACID 包括原子性（全做或全不做，由日誌 undo 實現）、一致性（交易前後滿足規則，由約束與應用程式邏輯實現）、隔離性（並行交易看似依序執行，由鎖與 MVCC 實現）與持久性（提交後斷電也不遺失，由 WAL 與強制寫入實現）。一致性部分是應用程式的責任。持久性的 fsync 成本以群組提交分攤，或以非同步提交換速度。NoSQL 常採 BASE 哲學放寬一致性。

🗄️ 本課程以原理為主，程式範例用 SQL 與 Python（以 Python 實作簡化版的 B+ 樹、WAL、LSM 樹等核心結構）。各資料庫的實際行為依產品與版本而異，文中以 PostgreSQL、MySQL（InnoDB）與 SQLite 為主要參考。

檢查你的理解

  1. 用轉帳說明原子性與持久性。
  2. 為什麼說一致性有一部分是應用程式的責任？
  3. 什麼是群組提交？為什麼需要它？
