模組 F｜分散式資料庫 · 第 41 課

NewSQL：Spanner、CockroachDB 與 TiDB

這一課的目標

  • 理解 NewSQL 的設計目標
  • 理解 Spanner 的 TrueTime
  • 比較主要的分散式 SQL 資料庫

2000 年代，大公司為了擴展放棄了 SQL 與交易，改用 NoSQL；但很快發現，沒有交易的應用程式非常難寫。NewSQL（分散式 SQL）的目標是：保留 SQL 與 ACID 交易，同時能像 NoSQL 一樣水平擴展。

共同架構

  • 資料自動切成許多範圍分片，每片用 Raft 或 Paxos 複製到多個節點（第 39 課）。
  • 跨分片的交易用兩階段提交，協調者與參與者本身都是共識群組（第 40 課）。
  • 用 MVCC 提供快照讀取——這需要一個全域一致的時間戳記。

Spanner 的 TrueTime

2012 年 Google 發表 Spanner 論文。全球分布的機器時鐘不可能完全同步，Spanner 的做法是：每個資料中心配備 GPS 接收器與原子鐘，TrueTime API 回傳的不是一個時間點，而是一個誤差區間（通常數毫秒以內）。

\[\text{TT.now()} = [\,t_{\text{earliest}},\; t_{\text{latest}}\,]\]

提交交易時，Spanner 會等待直到確定時間戳記已經過去（commit wait），這樣就保證了全球的交易順序與真實時間一致（外部一致性）。代價是每次提交多等幾毫秒。

資料庫出身特點
Google SpannerGoogle，2012 年論文TrueTime 硬體時鐘；Google Cloud 提供託管服務
CockroachDB美國，前 Google 工程師創立相容 PostgreSQL 協定；用混合邏輯時鐘取代原子鐘
TiDB中國 PingCAP相容 MySQL 協定；儲存層 TiKV 基於 RocksDB 與 Raft；TiFlash 提供欄式分析
YugabyteDB美國相容 PostgreSQL；開源

什麼時候需要

大多數應用程式，一台夠大的 PostgreSQL 加上讀取副本就足夠。只有在單機的寫入量或資料量確實撐不住、或需要跨地區的高可用與強一致時，分散式 SQL 的額外複雜度與延遲才值得。

🧭 這一課的重點

NewSQL 分散式 SQL 的目標是保留 SQL 與 ACID 交易並能水平擴展。共同架構是資料自動切成範圍分片、每片以 Raft 或 Paxos 複製，跨分片交易用以共識群組為協調者與參與者的兩階段提交，並以 MVCC 提供快照讀取，需要全域一致時間戳記。2012 年 Google Spanner 以 GPS 與原子鐘提供誤差區間的 TrueTime，提交時等待確定時間戳記已過以保證外部一致性。主要產品包括 Spanner、相容 PostgreSQL 並用混合邏輯時鐘的 CockroachDB、相容 MySQL 的 TiDB 與 YugabyteDB。多數應用一台 PostgreSQL 加讀取副本即足夠。

🗄️ 本課程以原理為主，程式範例用 SQL 與 Python（以 Python 實作簡化版的 B+ 樹、WAL、LSM 樹等核心結構）。各資料庫的實際行為依產品與版本而異，文中以 PostgreSQL、MySQL（InnoDB）與 SQLite 為主要參考。
