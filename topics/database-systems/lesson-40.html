分散式交易：兩階段提交

這一課的目標

  • 理解兩階段提交的流程
  • 理解它的阻塞問題
  • 認識 Saga 等替代方案

A 帳戶在分片 1、B 帳戶在分片 2。轉帳要同時修改兩個分片——如果分片 1 成功、分片 2 失敗呢？

兩階段提交（2PC）

  1. 準備階段：協調者問所有參與者：「你們可以提交嗎？」每個參與者把修改寫入日誌、鎖住資源，回答「可以」或「不行」。回答「可以」之後，就不能反悔。
  2. 提交階段：如果全部都說可以，協調者寫下「提交」的決定，通知所有參與者提交；只要有一個說不行，就通知全部中止。
def two_phase_commit(coordinator_log, participants, tx): # 階段一：準備 votes = [] for p in participants: votes.append(p.prepare(tx)) # 參與者寫好日誌、鎖住資源，回答 True／False decision = "COMMIT" if all(votes) else "ABORT" coordinator_log.append((tx, decision)) # 決定點：寫入協調者的日誌（持久化） # 階段二：通知 for p in participants: p.commit(tx) if decision == "COMMIT" else p.abort(tx) return decision

阻塞問題

如果協調者在參與者都回答「可以」之後當機，參與者既不能自行提交（說不定有人說不行），也不能自行中止（說不定協調者已經決定提交）——只能持有鎖、一直等到協調者恢復。解法：把協調者本身用共識演算法複製（例如 Spanner 讓每個參與者都是一個 Paxos 群組）。

替代方案：Saga

微服務架構中，各服務有自己的資料庫，常用 Saga：把一個大交易拆成一連串本地交易，每一步都定義對應的補償動作。例如訂機票＋訂飯店＋扣款，扣款失敗時，依序執行「取消飯店」「取消機票」。Saga 放棄了隔離性（中間狀態會被看見），換取不需要分散式鎖。

設計原則

分散式交易昂貴又複雜。好的資料模型與分片鍵設計，應該讓絕大多數交易只落在單一分片（例如同一位客戶的資料放在同一片）。

🧭 這一課的重點

跨分片的轉帳需要分散式交易。兩階段提交 2PC 的準備階段由協調者詢問所有參與者能否提交，參與者寫日誌、鎖資源並回答，回答可以後不能反悔；提交階段若全部同意則寫下提交決定並通知提交，否則全部中止。協調者在決定前當機會使參與者持鎖阻塞，解法是以共識演算法複製協調者（如 Spanner）。微服務常用 Saga，把大交易拆成一連串本地交易並定義補償動作，放棄隔離性換取不需分散式鎖。好的分片設計應讓多數交易落在單一分片。
