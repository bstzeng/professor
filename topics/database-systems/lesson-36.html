複製：主從、多主與複寫延遲

這一課的目標

  • 理解複製的目的與架構
  • 理解同步與非同步複製
  • 理解複寫延遲造成的異常

為什麼要複製

  • 高可用：主機故障時，副本接手。
  • 擴展讀取：讀取分散到多個副本。
  • 地理分布：讓各地使用者讀取附近的副本。

三種架構

架構做法挑戰
單一主節點（主從）所有寫入到主節點，再把日誌傳給從節點重播主節點故障時要選出新主節點（容錯移轉）
多主節點多個節點都能寫入，彼此同步寫入衝突：兩地同時修改同一筆資料
無主節點（Dynamo 式）寫入送到多個節點，讀取也從多個節點讀，依法定人數判斷需要處理版本衝突

同步 vs. 非同步

同步複製非同步複製
提交時等副本確認收到才回應主節點寫完就回應
資料遺失主節點故障也不遺失可能遺失最後幾秒的資料
延遲每次寫入都多一次網路往返低
可用性副本故障可能讓寫入卡住高

實務上常用「半同步」：至少一個副本同步確認，其他非同步。

複寫延遲的異常

  • 讀不到自己的寫入：使用者剛修改了暱稱，重新整理頁面時讀到的是還沒同步的副本，暱稱又變回舊的。解法：使用者自己的資料從主節點讀。
  • 時光倒流：連續兩次讀取打到不同的副本，第二次反而讀到更舊的資料。解法：同一個使用者固定讀同一個副本。
  • 因果顛倒：先看到回覆，才看到原本的問題。

🧭 這一課的重點

複製的目的是高可用、擴展讀取與地理分布。架構有單一主節點（寫入主節點再傳日誌給從節點，需容錯移轉）、多主節點（多處可寫，須處理寫入衝突）與 Dynamo 式無主節點（多節點讀寫並依法定人數判斷）。同步複製不遺失資料但增加延遲並可能卡住寫入，非同步低延遲高可用但可能遺失最後幾秒，實務常用半同步。複寫延遲會造成讀不到自己的寫入、時光倒流與因果顛倒，可由主節點讀自身資料或固定讀同一副本解決。

🗄️ 本課程以原理為主，程式範例用 SQL 與 Python（以 Python 實作簡化版的 B+ 樹、WAL、LSM 樹等核心結構）。各資料庫的實際行為依產品與版本而異，文中以 PostgreSQL、MySQL（InnoDB）與 SQLite 為主要參考。
