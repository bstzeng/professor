模組 G｜各種資料庫 · 第 49 課

資料倉儲與 OLAP：Snowflake、BigQuery、DuckDB

這一課的目標

  • 理解資料倉儲的架構與星狀綱要
  • 認識現代雲端資料倉儲
  • 理解資料湖與湖倉一體

為什麼不直接在交易資料庫上分析

  • 分析查詢掃描大量資料，會拖慢線上交易。
  • 交易資料庫是列式儲存，分析效率低（第 17 課）。
  • 分析需要整合多個來源（訂單、會員、廣告、客服）。

所以把資料用 ETL／ELT（擷取、轉換、載入）定期搬到專門的資料倉儲。

星狀綱要

  • 事實表：中間的大表，記錄每一筆事件與數值（銷售明細：日期鍵、商品鍵、門市鍵、數量、金額）。
  • 維度表：周圍的小表，描述事件的背景（日期維度：年、季、月、星期、是否假日；商品維度：品牌、類別）。
  • 刻意反正規化，讓分析查詢只需要少量、簡單的 JOIN。

現代雲端資料倉儲

產品特點
Snowflake儲存與運算分離，多個運算叢集共享同一份資料，依使用量計費
Google BigQuery無伺服器，按掃描的資料量計費；源自 Google 的 Dremel 論文（2010）
Amazon Redshift早期的雲端資料倉儲之一
ClickHouse開源、極快的欄式資料庫，常用於即時分析與日誌
DuckDB嵌入式分析資料庫（2019 年起），「分析界的 SQLite」，在筆電上就能快速分析數億筆資料
import duckdb # 直接查詢 Parquet 檔案，不需要先匯入 duckdb.sql(''' SELECT 門市, date_trunc('month', 日期) AS 月份, SUM(金額) AS 營收 FROM 'sales/*.parquet' WHERE 日期 >= '2026-01-01' GROUP BY ALL ORDER BY 月份, 營收 DESC ''').show()

資料湖與湖倉一體

  • 資料湖：把所有原始資料（結構化、日誌、圖片）以便宜的格式（例如 Parquet）存在物件儲存（S3）上。
  • 問題：缺乏交易、綱要管理，容易變成「資料沼澤」。
  • 湖倉一體（lakehouse）：用 Apache Iceberg、Delta Lake 等表格式，在資料湖上加入交易、綱要演進與時間旅行查詢，讓多種引擎（Spark、Trino、Snowflake、DuckDB）都能讀同一份資料。

🧭 這一課的重點

分析查詢會拖慢交易、列式儲存分析效率低且需整合多來源，因此以 ETL／ELT 搬到資料倉儲。星狀綱要以記錄事件與數值的事實表為中心，周圍是描述背景的維度表，刻意反正規化以簡化 JOIN。現代雲端資料倉儲有儲存運算分離的 Snowflake、按掃描量計費並源自 2010 年 Dremel 的 BigQuery、Redshift、開源極快的 ClickHouse，以及 2019 年起、可直接查詢 Parquet 的嵌入式 DuckDB。資料湖把原始資料以 Parquet 存在物件儲存，湖倉一體以 Iceberg、Delta Lake 加入交易、綱要演進與時間旅行。

🗄️ 本課程以原理為主，程式範例用 SQL 與 Python（以 Python 實作簡化版的 B+ 樹、WAL、LSM 樹等核心結構）。各資料庫的實際行為依產品與版本而異，文中以 PostgreSQL、MySQL（InnoDB）與 SQLite 為主要參考。
