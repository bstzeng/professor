時序資料庫：監控與物聯網

這一課的目標

  • 理解時序資料的特性
  • 認識時序資料庫的最佳化
  • 認識常見的時序資料庫

時序資料的特性

  • 幾乎只有附加：新資料不斷寫入，很少修改舊資料。
  • 依時間查詢：「過去一小時的 CPU 使用率」「上個月每天的平均溫度」。
  • 寫入量極大：一萬台伺服器、每台 100 個指標、每 10 秒一次，就是每秒十萬筆。
  • 越舊越不重要：最近的資料要精細，一年前的資料只需要每小時平均。

時序資料庫的最佳化

技術說明
依時間分區每天（或每小時）一個分區；刪除舊資料只要丟掉整個分區
欄式與壓縮時間戳記用差值的差值編碼、數值用 XOR 壓縮（Facebook Gorilla 論文），壓縮率可達十倍以上
降採樣自動把舊資料彙總成較粗的粒度（例如 1 分鐘 → 1 小時）
保留政策自動刪除超過期限的資料
連續彙總預先計算常用的彙總，查詢時直接讀取
-- TimescaleDB（PostgreSQL 擴充）：依 5 分鐘分桶計算平均溫度 SELECT time_bucket('5 minutes', 時間) AS 區間, 感測器編號, AVG(溫度) AS 平均溫度 FROM 感測器讀數 WHERE 時間 > now() - INTERVAL '1 day' GROUP BY 區間, 感測器編號 ORDER BY 區間;
資料庫特點
Prometheus雲端原生監控的標準，拉取式收集，PromQL 查詢語言
InfluxDB專門的時序資料庫
TimescaleDBPostgreSQL 擴充，可以用完整的 SQL
ClickHouse通用的欄式分析資料庫，也常用於時序與日誌

🧭 這一課的重點

時序資料幾乎只有附加、依時間查詢、寫入量極大（一萬台伺服器各 100 指標每 10 秒即每秒十萬筆）且越舊越不重要。時序資料庫以依時間分區（刪舊資料只丟分區）、欄式與壓縮（差值的差值、XOR 壓縮，Facebook Gorilla 論文，十倍以上）、降採樣、保留政策與連續彙總最佳化。TimescaleDB 可用 time_bucket 依時間分桶彙總。常見產品有 Prometheus（PromQL）、InfluxDB、TimescaleDB 與 ClickHouse。

🗄️ 本課程以原理為主，程式範例用 SQL 與 Python（以 Python 實作簡化版的 B+ 樹、WAL、LSM 樹等核心結構）。各資料庫的實際行為依產品與版本而異，文中以 PostgreSQL、MySQL（InnoDB）與 SQLite 為主要參考。
