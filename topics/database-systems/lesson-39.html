共識演算法：Raft 的直覺

這一課的目標

  • 理解共識要解決的問題
  • 理解 Raft 的領導者選舉與日誌複製
  • 知道共識在資料庫中的用途

在分散式系統中，機器會當機、網路會延遲或斷線。共識演算法讓一組節點對一連串的決定（例如日誌的每一筆紀錄）達成一致，只要多數節點正常就能繼續運作。

1989 年蘭波特提出的 Paxos 是經典，但以難以理解著稱。2014 年翁加羅與奧斯特豪特提出 Raft，目標就是「好懂」，現在被廣泛採用（etcd、CockroachDB、TiKV、Consul 等）。

Raft 的三個角色

  • 領導者：接收所有寫入，把日誌複製給其他節點。
  • 跟隨者：被動接收領導者的日誌。
  • 候選人：領導者失聯時，想成為新領導者的節點。

領導者選舉

  1. 跟隨者在一段隨機的時間內沒收到領導者的心跳，就把「任期」加一，成為候選人，向其他節點拉票。
  2. 每個節點在一個任期內只投一票。
  3. 得到多數票的候選人成為領導者。隨機的逾時時間讓大家不容易同時參選、平票。

日誌複製

  1. 客戶端的寫入送到領導者，領導者把它附加到自己的日誌。
  2. 領導者把這筆紀錄送給所有跟隨者。
  3. 多數節點確認寫入後，這筆紀錄就「已提交」，可以套用到狀態並回應客戶端。
  4. 新的領導者一定擁有所有已提交的紀錄（選舉規則保證：日誌不夠新的候選人拿不到票）。
\[\text{majority} = \left\lfloor \frac{n}{2} \right\rfloor + 1\]

5 個節點可以容忍 2 個故障；3 個節點可以容忍 1 個。所以共識叢集通常是奇數個節點。

在資料庫中的用途

分散式資料庫通常把資料切成很多片，每一片各自用一個 Raft 群組複製到 3 或 5 個節點，確保任何一片在少數節點故障時仍能讀寫，而且不會出現兩個主節點（腦裂）。

🧭 這一課的重點

共識演算法讓一組節點在機器當機與網路延遲下，對一連串決定達成一致，只要多數節點正常即可運作。1989 年蘭波特的 Paxos 難以理解，2014 年翁加羅與奧斯特豪特提出好懂的 Raft，被 etcd、CockroachDB、TiKV、Consul 採用。Raft 有領導者、跟隨者、候選人三種角色；領導者選舉以隨機逾時觸發、每任期一票、多數票當選；日誌複製在多數節點確認後即提交，選舉規則保證新領導者擁有所有已提交紀錄。多數為 ⌊n/2⌋ + 1，5 節點容忍 2 個故障。分散式資料庫通常每一片各用一個 Raft 群組。

🗄️ 本課程以原理為主，程式範例用 SQL 與 Python（以 Python 實作簡化版的 B+ 樹、WAL、LSM 樹等核心結構）。各資料庫的實際行為依產品與版本而異，文中以 PostgreSQL、MySQL（InnoDB）與 SQLite 為主要參考。
