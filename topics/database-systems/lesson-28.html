模組 D｜查詢處理與最佳化 · 第 28 課

慢查詢調校案例

這一課的目標

  • 建立系統化的調校流程
  • 認識常見的慢查詢模式
  • 知道何時該改架構而不是改查詢

調校流程

  1. 找出慢查詢：開啟慢查詢日誌，或使用 pg_stat_statements 找出「總耗時」最高的查詢（不只是單次最慢的）。
  2. 看計畫：EXPLAIN ANALYZE。
  3. 找出瓶頸：估計錯誤？缺索引？排序溢出到磁碟？
  4. 修改並驗證：一次只改一件事，比較前後的實際執行時間。

五個常見案例

症狀原因解法
N+1 查詢：列出 100 位客戶，每位再各查一次訂單，共 101 次查詢ORM 的延遲載入一次 JOIN，或用 IN 一次取回所有訂單
深分頁：LIMIT 20 OFFSET 1000000 越後面越慢資料庫要先讀過並丟掉前一百萬筆改用「鍵集分頁」：WHERE id > 上一頁最後的 id ORDER BY id LIMIT 20
函數讓索引失效WHERE LOWER(email) = …建立函數索引，或存正規化後的欄位
大量 COUNT(*)：首頁顯示「共 3,281,442 筆」每次都要掃描使用近似值、快取計數，或改設計
OR 條件：WHERE a = 1 OR b = 2單一索引無法同時處理拆成兩個查詢 UNION，或依賴資料庫的位元圖索引合併
import sqlite3, time db = sqlite3.connect(":memory:") db.execute("CREATE TABLE 訂單 (id INTEGER PRIMARY KEY, 客戶 INTEGER, 金額 INTEGER)") db.executemany("INSERT INTO 訂單 (客戶, 金額) VALUES (?, ?)", [(i % 5000, i % 997) for i in range(500_000)]) t = time.time(); db.execute("SELECT * FROM 訂單 LIMIT 20 OFFSET 490000").fetchall(); print("OFFSET", time.time() - t) t = time.time(); db.execute("SELECT * FROM 訂單 WHERE id > 490000 ORDER BY id LIMIT 20").fetchall(); print("鍵集", time.time() - t) t = time.time(); db.execute("SELECT SUM(金額) FROM 訂單 WHERE 客戶 = 42").fetchall(); print("無索引", time.time() - t) db.execute("CREATE INDEX idx_客戶 ON 訂單(客戶)") t = time.time(); db.execute("SELECT SUM(金額) FROM 訂單 WHERE 客戶 = 42").fetchall(); print("有索引", time.time() - t)

何時該改架構

如果最佳化之後，查詢仍然需要掃描數億筆資料（例如即時的多維度報表），問題可能不在 SQL，而在架構：該用讀取副本、快取、實體化檢視，或把分析工作移到資料倉儲（第 49 課）。

🧭 這一課的重點

調校流程為：以慢查詢日誌或 pg_stat_statements 找出總耗時最高的查詢、EXPLAIN ANALYZE 看計畫、找出瓶頸、一次改一件事並驗證。常見案例有 ORM 延遲載入造成的 N+1 查詢（改 JOIN 或 IN）、深分頁 OFFSET 越後越慢（改鍵集分頁）、函數使索引失效（函數索引）、大量 COUNT(*)（近似值或快取）與 OR 條件（拆 UNION 或位元圖合併）。若最佳化後仍需掃描數億筆，應考慮讀取副本、快取、實體化檢視或資料倉儲等架構改變。

🗄️ 本課程以原理為主，程式範例用 SQL 與 Python（以 Python 實作簡化版的 B+ 樹、WAL、LSM 樹等核心結構）。各資料庫的實際行為依產品與版本而異，文中以 PostgreSQL、MySQL（InnoDB）與 SQLite 為主要參考。
