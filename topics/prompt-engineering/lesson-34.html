模型路由

這一課的目標

  • 理解模型路由的目的
  • 寫出穩定的分類器提示
  • 設計路由的升級機制

不是每個請求都需要最強的模型。路由是先判斷請求的類型或難度，再交給適合的模型或流程：簡單的交給快而便宜的模型，困難的交給強模型。

路由的核心是一個分類器提示，它需要：

  • 封閉的類別清單，每類有清楚的定義與例子
  • 邊界規則：不確定時歸到哪一類（通常歸到較安全、較強的那一類）
  • 固定的輸出格式：只輸出類別，方便程式解析

🐍 Python 範例（離線可執行，已實際執行）　把分類結果對應到模型與流程

# 路由決策：分類結果 → 模型與流程（分類本身由便宜的模型完成） ROUTES = { "簡單問答": ("小模型", "直接回答"), "需要查資料": ("中模型", "先檢索再回答"), "複雜分析": ("大模型", "開啟思考、較高 effort"), "敏感／投訴": ("大模型", "回答後轉真人複核"), } FALLBACK = "複雜分析" # 分類器回傳無法辨識的結果時，走較安全的路線 def route(label): label = label.strip() if label not in ROUTES: label = FALLBACK model, flow = ROUTES[label] return label, model, flow for raw in ["簡單問答", "需要查資料", "敏感／投訴", "我覺得是簡單的", ""]: print("分類器輸出 %-10r → %s" % (raw, " / ".join(route(raw))))

▶ 執行結果

分類器輸出 '簡單問答' → 簡單問答 / 小模型 / 直接回答 分類器輸出 '需要查資料' → 需要查資料 / 中模型 / 先檢索再回答 分類器輸出 '敏感／投訴' → 敏感／投訴 / 大模型 / 回答後轉真人複核 分類器輸出 '我覺得是簡單的' → 複雜分析 / 大模型 / 開啟思考、較高 effort 分類器輸出 '' → 複雜分析 / 大模型 / 開啟思考、較高 effort
把客戶訊息分到下列一類，只輸出類別名稱： - 簡單問答：營業時間、地址、一般政策等固定答案的問題 - 需要查資料：涉及特定訂單、帳號、庫存的問題 - 複雜分析：需要比較、計算、多步驟推理的問題 - 敏感／投訴：抱怨、退款爭議、法律或安全相關 若同時符合多類，選擇列表中較下方的那一類。

🧭 這一課的重點

模型路由先判斷請求類型或難度，簡單的交給快而便宜的模型、困難的交給強模型。分類器提示需要封閉且有定義的類別清單、不確定時歸向較安全較強一類的邊界規則與固定輸出格式；程式也要處理無法辨識的輸出。

✍️ 提示工程的最佳做法會隨模型世代改變；本課以目前主流模型（特別是 Claude）的實際行為為例，原則大多通用。Python 範例中標示「已執行」的為離線程式，輸出是實際結果；呼叫 API 的範例需要金鑰，模型名稱與參數以官方文件為準。
