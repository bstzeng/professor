Level 4｜Engineering：把提示當成軟體 · 第 46 課

提示優化

這一課的目標

  • 比較兩個提示版本
  • 讓模型協助改寫提示
  • 知道自動優化的限制

有了測試集和評分方式，就可以系統性地優化提示：

方法做法注意
離線 A/B兩版提示跑同一組測試集，比較分數樣本太少時差異可能只是隨機
線上 A/B部分真實流量用新版，比較使用者行為要先通過離線評估
用模型改提示把提示、失敗案例與評審理由給模型，請它提出修改仍要用測試集驗證，不能直接採用
自動化迴圈程式反覆「改寫 → 評估 → 保留較好的」容易過度擬合，要用保留集確認

🐍 Python 範例（離線可執行，已實際執行）　樣本數夠不夠？

# 兩版提示各跑 40 個案例：差異是真的，還是運氣？ import math n = 40 pass_a, pass_b = 30, 34 # v1 通過 30 題、v2 通過 34 題 pa, pb = pass_a / n, pass_b / n p = (pass_a + pass_b) / (2 * n) se = math.sqrt(p * (1 - p) * 2 / n) z = (pb - pa) / se print("v1 %.0f%% v2 %.0f%% 差 %.0f 個百分點" % (pa * 100, pb * 100, (pb - pa) * 100)) print("z = %.2f → %s" % (z, "差異可能是真的" if abs(z) > 1.96 else "差異可能只是隨機，需要更多案例"))

▶ 執行結果

v1 75% v2 85% 差 10 個百分點 z = 1.12 → 差異可能只是隨機，需要更多案例
下面是一個提示、它在測試集上失敗的案例，以及評審給的失敗理由。 <prompt>{目前的提示}</prompt> <failures>{失敗案例與理由}</failures> 請找出這些失敗的共通原因，提出一個最小的修改，並說明為什麼這個修改能解決問題、可能會影響哪些原本通過的案例。 不要針對個別案例加特例規則。

🧭 這一課的重點

系統性優化包括離線 A/B（同測試集比分數，注意樣本數）、線上 A/B（先通過離線評估）、把提示與失敗案例交給模型提出修改（仍需驗證），以及自動化改寫評估迴圈（要用保留集防過度擬合）。案例太少時分數差異可能只是隨機。

✍️ 提示工程的最佳做法會隨模型世代改變；本課以目前主流模型（特別是 Claude）的實際行為為例，原則大多通用。Python 範例中標示「已執行」的為離線程式，輸出是實際結果；呼叫 API 的範例需要金鑰，模型名稱與參數以官方文件為準。

檢查你的理解

  2. 請模型改寫提示時，要提供哪些資訊？
  3. 自動化優化迴圈有什麼風險？
