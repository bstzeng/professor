Level 4｜Engineering：把提示當成軟體 · 第 50 課

總結：提示工程檢查清單

這一課的目標

  • 回顧四個層級的重點
  • 取得一份可用的檢查清單
  • 規劃下一步的學習
層級核心問題檢查項目
Level 1 基礎這句話清楚嗎？任務明確、說明理由、具體、結構化、範例多樣、輸出格式清楚、限制正面表述
Level 2 上下文模型看到對的東西嗎？只放相關資料、長文件放前、要求引用、允許說不知道、工具說明清楚、快取順序正確、外部內容標記為資料
Level 3 代理沒人看著時它會做對嗎？角色環境方式邊界完成條件、狀態寫下來、錯誤恢復策略、具體的自我檢查、自主程度依可逆性分級
Level 4 工程怎麼知道它真的變好？可衡量的需求、測試集、評分方式、失敗分類、一次改一件事、縱深防禦、版本控制、成本評估

上線前的最後檢查

  1. 有可衡量的成功標準嗎？
  2. 有測試集嗎？包含邊界情況與對抗案例嗎？
  3. 最新版本在測試集上的分數是多少？有沒有個別案例退步？
  4. 安全防護有在提示以外的地方實作嗎？
  5. 提示放在版本控制中、記錄了搭配的模型嗎？
  6. 成本與延遲在預算內嗎？
  7. 上線後如何收集失敗案例、回饋到測試集？

最重要的一句話

提示工程不是找到神奇的咒語，而是清楚地溝通，加上有紀律的測量。把模型當成一位聰明但不了解你情況的新同事：給它需要的資訊，告訴它為什麼，然後檢查結果。

🧭 這一課的重點

四個層級的核心問題：基礎是話說清楚沒、上下文是模型看到對的東西沒、代理是沒人看著時會不會做對、工程是怎麼知道真的變好。上線前檢查成功標準、測試集、分數與退步、提示外的安全防護、版本控制、成本延遲與失敗回饋機制。提示工程是清楚溝通加上有紀律的測量。

✍️ 提示工程的最佳做法會隨模型世代改變；本課以目前主流模型（特別是 Claude）的實際行為為例，原則大多通用。Python 範例中標示「已執行」的為離線程式，輸出是實際結果；呼叫 API 的範例需要金鑰，模型名稱與參數以官方文件為準。
