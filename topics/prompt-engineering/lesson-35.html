子代理與委派

這一課的目標

  • 理解委派給子代理的情境
  • 寫出完整的委派提示
  • 設計子代理的回報格式

主代理把一部分工作交給子代理時，子代理是從零開始的——它看不到主代理的對話歷史。所以委派提示要像交辦給一位外部顧問：自成一體、資訊完整。

✗ 改寫前
幫我查一下那個 bug 的原因。
✓ 改寫後
背景：使用者回報結帳頁在 Safari 上點「付款」沒有反應，Chrome 正常。 已知：問題從 10/1 的版本開始出現；那次更新修改了 src/checkout/ 底下的檔案。 任務：找出 Safari 上失效的原因。只需要調查與回報，不要修改任何檔案。 回報格式： - 最可能的原因（附檔名與行號） - 證據 - 你排除了哪些可能性 - 你不確定的地方
  • 提供子代理看不到的背景
  • 說明已知線索，避免重複調查
  • 限定範圍（只調查、不修改）
  • 規定回報格式，方便主代理整合

委派的另一個好處是保持主代理的上下文乾淨：子代理可能讀了幾十個檔案，但只回報幾段結論。所以回報格式要「精簡但完整」——結論、證據、不確定之處。

🧭 這一課的重點

子代理從零開始、看不到主代理的歷史，委派提示要像交辦外部顧問一樣自成一體：提供背景、已知線索、明確範圍與回報格式。委派也讓主代理上下文保持乾淨，回報應精簡但完整，包含結論、證據與不確定之處。

✍️ 提示工程的最佳做法會隨模型世代改變；本課以目前主流模型（特別是 Claude）的實際行為為例，原則大多通用。Python 範例中標示「已執行」的為離線程式，輸出是實際結果；呼叫 API 的範例需要金鑰，模型名稱與參數以官方文件為準。
