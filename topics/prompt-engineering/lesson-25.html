提示快取

這一課的目標

  • 理解提示快取的原理
  • 安排提示順序以提高命中率
  • 避免讓快取失效的常見錯誤

許多 API 支援提示快取：如果這次請求的開頭和上次完全一樣，伺服器可以重用之前的計算結果，這部分的費用大幅降低、速度也更快。代理與聊天機器人每一輪都重送相同的系統提示與歷史，最能受惠。

快取是前綴匹配：從開頭開始比對，遇到第一個不同的字，之後的全部失效。所以提示的排列原則是：

  1. 最穩定的放最前面：工具定義、系統提示、固定的參考文件。
  2. 會變的放最後面：使用者的新問題、時間、本次的資料。
✗ 改寫前
system： 今天是 2026-10-05 14:32:07。 你是客服助理……（以下 5,000 字的規則與產品資料）
✓ 改寫後
system： 你是客服助理……（5,000 字的規則與產品資料，固定不變） user： （今天日期：2026-10-05） 客人的問題：……
  • 把每次都不同的時間戳記從開頭移到最後，前面 5,000 字就能被快取

☁️ Claude API 範例（需要 pip install anthropic 與 API 金鑰）　開啟提示快取並檢查是否命中

import anthropic client = anthropic.Anthropic() RULES = open("customer_service_rules.txt", encoding="utf-8").read() # 長而固定的規則 r = client.messages.create( model="claude-opus-5-5", max_tokens=16000, cache_control={"type": "ephemeral"}, # 自動在最後一個可快取區塊設快取點 system=RULES, # 固定內容放前面 messages=[{"role": "user", "content": "（今天 10/5）我的訂單什麼時候到？"}], # 變動內容放後面 ) u = r.usage print("讀取快取:", u.cache_read_input_tokens, "寫入快取:", u.cache_creation_input_tokens)

🧭 這一課的重點

提示快取在請求開頭與上次相同時重用計算結果，降低費用與延遲，代理與聊天機器人最受惠。快取是前綴匹配，遇到第一個不同的字後全部失效，所以最穩定的內容（工具、系統提示、參考文件）放前、會變的（新問題、時間）放後。

✍️ 提示工程的最佳做法會隨模型世代改變；本課以目前主流模型（特別是 Claude）的實際行為為例，原則大多通用。Python 範例中標示「已執行」的為離線程式，輸出是實際結果；呼叫 API 的範例需要金鑰，模型名稱與參數以官方文件為準。

  3. 為什麼把時間戳記放在系統提示開頭會讓快取失效？
