安全（二）：防護欄不能只寫在提示裡

這一課的目標

  • 理解只靠提示防禦的局限
  • 設計程式層的防護
  • 防止資料外洩

一個關鍵觀念：沒有任何提示寫法能保證模型不被繞過。所以真正的安全要放在提示以外：

防護層做法
最小權限只給模型完成任務所需的工具與資料；客服機器人不需要「查詢所有客戶」的權限
使用者身分工具在程式層檢查身分，只能查這位使用者自己的資料，不依賴模型判斷
輸出檢查用程式過濾個資、檢查連結是否在白名單、驗證格式
人工確認付款、寄信、刪除等不可逆動作需要人按確認
隔離讀取不可信內容的模型不給敏感工具；或分成兩個模型分工
監控記錄與警示異常行為
  • 系統提示不是秘密：假設使用者最終能看到系統提示。不要把 API 金鑰、密碼、內部網址寫在裡面。
  • 資料外洩的常見路徑：模型輸出一個包含資料的連結或圖片網址，瀏覽器載入時就把資料送出去了。對策是限制可輸出的網址。

🧭 這一課的重點

沒有任何提示寫法能保證不被繞過，真正的安全要靠縱深防禦：最小權限、在程式層檢查使用者身分、輸出檢查（個資過濾、連結白名單）、不可逆動作人工確認、隔離讀取不可信內容的模型與監控。系統提示不是秘密，不能放金鑰；要防範透過連結或圖片網址外洩資料。

✍️ 提示工程的最佳做法會隨模型世代改變；本課以目前主流模型（特別是 Claude）的實際行為為例，原則大多通用。Python 範例中標示「已執行」的為離線程式，輸出是實際結果；呼叫 API 的範例需要金鑰，模型名稱與參數以官方文件為準。

檢查你的理解

  1. 為什麼防護欄不能只寫在提示裡？
  2. 「最小權限」在客服機器人中是什麼意思？
  3. 為什麼不能把 API 金鑰寫在系統提示中？
