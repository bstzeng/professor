Level 4｜Engineering：把提示當成軟體 · 第 42 課

失敗分類

這一課的目標

  • 認識常見的失敗類型
  • 把失敗案例歸類
  • 根據類型選擇修法

評估跑完後，不要只看通過率。把每個失敗案例歸類，你會發現失敗通常集中在少數幾種模式。每種模式有不同的修法——用錯方法修，只會越改越亂。

失敗案例類型修法
回答了知識庫沒有的退貨地址幻覺強化「只根據資料」並允許說不知道
JSON 少了 status 欄位格式錯誤改用結構化輸出
要求 3 句以內，回了 8 句不遵守指令說明理由（聊天視窗很小），檢查是否有矛盾指令
拒絕回答「如何退訂」過度拒答刪掉過於籠統的「不要討論帳號」
問運費，回答了配送時間答非所問檢查檢索結果是否正確
多步驟計算算錯能力不足開啟思考、改用工具計算

先找根本原因

「答非所問」的根本原因常常不在提示，而在檢索（第 20 課）——放進上下文的資料本身就不對。分類時要追問：問題出在提示、上下文、工具，還是模型能力？

🧭 這一課的重點

評估後要把失敗案例歸類，失敗通常集中在少數模式：幻覺、格式錯誤、不遵守指令、過度拒答、答非所問、能力不足，各有不同修法。分類時要追問根本原因在提示、上下文、工具還是模型能力，例如答非所問常是檢索問題。

✍️ 提示工程的最佳做法會隨模型世代改變；本課以目前主流模型（特別是 Claude）的實際行為為例，原則大多通用。Python 範例中標示「已執行」的為離線程式，輸出是實際結果；呼叫 API 的範例需要金鑰，模型名稱與參數以官方文件為準。

檢查你的理解

  1. 為什麼不能只看通過率？
  2. 「過度拒答」通常怎麼修？
  3. 「答非所問」的根本原因可能在哪裡？
