保護 main 分支

這一課的目標

  • 理解為什麼要保護分支
  • 設定常見的保護規則
  • 認識 CODEOWNERS 與合併佇列

團隊大了，總會有人不小心直接 push 到 main、或合併了測試沒過的 PR。GitHub 可以替分支加上規則（Settings → Rules → Rulesets，舊介面為 Branches → Branch protection rules）：

規則效果
Require a pull request before merging不能直接 push，一定要透過 PR
Required approvals至少要幾個人 Approve
Require status checks to pass指定的 CI 檢查（例如測試）要綠燈才能合併
Require branches to be up to datePR 分支必須包含 main 的最新 commit
Block force pushes禁止強制推送
Restrict deletions禁止刪除這個分支
Require signed commitscommit 必須有簽章
Require linear history禁止合併 commit（只能 squash 或 rebase）

CODEOWNERS

在 .github/CODEOWNERS 檔案中指定誰負責哪些檔案，有人修改時會自動請他審查：

# 預設：前端組審查所有檔案 * @ming-org/frontend # 資料庫相關要 DBA 審查 /db/ @hua *.sql @hua # 文件 /docs/ @ming

搭配「Require review from Code Owners」規則，就能確保重要的檔案一定經過負責人看過。

大型專案還可以開啟 Merge queue（合併佇列）：多個 PR 排隊，GitHub 依序把它們與最新的 main 組合起來再測一次，避免「兩個各自都通過的 PR 合在一起卻壞掉」。

🧭 這一課的重點

分支規則（Rulesets 或 Branch protection rules）可要求透過 PR 合併、需幾人核准、CI 檢查通過、分支須最新，並可禁止強制推送與刪除、要求簽章或線性歷史。.github/CODEOWNERS 指定檔案負責人並自動請其審查，可搭配要求 Code Owner 審查。Merge queue 讓多個 PR 依序與最新 main 一起測試再合併。

🐙 本課程的 Git 指令範例都在 Git 2.43 實際執行過，畫面上的輸出就是當時的結果（日期固定，所以雜湊值可重現）；範例中的「GitHub 遠端」是用本機的裸倉庫模擬的，指令與真正連到 GitHub 時相同，只有網址不同。GitHub 網站的按鈕位置與名稱偶爾會改版，以官方說明為準。

  2. CODEOWNERS 檔案的作用是什麼？
  3. Merge queue 解決了什麼問題？
