Code Review

這一課的目標

  • 在 PR 上留言與建議修改
  • 理解 Approve 與 Request changes
  • 學會給與接受回饋

PR 頁面有四個分頁：Conversation（討論）、Commits、Checks（自動檢查）、Files changed（差異）。審查主要在 Files changed 進行：

  • 點某一行左邊的 ＋ 號留言；拖曳可以選多行。
  • 留言時按 Suggest changes 圖示，可以直接寫出建議的程式碼，作者按一下 Commit suggestion 就會套用。
  • 所有留言寫完後按 Review changes，選一個結論：
結論意思
Comment只是留言，沒有表態
Approve核准，可以合併
Request changes需要修改後才能合併（如果有設定保護規則，會擋住合併）

作者修改後回覆留言並按 Resolve conversation，然後按 Reviewer 旁的🔄重新請求審查。

審查的禮儀

審查者作者
對事不對人：「這裡可能會漏掉空字串」而不是「你寫錯了」不要把審查當成攻擊；它是在幫你抓 bug
區分必要與建議：用「nit:」標示小地方（不改也行）不同意就說明理由，討論是正常的
說明理由，附上文件或範例每則留言都回覆或處理，不要默默忽略
也稱讚寫得好的地方感謝審查者花的時間

Code Review 不只是抓錯：它讓團隊中至少有兩個人懂每一段程式碼，也是新人學習的好機會。

🧭 這一課的重點

PR 有 Conversation、Commits、Checks、Files changed 分頁；在 Files changed 點行號旁＋留言、用 Suggest changes 寫出建議程式碼讓作者一鍵套用，最後以 Comment、Approve 或 Request changes 結論。作者修改後 Resolve 並重新請求審查。審查應對事不對人、區分必要與 nit、說明理由；作者應把審查當幫助並回應每則留言。

🐙 本課程的 Git 指令範例都在 Git 2.43 實際執行過，畫面上的輸出就是當時的結果（日期固定，所以雜湊值可重現）；範例中的「GitHub 遠端」是用本機的裸倉庫模擬的，指令與真正連到 GitHub 時相同，只有網址不同。GitHub 網站的按鈕位置與名稱偶爾會改版，以官方說明為準。

檢查你的理解

  1. Approve 和 Request changes 有什麼差別？
  2. Suggest changes 的好處是什麼？
  3. nit: 是什麼意思？
