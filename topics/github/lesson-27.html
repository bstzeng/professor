分支策略

這一課的目標

  • 認識三種常見的分支策略
  • 比較它們的適用情境
  • 為自己的專案選擇策略

團隊要約定「什麼時候開分支、合併到哪裡」。三種常見做法：

策略規則適合
GitHub Flowmain 永遠可以部署；每件工作開一個短命分支 → Pull Request → 審查 → 合併回 main → 部署網站、持續部署的服務，大多數團隊
Git Flowmain（正式版）＋ develop（開發中）＋ feature／release／hotfix 分支，各有合併規則有明確版本發布週期的軟體（例如 App、桌面軟體）
主幹開發（Trunk-based）大家頻繁地（每天）把小改動合併進 main，未完成的功能用「功能開關」藏起來高度自動化測試的大團隊（Google 等）

給初學者與小團隊的建議：用 GitHub Flow。規則只有一條——不要直接在 main 上 commit，任何修改都開分支、發 PR。它簡單、跟 GitHub 的功能完美搭配，本課程後面的協作流程都以它為準。

🧭 這一課的重點

GitHub Flow：main 永遠可部署，每件工作開短命分支、發 PR 審查後合併；Git Flow：main 加 develop 加 feature、release、hotfix 分支，適合有版本週期的軟體；主幹開發：每天把小改動併入 main、用功能開關隱藏未完成功能，適合高度自動化的大團隊。初學者與小團隊建議用 GitHub Flow。

🐙 本課程的 Git 指令範例都在 Git 2.43 實際執行過，畫面上的輸出就是當時的結果（日期固定，所以雜湊值可重現）；範例中的「GitHub 遠端」是用本機的裸倉庫模擬的，指令與真正連到 GitHub 時相同，只有網址不同。GitHub 網站的按鈕位置與名稱偶爾會改版，以官方說明為準。
