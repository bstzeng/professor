merge 還是 rebase？

這一課的目標

  • 記住 rebase 的黃金守則
  • 知道兩者常見的使用時機
  • 認識 pull 的兩種模式

黃金守則：不要 rebase 已經 push、別人可能已經拿到的 commit。

原因：rebase 會產生新 commit、丟掉舊的。如果同事的分支是建立在你的舊 commit 上，你 rebase 後強制推送，他的歷史就和 GitHub 對不上，會出現重複的 commit 和一堆莫名的衝突。

情境建議
自己的功能分支，還沒 push 或只有你在用可以 rebase main，讓 PR 歷史乾淨
把功能合併回 main在 GitHub 上用 Pull Request 合併（第 31 課的三種方式）
main、develop 等共用分支永遠不要 rebase、不要強制推送
pull 時本機和 GitHub 都有新 commit可以設定 pull 用 rebase，避免多出無意義的合併 commit

最後一種情況很常見：你和同事都 push 了 main，你的 push 被拒絕：

▶ 動手做　實際執行的輸出

$ git push To /home/ming/github/ming/demo.git ! [rejected] main -> main (fetch first) error: failed to push some refs to '/home/ming/github/ming/demo.git' hint: Updates were rejected because the remote contains work that you do not hint: have locally. This is usually caused by another repository pushing to hint: the same ref. If you want to integrate the remote changes, use hint: 'git pull' before pushing again. hint: See the 'Note about fast-forwards' in 'git push --help' for details. $ git pull From /home/ming/github/ming/demo 562cf03..b08ec1d main -> origin/main Successfully rebased and updated refs/heads/main. $ git log --oneline --graph * 7e3caea 筆電：加入 LICENSE * b08ec1d 桌機的修改 * 562cf03 Initial commit $ git push To /home/ming/github/ming/demo.git b08ec1d..7e3caea main -> main

範例中設定了 git config pull.rebase true，所以 git pull 用 rebase 把你的 commit 接在同事的之後，歷史保持一直線。若不設定，新版 Git 在兩邊分岔時會要求你選擇：git pull --rebase 或 git pull --no-rebase（merge）。

真的需要覆蓋遠端時（例如 rebase 了自己的 PR 分支），用 git push --force-with-lease 而不是 --force：前者會先確認遠端沒有你不知道的新 commit，避免覆蓋掉別人的工作。

🧭 這一課的重點

rebase 的黃金守則：不要 rebase 已經 push、別人可能拿到的 commit，否則他人的歷史會對不上。自己未分享的功能分支可以 rebase main；共用分支永不 rebase 或強制推送。push 被拒時 pull 可設定 pull.rebase true 讓歷史保持直線。需要覆蓋遠端時用 --force-with-lease 而非 --force。

🐙 本課程的 Git 指令範例都在 Git 2.43 實際執行過，畫面上的輸出就是當時的結果（日期固定，所以雜湊值可重現）；範例中的「GitHub 遠端」是用本機的裸倉庫模擬的，指令與真正連到 GitHub 時相同，只有網址不同。GitHub 網站的按鈕位置與名稱偶爾會改版，以官方說明為準。
