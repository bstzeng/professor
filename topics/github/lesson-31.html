三種合併方式

這一課的目標

  • 比較 GitHub 的三種合併按鈕
  • 看出各自產生的歷史
  • 為團隊選擇合併方式

GitHub 的合併按鈕旁有一個下拉選單，提供三種方式：

方式結果優點缺點
Create a merge commit保留分支所有 commit，再加一個合併 commit完整保留真實歷史main 的歷史有很多分岔與「修錯字」之類的小 commit
Squash and merge把 PR 所有 commit 壓成一個 commit 放到 mainmain 上一個 PR 一個 commit，非常乾淨分支內的細節歷史消失
Rebase and merge把 PR 的每個 commit 複製到 main 最後面，不產生合併 commit一直線，保留每個 commitcommit 雜湊改變；每個 commit 都要有意義

Squash 是很多團隊的預設選擇。它在本機的等價指令是 git merge --squash：

▶ 動手做　實際執行的輸出

$ git merge --squash feature-login Updating edad20f..8adfe29 Fast-forward Squash commit -- not updating HEAD login.py | 3 +++ 1 file changed, 3 insertions(+) create mode 100644 login.py $ git commit -q -m "登入與登出功能 (#12)" $ git log --oneline --graph * 9488826 登入與登出功能 (#12) * edad20f 加入 app.py * 582091b 初始提交：加入 README

分支上的三個 commit（包括「修錯字」）在 main 上變成了一個「登入與登出功能 (#12)」。GitHub 預設會在 squash 的訊息後面附上 PR 編號，方便日後追查。

倉庫管理者可以在 Settings → General → Pull Requests 中只開放其中幾種方式。另外，Squash 或 Rebase 合併後，本機的功能分支在 Git 看來「沒有被合併」（因為 main 上的是新 commit），所以要用 git branch -D 刪除。

🧭 這一課的重點

GitHub 有三種合併方式：Create a merge commit 保留所有 commit 加合併 commit（真實但雜亂）；Squash and merge 把 PR 壓成一個 commit（乾淨但失去細節，常見預設）；Rebase and merge 把每個 commit 複製到 main 後面（直線但雜湊改變）。squash 對應 git merge --squash。管理者可在設定中限制方式；squash／rebase 後本機分支要用 -D 刪除。

🐙 本課程的 Git 指令範例都在 Git 2.43 實際執行過，畫面上的輸出就是當時的結果（日期固定，所以雜湊值可重現）；範例中的「GitHub 遠端」是用本機的裸倉庫模擬的，指令與真正連到 GitHub 時相同，只有網址不同。GitHub 網站的按鈕位置與名稱偶爾會改版，以官方說明為準。

檢查你的理解

  1. Squash and merge 會在 main 產生幾個 commit？
  2. 哪種方式會保留分支上的每一個 commit 且不產生合併 commit？
  3. squash 合併後為什麼本機分支要用 -D 刪除？
