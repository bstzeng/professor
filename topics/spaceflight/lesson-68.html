1202 警報：那台電腦到底發生什麼事

這一課的目標

  • 理解 1202 警報的真正成因
  • 看懂重啟保護機制如何救了這次登月
  • 認識「優雅降級」這個設計原則

1. 事件經過

阿波羅 11 號，動力下降中 PDI + 5:16 高度 9,700 m DSKY 顯示：PROGRAM ALARM 代碼：1202 Armstrong：「Program alarm.」 「It's a 1202.」 「Give us a reading on the 1202 program alarm.」 任務控制中心，約 15 秒後 導引官 Steve Bales：「We're GO on that alarm.」 CAPCOM Charlie Duke：「Roger, we're GO. We're GO on that alarm.」 之後又出現四次（1202 三次、1201 兩次）， 最後一次在高度 600 公尺左右。 每一次都回答 GO。

那 15 秒是整個計畫最緊繃的 15 秒之一。

2. 代碼的意思

代碼意思
1201NO VAC AREAS（沒有可用的向量累加區）
1202EXECUTIVE OVERFLOW — NO CORE SETS（執行緒表滿了）
兩者都是「記憶體不夠」的警報 AGC 的 EXEC（第 40 課）用一組固定數量的 「core set」（每個約 12 個字）來記錄正在執行的工作。 可用的 core set 數量：7 個 可用的 VAC area（向量暫存區）：5 個 當有新工作要排程，但沒有空的 core set 時 → 觸發 1202 這不是當機，是一個「我過載了」的通知。

3. 為什麼會過載

真正的原因在 1969 年花了幾天才查清楚。

直接原因：會合雷達持續送出中斷請求 登月艙上有兩具雷達 著陸雷達（LR）—— 下降時必須用 會合雷達（RR）—— 上升會合時才用 檢查清單要求在下降時把 RR 的開關 設在「AUTO TRACK」位置， 目的是：如果需要中止，RR 已經在追蹤 CSM， 可以立刻開始會合。 問題出在電源相位 RR 的角度編碼器（CDU）用 800 Hz 交流電驅動。 LM 有兩個 800 Hz 電源：一個給 RR，一個給 AGC。 兩者的相位沒有被鎖定（設計上認為不需要）。 當兩者相位差很大時， 角度編碼器會不斷回報「角度在變化」—— 即使天線根本沒有動。 每一次「變化」都觸發一次中斷， 要求 AGC 執行一小段程式來更新角度。
量化 正常情況：RR 的 CDU 中斷佔用約 0% 的 CPU 異常情況：每秒約 12,800 次中斷 每次約 45 微秒 → 佔用約 13% 的 CPU 時間 而動力下降本身已經用掉約 85% 的 CPU。 85% + 13% = 98% ... 還不到 100%？ 問題在於：不只是 CPU 時間，還有 core set。 中斷處理程式需要佔用一個 core set， 而在尖峰時所有 7 個都被占滿。 → 1202

為什麼相位會不對？ 因為 LM 的兩個 800 Hz 電源 本來是設計成同一個來源， 但在某個設計修改中變成了兩個獨立的來源， 而沒有人追蹤到這個改變對 AGC 的影響。

更巧的是：這個問題在阿波羅 5 號（無人）與 10 號的測試中 都沒有出現，因為那些飛行的 RR 開關位置不同。

4. 為什麼可以回答 GO

關鍵在 Margaret Hamilton 團隊寫進 EXEC 的 重啟保護機制（第 40 課）。

機制 1. 偵測到 core set 用盡 2. 立刻執行「軟體重啟」（software restart） 3. 重啟不是關機重開 —— 它： 清空所有 core set 從每個工作登記的「重啟點」恢復 依優先權重新排程 4. 高優先權工作（導引、姿態控制、節流） 在幾十毫秒內恢復 5. 低優先權工作（顯示更新、非必要的計算） 被放棄 整個過程約 0.3 秒。 對太空人來說：DSKY 閃了一下， 導引與引擎控制從未中斷。

5. 那 15 秒裡發生了什麼

Steve Bales（導引官，當時 26 歲） 他身後的後援室裡是 Jack Garman（24 歲）， MIT 軟體團隊的聯絡人。 幾週前的一次模擬中， 出現過一個不同的程式警報， Bales 錯誤地下令中止 —— 事後檢討認為那是不必要的。 之後 Garman 手寫了一張清單： 每一個可能的程式警報代碼， 以及「什麼情況下可以繼續」。 1202 在那張清單上，標註是： 「只要它不是連續不斷地出現，而且導引資料看起來正常，就可以繼續。」 當警報出現時，Garman 看了一眼遙測： 高度、速度、推力都正常 導引資料在更新 → 對 Bales 說「GO」 Bales 對飛航主任 Gene Kranz 說「GO」。

整個判斷建立在兩件事上： 一份因為先前一次模擬失誤而製作的清單， 以及「遙測資料顯示導引仍在正常運作」這個獨立證據。

6. 後續的修正

改變內容
檢查清單阿波羅 12 號起，下降時 RR 開關改到不同位置
硬體後續的 LM 修改了 800 Hz 電源的配置
軟體改進 EXEC 對中斷洪水的處理
程序把程式警報的判斷準則正式寫進飛行規則

7. 這件事真正的教訓

流行的說法是「太空人靠冷靜救了任務」， 或「電腦差點毀了登月」。 兩者都不準確。

真正發生的是：一個被設計來「優雅降級」的系統， 在過載時正確地降級了。 它沒有當機 它沒有停止導引 它沒有把控制權交給一個不知所措的人 它丟掉了最不重要的工作，保住了最重要的 而它會這樣做，是因為 Margaret Hamilton 的團隊堅持要寫這些 「反正不會用到」的錯誤處理程式碼 —— 儘管當時有人認為那是浪費寶貴的記憶體。 三個獨立的防線同時發揮作用 1. 軟體的重啟保護（技術） 2. Garman 的警報清單（知識管理） 3. 遙測可以獨立驗證導引是否正常（可觀測性） 任何一個缺席，那 15 秒的答案可能就是「ABORT」。

這是一個關於「為不會發生的事做準備」的故事。 而它的價值只有在那件事真的發生時才會顯現。
